===========================

           version", Douglas Sherk, 2020-05-07), the head of the repository's default branch
Copied:    2026-11-02: every file the repository tracks (230), byte for byte, line endings as

What it is
----------
README is upstream's own. base\ is Apollo RP's main package: AMX Mod X plugins (sources in
base\addons\amxmodx\scripting, ARP_*.sma with include\ApolloRP*.inc, arrayx_travtrie.inc and
celltravtrie.inc), their configs (base\addons\amxmodx\configs\arp\: arp.ini, arp.cfg, and a folder
a map with its SQL and its ini files), models\arp and sound\arp. extra\ holds the author's other
plugins and website\ the old apollorp.org site. The .amxx files under base\addons\amxmodx\plugins are
upstream's own builds: H9 never ships them, build.bat builds its own into TSM\compiled. Upstream's
plugins-arp.ini and modules.ini are not installed either: build.bat lists the plugins in plugins.ini.

H9's changes (H9.patch, H9-menus.patch and H9-arpfix.patch, beside this file, are the whole diff against the commit above)
--------------------------------------------------------------------------------------------------------------------------
H9.patch is the diff against the commit above as of 2026-11-03 (items 1 to 13); H9-menus.patch (item 14, 2026-11-08) and
H9-arpfix.patch (items 15 to 17, 2026-11-09) hold the later changes, each a diff against the files as they stood before it;
H9-arpcontent.patch (the two plugin changes of item 19, 2026-11-09), H9-arphud.patch (item 21) and H9-arpaudit.patch (items 22 and 23, 2026-11-09) and H9-arpneeds.patch (item 26, 2026-11-10), H9-arpthirst.patch (item 27), H9-arpitemhover.patch (item 28), H9-arpinventory.patch (items 29 to 33, 35 and 36, 2026-11-10), H9-arpitemicon.patch (item 28's picture, 2026-11-10), H9-arpweapons.patch (item 34, 2026-11-10), H9-arpplaque.patch (item 41, 2026-11-11), H9-arpitemworld.patch (item 28's picture in the world and its look-at branch, 2026-11-11), H9-arpcuff.patch (item 39's lighting, 2026-11-11), H9-arpowner.patch (item 42's owner keys, 2026-11-11), H9-arpiconfix.patch (items 28 and 39: the pictures unlit,
room in the entity table, 2026-11-11) and H9-arpteams.patch (item 43, 2026-11-11) come after
(item 20 is a default in arp.cfg and ARP_Core.sma, in no patch).
In base\addons\amxmodx\scripting, only in the set H9 builds for The Specialists: ARP_Core,
ARP_Commands, ARP_Config, ARP_HUD, ARP_HungerMod, ARP_Items, ARP_JailMod, ARP_NPCs, ARP_RobMod,
ARP_TalkArea, ARP_Zones, ARP_TS, ARP_H9Menu (H9's own, in no patch), ARP_Inventory (items 31, 32) and ARP_PropertyTax (item 42, H9's own, in no patch). ARP_CS, ARP_TFC, ARP_BCompat and extra\ are not built. And two
folders of H9's own maps under base\addons\amxmodx\configs\arp\maps (item 13).

1. Roleplay maps only (ARP_Core, plugin_precache). On a map whose name is not a roleplay one -- rp_
   or tsrp_ at the start, or _rp_ or _tsrp_ inside it, in any case: the rule of ts_matchmode's
   roleplay_map() and of tsrp_roambots -- H9_StandDown() pauses every loaded ARP_*.amxx and then the
   core itself, before their own precache runs. A paused plugin stays loaded and gets no forward,
   hook, command or task: no config is read, no database opened, no player touched, and the next map
   loads them all afresh. The core is listed first in plugins.ini, so it runs first.
2. A map's data keyed by its name (ARP_Core). The properties, doors and keys tables carry the map's
   name -- arp_property_<map>, arp_doors_<map>, arp_keys_<map>, the name in lower case with anything
   but letters and digits as "_" -- so one database serves every roleplay map. Users, jobs, items and
   data stay shared. The per-map files under configs\arp\maps\<map>\ (npcs.ini, jailmod.ini, rob.ini,
   zones.ini, the map's SQL) were the map's own already.
3. The SQL driver (ARP_Core). arp.ini's sqlite is loaded with the core (#pragma loadlib sqlite): sqlx
   alone loads mysql, its default, and H9's configs\modules.ini does not list sqlite.
4. Player slots. Every per-player array sized for 32 slots is sized by MAX_PLAYERS (H9's AMX Mod X is
   built for 128), and so are the get_players buffers (with H9's MAX_PLAYERS a smaller one does not
   compile) and the three per-player loops.
5. TS ammo (ARP_TS, ARP_NPCs). Each carried its own ts_setuserammo, Avalanche's code that writes TS
   3.0's private data offsets; it clashed with TSX's native of the same name and is gone, so both
   call the native, which H9's TSX provides for TS 3.0 and reTS alike.
6. TS weapon numbers (ARP_TS, ARP_NPCs). Their tables -- a gun's attachments, the ammunition it
   loads, the ammunition item it takes -- go by weapon id, and were written for 36 kung fu, 37 the
   throwing knife and 38 the Contender. H9's TSX uses the game's own ids (tsconst.inc): 0 kung fu,
   2 the Beretta 92F, 36 the Contender, 37 the akimbo Skorpions, 38 the throwing knife -- the order
   ARP_TS's own item names already had. The rows follow it now; the Beretta and the akimbo Skorpions
   load as the akimbo Berettas and the Skorpion do, and ARP_NPCs' ammunition table reaches 38.
7. ARP_Items' Ham_TakeDamage (the assassin knife) stays on the hook ts_matchmode uses for damage and
   assists, which H9's mp.dll (reTS) delivers, and logs its first hit on each map as the proof.
8. Jobs (ARP_Core). A database with no jobs -- a fresh one, on a map no SQL file was loaded for --
   left every player on job -1, and every look-up of his job read the job array of handle 0: the
   hover line every frame and the HUD every second (TrieKeyExists on an invalid handle, which also
   stopped the HUD's own task for the rest of the map), and the save. The core makes "Unemployed"
   once the jobs are read when there is none, takes the 1-based id ARP_FindJobId gives as such, adds
   the job with the id it is given, and looks a job up only when it is there.
9. Bots (ARP_Core). Bots share one auth id, so the first one made a row and every other one failed
   on its UNIQUE key: bots are neither loaded from the database nor saved to it, and are Unemployed
   with nothing for as long as they stay.
10. More slot encodings. The tasks that carried a player as id + 32 (the core's retry of a player
   still being saved, ARP_Items' hallucination, ARP_TalkArea's 911 sounds) carry id + MAX_PLAYERS;
   a property's key holders, one 32-bit mask (so slot 33 held slot 1's keys), are a bit for each
   slot, 32 to a cell (H9_HasKey, H9_SetKey: cell 8 as before, then cells 101 on); ARP_TalkArea's
   bugs are a cell for each pair of slots, and a player who leaves takes the bugs he planted.
11. The jails (ARP_JailMod). A map without a jailmod.ini has no jails, and the plugin runs (it
   stopped itself). jail <command> numbers jails from 1, as the menu does. A jail may name its
   cell's own controls in the map -- cage (the door that shuts it), toggle (what opens and shuts it)
   and panel (the cell's wall panel) -- and then jailing a player shuts the cage on him, freeing him
   opens it, and the panels are the doors of one locked property, "h9_jail", that only police use.
12. The HUD (ARP_Core, RenderHud). A HUD with nothing to show is cleared once and not sent again
   until it has something: ARP's four HUDs no longer hold all four of AMX Mod X's HUD channels
   every second, so other plugins' HUD text does not fight them for one.
13. H9's maps (configs\arp\maps). h9_tsrp_hive: its jailmod.ini, the four cells of the Alexandria
   jail wired to the map's cages (al_cell1-4), managers (al_cell1mm-4mm) and panels
   (al_jail1act-4act), and an empty zones.ini. h9_tsrp_newbyzantium: an empty jailmod.ini and
   zones.ini. Neither has a rob.ini. Their NPCs and jobs are item 19.

14. H9 VGUI menus (every plugin that shows a menu: ARP_Core, ARP_Commands, ARP_Config, ARP_Items,
   ARP_JailMod, ARP_NPCs, ARP_TalkArea, ARP_TS). Each menu is also an H9 VGUI panel for a player whose
   game draws them. include\ApolloRP_VGui.inc, new, wraps include\h9_vgui.inc: a plugin calls
   arpvgui_precache() in plugin_precache and arpvgui_init("<ns>") in plugin_init; show_menu() became
   arpvgui_show_menu(..., "<ns>.<name>") (16 menus), and menu_display() on a menu_create() menu became
   arpvgui_menu_display(id, menu, panel, title, handler) (6 menus; the plugin defines ARPVGUI_PAGED
   before the include). Any other player, and a player whose cl_h9_arpvgui is 0 (arpvgui_wanted reads the
   _h9arpvgui key of his userinfo), gets the call it replaces, unchanged. docs\H9_VGUI.txt 1e lists every menu.

15. Characters across a server address change (ARP_Core, include\ApolloRP_Player.inc, ApolloRP_Properties.inc).
   H9XASH makes a player's authid per server (ID_ and an MD5 of his id and the server's IPv4), and ARP keys
   everything on it. ARP_Core now keeps a character's key (ARP_GetUserKey, the authid its rows are under) and
   makes a table, arp_ids (authid, account), beside the others: when h9_presence proves a player's havoc9.org
   account (h9p_account, a second or two after he is in game), his authid is recorded with it; the first authid
   recorded for an account is its character's key, and a join under any authid of the account reads the
   character under that key. A player no row knows waits for the proof, up to arp_account_wait seconds (30; 0
   leaves it all out), then gets a character of his own. Nothing is rewritten: rows of the other tables stay
   under the authid they were made with. ARP_IDS.txt has the migration and the way back.

16. SQL values (include\ApolloRP_SQL.inc, ARP_Core). ARP_SqlEscape quotes with the SQL module's SQL_QuoteString
   (it did its own replace_all, wrong for MySQL), and every authid, key and name that reaches a query is quoted:
   UTIL_ARP_AddJob used the job name it had not quoted. A property owner's authid is read 35 characters long (32
   cut an H9XASH authid), and a key row is read 95 (64 cut a long property name after one).

17. Bots (ARP_Core). No HUD is sent to a bot, nor its hover line: nothing reads a bot's datagram, and the
   engine logged "Datagram overflowed" for them every second (ts\logs\h9_overflow.log).

18. Jobs by map (ARP_Core). A map's folder may hold an arp.ini of its own, which the core reads after the server's, so it can
   name tables of its own (arp_table_jobs, arp_table_users, arp_table_items; upstream's own override). H9's two maps use it for
   their jobs (arp_table_jobs "arp_jobs_<map>"), so a server's other maps do not get H9's jobs. A character whose saved job is
   not in the map's jobs table is Unemployed there, as before, and his saved job is kept (g_KeptJob): the save writes it back as it
   was, unless he takes another job on that map (the SetUserJob native or a deleted job clears it), and the notice says the job is
   not offered on this map. A visit to another map does not cost a character his rank.

19. H9's content (configs\arp\maps\<map>\npcs.ini and <map>.sql, docs\ARP_CONTENT.txt). Each of the two roleplay maps has NPCs that
   open its menus (shops, bank tellers, ATM droids, doctors, a gun shop, ammunition and licence counters, the Ministry quartermaster),
   standing where docs\ARP_CONTENT.txt (section 6) puts them, and an SQL file with the Ministry of Defense ranks and a civilian layer as jobs (INSERT OR
   IGNORE, loaded by an admin with arp_config > Load Map SQL Data into the map's own jobs table). Two plugin changes, in
   H9-arpcontent.patch: ARP_Core's ARP_FindJobId copies at most the caller's MaxResults ids into its array (a short name that matched
   more jobs wrote past the array of arp_setjob and arp_employ), and arp_setjob and arp_employ take the job whose name is exactly the
   argument although a longer name holds it too (Cadet and M-Cadet).

Building and running it
-----------------------
build.bat builds the fourteen with the game's amxxpc, deploys them, lists them in plugins.ini with
ARP_Core first, and copies configs\arp\, models\arp and sound\arp into the live install; export.bat
carries them, and this folder, on. ARP uses the AMX Mod X modules engine, fakemeta, hamsandwich,
fun, tsx, tsfun and sqlite, all in H9's build (TSM\AMXMODX). On a roleplay map without a folder of
its own under configs\arp\maps the core logs "Configuration directory missing" and runs with no
doors, properties, NPCs or zones until one is made; H9's two have theirs (item 13).

20. arp_godwindows (configs\arp\arp.cfg, and the default register_cvar gives it in ARP_Core.sma) is 0, not 1: only func_door and
   func_door_rotating are unbreakable (arp_goddoors 1), and func_breakable (manhole covers, vents, glass, crates) can be broken. Set it to 1 to protect them too.

21. The HUD as panels (ARP_Core, ARP_HUD, include\ApolloRP_HUD.inc; H9-arphud.patch). A player whose game says it can
   (the userinfo key _h9arphud, which H9's client keeps at 1 while cl_h9_arphud and cl_h9_vgui are not 0) is sent each of ARP's
   four HUDs as lines in the user message H9ArpHud, reliably (MSG_ONE; an unreliable message rides in the datagram the entities
   fill on a big map, and the engine drops a datagram that does not fit whole, the way ts\logs\h9_overflow.log reports
   "Datagram overflowed"), in place of the hudmessage; every other player, and every bot, keeps the hudmessage exactly as before.
   RenderHud gathers the lines of a HUD as it always did and, for a panel player, sends them (ArpHudSend): a message is op 1, hud,
   the content's number, the part (bit 7 on the last), the line count, then in part 0 the HUD's x and y (arp_hudN_x and _y in
   thousandths) and for each line a kind byte and the text, at most 184 bytes; a longer HUD is sent in parts, and the client keeps
   what it had until the last part has come. A HUD is sent when its lines, kinds or place change and again after arp_hud_refresh
   seconds (10, 5 to 60); the notice (HUD 4) after a second and a half when unchanged. A HUD that empties is taken down once (op 2);
   a player moved between the two forms has the other form taken down (an empty hudmessage on each channel, or op 3).
   arp_hud_panel (1) is the server's switch: 0 sends everyone the text HUD. ShowHud decides each player's form once a pass
   (ArpHudUpdate): the panel needs arp_hud_panel 1, the message registered (plugin_precache, after arpvgui_precache), h9vgui_supported
   (h9_vgui 1, _h9vgui, not a bot) and _h9arphud at 1; the log has a line when his form changes, with the reason, and one when
   the first panel update goes to him. arp_hudstate (a console command, so the server console can ask; ARP_CmdAccess) lists every
   player, his form and the reason, the userinfo key as the server reads it, the messages sent and the last lines of each HUD.
   Each line of a HUD now has a kind: the value the HUD's trie holds for its line is HUDK_* (it was the channel, which nothing
   read). The new native ARP_AddHudItemKind(id, channel, refresh, kind, text, ...) adds a line of a kind (a channel outside 0 to
   HUD_NUM - 1 is refused; ARP_AddHudItem's own test, "> HUD_NUM", is left as it was); ARP_AddHudItem adds HUDK_EXTRA. ARP_HUD
   gives its lines HUDK_TITLE (the title and the blank line after it), _WALLET, _BANK, _PAYDAY, _SALARY, _JOB and _STATUS (the
   dead, account loading and malfunction lines); the lines the other plugins add (jail, zone, alcohol, the third HUD's chat) stay
   HUDK_EXTRA (hunger is a need since item 26). ARP_HUD needs this ARP_Core: against an older one it fails to load (native ARP_AddHudItemKind not found);
   build.bat builds both. UTIL_ARP_AddHudItem and AddItem take the kind. docs\APOLLO_RP.txt 2 says what a player sees.

22. Trie lists (include\celltravtrie.inc; H9-arpaudit.patch). TravTrieClear empties the trie and puts the list of its keys back under
   the "" key, where TravTrieCreate keeps it. AMX Mod X's TrieClear removes that key with all the others, and a trie without it takes no
   key at all: TravTrieSetString and the other setters return false and TravTrieSize is 0, for good. The core clears a trie in
   these places: the client menu each time arp_menu builds it (CmdMenu: it stayed empty, "There are no items in the menu"), a player's
   HUD lines on every HUD pass (RenderHud, ClearSettings and the notice: no HUD line was ever kept, text or panel), his speed
   multipliers when he leaves (client_disconnect: the slot took no multiplier again) and his item list (array_clear in ClearSettings and
   when he joins and when his items arrive: items bought or found were lost, and saved items did not load). Only ARP_Core calls
   TravTrieClear, so only its code changes; the build tool builds again every plugin that includes the file. ARP_H9Menu (H9's own
   plugin, in no patch) ends its Menu_Display handler with an explicit return PLUGIN_CONTINUE (the core takes any non-zero return value of an
   event handler for a veto, and then does not show the menu it was given).

23. ARP_Core, ClassSaveHandle (H9-arpaudit.patch). It counts the answers of a class save down in the class's "/lastquery" and is done
   when the count is spent. The SQL module hands the answers that finished in one frame over last in, first out, and a save that
   waited for the answer to the last query number destroyed the class before the other answers came ("Invalid trie handle provided"
   in the error log, on a class save that changed two or more keys).

24. The OOC ping (base\sound\arp\ooc.wav, the sound ARP_TalkArea plays with the global /ooc box). Replaced by a synthesized
   one, a two-step digital chirp and a high ping that rings out (0.40 s, 22050 Hz mono, 16 bit, RMS 0.05; the old file was 8 bit with a
   peak of 0.12, very quiet, and is kept beside it as ooc.wav.original: it ships with the game, in sound\arp beside ooc.wav, and to go back
   to it a player copies it over ooc.wav). tools\ooc-ping-synth.py makes the new one and two alternates
   (B, a three-note terminal blip; C, a sonar ping): python tools\ooc-ping-synth.py <outdir> [rms]; A is the one installed. To change
   the sound: copy the one wanted over ooc.wav, here, in H9XASH\ts\sound\arp and in the game; a client keeps the file it has until
   it is replaced there. build.bat copies base\sound\arp\*.wav and *.wav.original into the game's sound\arp.

25. A map's SQL file runs by itself (ARP_Core; H9-arpjobs.patch; configs\arp\arp.cfg; the .sql headers of H9's two maps; docs\ARP_CONTENT.txt 2).
   configs\arp\maps\<map>\<map>.sql ran only when an ARP admin opened arp_config and chose Load Map SQL Data, and the core reads the jobs,
   properties and doors once, at map load, so a map's own jobs table stayed as the core had made it: h9_tsrp_hive had its one fallback job
   and h9_tsrp_newbyzantium no jobs table at all (the command that lists jobs is arp_joblist; arp_jobmenu is none of this set's).
   SqlInit now calls LoadMapSql between the CREATE TABLE statements and the three SELECTs, so the rows are read in the same map load.
   LoadMapSql reads the whole file against a rule first and runs nothing of a file that breaks it (H9_MapSqlRead, H9_MapSqlCheck): SQLite
   only; one statement to a line of at most 1000 characters, at most 4000 statements; each one  INSERT OR IGNORE INTO arp_jobs |
   arp_property | arp_doors VALUES (...);  with the default table name in lower case, once, and nothing after the ; (which may be left
   off), no other ; outside a text, no comment, no quoted name. The default name is swapped for the map's own table (H9_MapSqlBuild).
   The upstream maps' files are plain INSERTs and keep the arp_config way, which is unchanged (ARP_Config.sma has no edit; a file that
   passes the rule gives the same rows by hand). Each statement goes through UTIL_ARP_CleverQuery with its line number as data. Nobody
   is in the game at the map load, so each runs in line and its answer is in before the next; with players the module's one worker
   keeps the order, so the SELECTs see the rows. MapSqlAnswer only counts the answers, which come back last in, first out within a
   frame (item 23), and H9_MapSqlReport writes the one log line for the map once all are in: [ARP] map SQL: N statements, E errors,
   jobs now J, properties now P, doors now D. The reasons for not running, and each failed statement, have lines of their own.
   arp_mapsql_autoload (1; registered in the core's precache) is read from configs\arp\arp.cfg by the core as well (H9_MapSqlWanted):
   the server executes that file only after the core's precache, so on the first map of a server run a 0 there would be ignored.
   A start adds only the rows a table lacks and the rows already there keep their place, so a job's number does not change under a
   player; the Unemployed job FetchJobs makes when a table has none is made only when the file gave no such job.

26. The needs panel (include\ApolloRP_HUD.inc, ARP_HungerMod, ARP_Core; H9-arpneeds.patch; reTS\cl_dll\h9_arphud.cpp, client.dll.patch). Hunger was a
   line among the first HUD's (HUDK_EXTRA: "Hunger: 42%" and, from 90, "Starving: No Salary" then), and ARP had no thirst (item 27 adds one). The second HUD, which
   no plugin used (arp_hud2_x 1.0 and _y 0.0 are the top right), now holds the needs. The line kind HUDK_NEED (8) is a need: its text is
   "<label>: <0 to 100>%", and the stock ARP_AddNeedItem(id, label, value) adds one to the second HUD (ARP_AddHudItemKind with that kind,
   the value held to 0 to 100). ARP_Core's only change is the test in _ARP_AddHudItemKind, which turned a kind above HUDK_STATUS into
   HUDK_EXTRA and now does so above HUDK_NEED. ARP_HungerMod's HUD_Render handler answers for HUD_SEC instead of HUD_PRIM: Hunger, as a
   need, for a living player whose character has loaded (ARP_PlayerReady) while arp_hunger_enabled is 1, and from 90 the HUDK_STATUS
   line "Starving: No Salary" (item 27 shortens it to "Starving"); the words are the same, so a player with the text HUD reads the same two lines, now as the second HUD's
   text (the top right, in arp_hud2_r, _g and _b, flush right by the engine) instead of among the lines at the left. Nothing else of
   hunger changes: the rate, the effects at 75 and 90, the items, the stored value, arp_hunger_enabled, which the shipped arp.cfg sets to 1 as the plugin does.
   The wire is item 21's, with kind byte 8: a client older than this draws the line as text, and a server older than this sends hunger as
   an extra line of the first HUD, which this client draws as text. The client (client.dll.patch, h9_arphud.cpp) draws a need as a row of
   its panel, anywhere but the notice (the label, a bar that is green at 0 through yellow to red from 75 with a mark at 75 and at 90, and
   the number), headed "Needs" when a need opens the second or third HUD; a status line in those two HUDs is a red row; cl_h9_arphud_needs
   0 takes a second or third HUD that holds a need away whole, and the client hides it while the player is dead or spectating. A plugin
   with another need needs one line, ARP_AddNeedItem(id, "Label", value), from its HUD_Render handler. The same client change
   keeps the first panel under TS's weapon select bar (CHudTSWeaponBar::DrawnBottom); docs\APOLLO_RP.txt 2 says how. Where the line kinds
   are written down: this item and 21, include\ApolloRP_HUD.inc (the HUDK_* list and ARP_AddNeedItem), the first lines of h9_arphud.cpp,
   COMMANDS.txt (ITS HUD). H9-arpneeds.patch is the plugin and include changes against the files as they stood before it.

27. Thirst (ARP_HungerMod; H9-arpthirst.patch; configs\arp\arp.cfg). ARP had hunger only. ARP_HungerMod now keeps a second need, thirst, beside it,
   switched by arp_thirst_enabled (the plugin's default is 1, and the shipped arp.cfg sets 1, as it does for hunger): 0 to 100 for each player, up by one
   with a one in three chance every 15 seconds (about a point every 45 seconds; hunger's chance is one in six), kept in the plugin while the player
   is in the game and not stored (a player who joins starts at 0, and a death resets it as ARP_Core's death handler does hunger), and quenched only by a drink when it is finished: Soda by 35 and
   Milk by 30. They heal their hunger as before; a thirsty player may drink with no hunger to heal, where "you don't feel like drinking" refused
   it. Thirst is a meter and nothing more: no speed change, no message, no salary; from 90 the second HUD shows the status line "Dehydrated" (HUDK_STATUS)
   under the bars, and the hunger line is now "Starving" (it was "Starving: No Salary"; the rule, no salary while starving, is stock ARP's and stays). The two needs are
   two rows of the needs panel (ARP_AddNeedItem(id, "Thirst", value), item 26), Hunger first. Nothing in the core changed. H9-arpthirst.patch is the
   plugin and arp.cfg changes against the files as item 26 left them.

28. Dropped items name themselves (ARP_Core.sma, GetMsg and H9_AimedItem; H9-arpitemhover.patch, H9-arpitemworld.patch). An item dropped on the floor (classname arp_item, the
   backpack model; its name in the noise string, its number in iuser2) looked the same whatever it was, and its box (5 units) is too small for
   get_user_aiming, which finds the floor behind it. GetMsg now tries, when nothing else is aimed at (Index 0) and at most every 0.25 s for a
   player, the dropped items within 120 units that are in view (fm_is_ent_visible), takes the one nearest the middle of a cone of about 14 degrees
   from the eye (the dot product of the direction to it and the view, above 0.97), and prints "<name> x<number>" (just the name for one) to the

42. The property tax (new plugin ARP_PropertyTax.sma, H9's own, in no patch; ARP_Core.sma's two owner key natives, H9-arpowner.patch; configs\arp\arp.cfg; build.bat; docs\APOLLO_RP.txt, 11; docs\ARP_TAX_CHECKS.txt). Every arp_h9_tax_minutes minutes (15)
   each property that has an owner costs its owner arp_h9_tax_flat (0) plus arp_h9_tax_percent (1.0) per cent of what the property cost him, rounded up to a whole number (the percent and the flat sum

   forgotten: no debt, no eviction). The core changes in two natives only (below). An owner in the game whose character has loaded (ARP_PlayerReady) is charged in the core's memory (ARP_GetUserBank, ARP_SetUserBank) and told
   in one [ARP] line (the popups of item 40; the "$" of the line is the credit sign of item 33); one whose character has not loaded is left out of the toll; one who is away is charged in the database, in
   the users table of the map (ARP_GetTable): two statements for the module's one worker (ARP_CleverQuery), the first adding the toll to his row in the table arp_h9_tax (authid, taken, unpaid, tolls,
   props, updated; it reads the bank as it is, so what the bank holds is "taken" and the rest "unpaid"), the second taking it from his bank, never below 0, and only when that row is there, so a

   ARP_PropertyGetOwner fail for an H9XASH owner, so /sell, /lock, /changename, /addaccess, /delaccess, /profit and /changeowner refused him: they hold the whole key now, OwnerAuth[36] and

   and nobody is charged for the downtime. The two tables are made with CREATE TABLE IF NOT EXISTS when first needed (a query that waits, as arp_h9_cells is); no row of an ARP table is added, and going
