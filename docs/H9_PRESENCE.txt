===============================================================================
 H9 PRESENCE: WHO IS PLAYING, ON HAVOC9.ORG, AND THE PERKS THAT FOLLOW
===============================================================================

 Who this is for: whoever runs an H9 game server or the havoc9.org VPS, and
 anyone who wants to know what the site shows about them and why.

 The short version
   * A plugin on each H9 game server, h9_presence.sma, tells havoc9.org who is
     in game there. The site shows it: "PLAYING ON <server> / <map> (<mode>) /
     <n> MIN" with the map's picture, beside forum posts, on a player's card and
     in "who's playing".
   * Only players whose game uses their havoc9.org account's player id count
     (section 2). Everyone else's id is thrown away the moment it arrives.
   * An account that has been seen in game gets a PLAYS IN GAME badge, its
     playtime and a "last seen".
   * Six privacy switches on the ACCOUNT page decide what others see
     (section 6). The player always sees all of their own.
   * h9_clientid alone proves nothing: anyone on the same server can copy it.
     A challenge the game answers with the raw player id closes that (section
     8); until H9XASH answers it, game presence shows as "unverified" and
     counts for nothing.
   * This is not the Discord card. docs\RICH_PRESENCE.txt is the engine's own
     Discord Rich Presence; this is the website's. The two name the mode the
     same way, on purpose.
   * A server gets its key by itself: it enrolls with havoc9.org and proves
     its address (section 4a). Communities, chat across servers, bans and
     shared data build on that: docs\H9_COMMUNITIES.txt.

 1. HOW IT WORKS
 ---------------
 Every 60 seconds (a server nobody is on reports too: that is its heartbeat,
 and its chain, section 4d, needs it), and a few seconds after anyone joins,
 leaves or changes name, h9_presence.sma POSTs a report to h9web (the service
 behind havoc9.org) at /api/presence/report; a player's proof (section 8) is
 reported at once, 0.3 seconds after its answer and one report every 2
 seconds at most (h9_presence 1.8), so a proven player's chain, picture and
 level reach every scoreboard a second or two after the player is in game,
 at a map's start as well. A report holds:
   * the map, and the mode named the way the Discord card names it (Team
     Elimination, Siege, Capture the Uplink, Wave Survival, Mech Warrior,
     Assault, Capture the Flag, Roleplay, Match Mode, Deathmatch), with the mode's progress where
     there is one ("Siege - Insurgents attacking: 2 of 5 objectives", "Assault
     - points: Middle Sea Republic 2, Insurrectionists 1 of 5"). Its sides go by the
     names the game itself shows (h9_presence 1.7): entries 1 and 2 of
     mp_teamlist when it has them, "Middle Sea Republic" and "Insurrectionists"
     on H9XASH ("Capture the Uplink - zones: Middle Sea Republic 1,
     Insurrectionists 2 of 4", initials such as MSR where a line would run
     long), else ts_matchmode's tsm_team1_name and tsm_team2_name ("msr",
     "insurgents" on GoldSrc), else MSR and Insurgents;
   * for every human player with an h9_clientid: that id, the name, when they
     joined and how long they have been in game. Bots and HLTV are left out.
 Each report is signed with that server's own key (section 4a; HMAC-SHA256
 over the whole body) and carries a timestamp, which must be within 2
 minutes of h9web's clock and later than the last report h9web took from
 that server. A forged, changed, stale or replayed report is refused.

 h9web works out, for every account, what that account's h9_clientid is on
 that server (only h9web can: it holds the player ids). An id that belongs to
 no account is dropped there and then, with its name: it is never stored and
 never logged. What matches becomes a session: when it started, how long it
 has been counted, and on which server.

 A player missing from one report is "away", not gone: a map change looks like
 that. Back within 2 minutes, the same session goes on. A server that sends
 nothing for 3 minutes is taken to be down, and its sessions end at its last
 report. Playtime counts the time between two sightings, at most 150 seconds
 at a time, so an outage is never counted as play.

 Web client players need no plugin: the relay already knows which signed-in
 account each browser player is, and tells the presence module when that
 account starts and stops playing on a server (section 3, "core hooks").

 2. WHO COUNTS: THE PLAYER ID
 ----------------------------
 docs\CUSTOM_XASH_USERID.txt has the whole story. In short: H9XASH sends each
 server h9_clientid = MD5(cl_h9_userid + the server's IPv4 address). A
 havoc9.org account has a player id of the same shape. A player whose game
 uses the account's player id is that account to every H9 server:
   * in the browser, the web client uses it by itself;
   * in the downloaded game, Link your Account in the main menu (or .link in
     chat on an H9 server, h9_link.sma) shows a code; approved on
     havoc9.org/link, the game is handed the player id and keeps it protected
     (docs\CUSTOM_XASH_USERID.txt, section 2a). The older way still works:
     enter_userid.cmd in the H9XASH folder, with the player id from the
     ACCOUNT page (COPY on its PLAYER ID line), from the next launch.
 A player who keeps H9XASH's own random id is not an account and is never
 tracked. Nothing is stored about them.

 A completed link is also an event on h9web's core (h9web\README.txt, section
 13): account-link { id, link, device } and account-unlink { id, link, device,
 reason }, device being the game's device hash in this module's own form
 (section 9). The presence module does not act on them today: a linked game's
 device is bound or refused by its first proof, as any other.

 The id is salted with the address the game connected to, which must be the
 address the server enrolled with (with a hand-made key, the one servers.json
 lists): a player who joins over a LAN address, or a server reached at
 another address, sends an id that matches nobody. Two servers on one IP
 (different ports) see the same h9_clientid for a player; that is how the
 engine salts it.

 3. SETTING UP THE VPS (H9WEB)
 -----------------------------
 The presence module lives in h9web\modules\presence (its README.txt has the
 detail). On the VPS:

   1. The core hooks. The module needs a few things only h9web's core has
      (the player ids, servers.json, the relay's sockets, site activity).
      h9web's core gives them to every module (modules\presence\README.txt,
      "Core hooks"): nothing to do here.
   2. Load it: in /etc/h9web/config.json, "modules": [..., "presence"], then
      systemctl restart h9web. The tables are made on that start.
   3. Keys: none to make. Each dedicated server enrolls by itself (section
      4a). One on servers.json goes live as soon as it proves its address;
      any other waits until an H9 admin approves it on havoc9.org/community/
      (H9 ADMIN, ENROLLED SERVERS), unless enrollAutoApprove is on. Enrolled
      keys are worked out from a secret h9web makes on its first start,
      /var/lib/h9web/modules/presence/enroll-key (mode 0600), and a salt per
      server: the keys themselves are stored nowhere on the VPS. A new
      enroll-key turns every enrolled key off at once, and each server then
      enrolls again by itself.
      A key made by hand still works for a server on servers.json, and wins
      over its enrollment. As the service's user:
        sudo -u h9web node /opt/h9web/modules/presence/bin/presence-key.js \
          --config /etc/h9web/config.json add 203.0.113.10:27015
      It prints two lines for that server's h9_presence.cfg, once. The keys
      live in /var/lib/h9web/modules/presence/server-keys.json (mode 0600).
      rotate gives a server a new key, remove takes it away, list shows which
      servers have one (never the keys). No restart: the file is read again
      when it changes.
   4. servers.json: a server listed there with the address it enrolls with
      goes live without an approval and shows under the name servers.json
      gives it; an approved server that is not listed shows under its own
      hostname.
   5. nginx: nothing new. Reports, enrollment and the communities' calls go to
      /api/presence/..., which the existing location /api/ already passes on
      (client_max_body_size 128k: a full 32-player report is about 10 KB, and
      h9_presence's report is at most about 82 KiB, every one of 128 slots at
      its largest; h9web's own limit, the presence module's maxBodyBytes, is
      128 KiB. proxy_read_timeout 30s covers the communities' 20-second
      long-poll). Keep trustProxy on, so h9web sees each server's own
      address, and let the VPS send UDP to the game servers: enrollment reads
      their rules.
   6. The map pictures (optional). presence\maps\<map>.png are the Discord
      card's art. To show them on the site without a second copy in git, a
      deploy step copies them into the web root:
        install -d -m 755 /var/www/havoc9.org/assets/maps
        cp /opt/h9-src/presence/maps/*.png /var/www/havoc9.org/assets/maps/
      (not the *.bak_* files), and config.json gets
        "moduleSettings": { "presence": {
          "mapPicturesDir": "/var/www/havoc9.org/assets/maps" } }
      h9web then gives a picture URL only for a map that has one; a map with
      none shows as text, as the Discord card does. servers\index.html looks
      for assets/maps/<map>.jpg; change .jpg to .png there to share them.

 Settings (moduleSettings.presence; all have defaults):
   privacy               the switches' defaults (section 6)
   requireProof          false: an unproven game sighting shows as unverified
                         and counts for nothing; true: it is dropped
   inGameNames           true: answer a server that asks for names (section 10)
   siteActiveSeconds     300: how recent a signed-in request is "on the site"
   sessionTimeoutSeconds 180, rejoinSeconds 120, maxCreditSeconds 150,
   clockSkewSeconds 120, proofMaxAgeSeconds 600,
   sessionRetentionDays 90, netRetentionDays 30, flagRetentionDays 90,
   batchMax 50, cacheSeconds 15, mapPicturesDir, mapPicturesUrl
   defaultPicture        null: the scoreboard's picture for an account with
                         none is modules\presence\default-picture.png, the
                         site's default; or the absolute path of a PNG or GIF
   webClientSeconds      180: how long the web client's page counts as open
                         after it last said so (it says so every minute)
   enrollSameIp          true: a server enrolls only the address its request
                         comes from
   enrollAutoApprove     false: a proven server not on servers.json waits for
                         an admin; true: it goes live at once
   enrollStaleDays 30, enrollPendingMinutes 60, enrollProbeSeconds 10,
   enrollProbeTimeoutMs 2500
   limits                reportPerIp, reportPerServer, readPerIp,
                         settingsPerAccount, adminPerAccount, enrollPerIp,
                         enrollPerAddress, gamePicturePerAccount (20 an
                         hour), webClientPerAccount (10 a minute)
 The communities' settings and limits: docs\H9_COMMUNITIES.txt, section 11.

 4. SETTING UP A GAME SERVER
 ---------------------------
   1. The AmxxEasyHttp module and its CA bundle, as for ts_advertise:
        ts\addons\amxmodx\modules\easy_http_amxx.dll
        ts\addons\amxmodx\data\amxx_easy_http_cacert.pem
      build.bat installs both from compts\ when they are missing. On a Linux
      server they are ts/addons/amxmodx/modules/easy_http_amxx_i386.so and the
      same CA bundle in ts/addons/amxmodx/data/; linux\build-linux.sh assemble
      installs both (AmxxEasyHttp 1.4.0, the same version as the Windows
      module; linux\LICENSE-AMXXEASYHTTP.txt).
   2. h9_presence.amxx in plugins and in plugins.ini. build.bat builds,
      deploys and registers it with the other plugins.
   3. Nothing more for a dedicated server: the plugin enrolls it by itself
      (section 4a) and keeps the key in addons\amxmodx\data\h9_presence.key.
      h9web has to reach the server over UDP at the address players use (it
      can, if players can join it).
      ts\addons\amxmodx\configs\h9_presence.cfg (build.bat makes it from
      h9_presence.cfg.example once, and never touches it again) is only for
      changing a setting, or for a key made by hand:
        h9_presence_server  "<this server's address, as servers.json lists it>"
        h9_presence_key     "<the key presence-key.js printed>"
      Never commit either file: the .gitignore files leave them out,
      export.bat never copies them, xash.bat gives H9XASH the empty template
      and never the live server's h9_presence.key, and the client package
      leaves *.key out.
   4. The server's clock must be right (NTP): a report more than 2 minutes off
      h9web's clock is refused.
   5. Restart the server, or change map. In the server console,
      h9_presence_status says whether it reports, whether its self-test
      passed, its enrollment and public server id, and the last answer from
      h9web.

 The other cvars (h9_presence.cfg):
   h9_presence_url        default https://havoc9.org/api/presence/report
   h9_presence_interval   seconds between reports, 30 to 600 (default 60)
   h9_presence_challenge  1: the id proof (section 8); the default. With 0 no
                          one is proven and an announced id can be copied
   h9_presence_names      1: names in game (section 10). Needs the challenge
   h9_presence_autoenroll 1: a dedicated server enrolls by itself (default);
                          0: a hand-made key only
   h9_presence_enroll     the enrollment code, set and cleared by the plugin
                          (in the server's rules while h9web looks for it)
   h9_preset              the game-mode preset this server runs (section 4d), set
                          by configs\h9_preset.cfg (H9XASH's h9_presets puts it
                          there); empty names none

 The plugin logs to the AMXX log only when something changes: "h9web accepts
 this server's reports", or why not ("HTTP 401 bad_signature", "Could not
 reach h9web"), and once when the server is enrolled ("Enrolled with
 havoc9.org as server <id>"). Waiting for a proof or an approval, it logs
 nothing. It never logs the key, a player's id, name or address.

 Reading the mode: the plugin reads ts_matchmode's tsm_pres_mode,
 tsm_pres_siege, tsm_pres_attack and tsm_pres_prog cvars, the same ones the
 Discord card reads from the serverinfo, and the map's name; without
 ts_matchmode it names the mode by the map alone.

 4a. ENROLLMENT: A SERVER'S KEY, BY ITSELF
 -----------------------------------------
 A dedicated server with h9_presence_autoenroll 1 (the default) gets its own
 key without anyone typing one; a listen server (a player's own game) never
 enrolls. The steps, all of them quiet:
   1. The plugin POSTs { "v": 1, "port": <hostport> } to
      /api/presence/enroll. h9web takes the address from the request itself
      (the caller's IP, through nginx) and that port: a server enrolls only
      its own address (enrollSameIp). The answer holds a key, a one-time
      code and the server's public id. The key does nothing yet.
   2. The plugin puts the code in the cvar h9_presence_enroll, which is
      FCVAR_SERVER (in the server's rules, as server browsers read them) and
      FCVAR_UNLOGGED (no "changed to" line for anyone).
   3. The plugin asks /api/presence/enroll/status, signed with the new key.
      h9web reads the server's rules over UDP (A2S_RULES, with the challenge
      FWGS and HLDS ask for) at that exact address, at most every 10 seconds.
      The code there proves that whoever holds the key runs the server at
      that address.
   4. The key goes live: at once for a server on servers.json (or with
      enrollAutoApprove), otherwise once an H9 admin approves it on
      havoc9.org/community/ (H9 ADMIN). The plugin clears the cvar, keeps
      the key, the address, the server id and the state in
      addons\amxmodx\data\h9_presence.key, and starts reporting.
 A server h9web cannot reach (behind NAT, a LAN game) never proves its code.
 It stays unenrolled and asks again less and less often, from 10 seconds to
 every 6 hours, without a word. An unproven enrollment is forgotten after an
 hour (enrollPendingMinutes).

 Enrolling again: an address that already has a live key gets a new one that
 replaces the old only once proven, and an approved address stays approved.
 h9web flags it (re-enrolled) for the admins and writes it to the audit log.
 A server whose key file is gone, or whose key stops working (revoked, or a
 new enroll-key on the VPS), enrolls again by itself after three refused
 reports.

 Housekeeping: a live key with no report for 30 days (enrollStaleDays)
 expires; the server enrolls again when it is back. H9's admins approve,
 revoke (the key stops; the server may enroll again, and waits for approval
 again) or block (it may not enroll at all) on havoc9.org/community/ or
 through /api/presence/admin/servers (docs\H9_COMMUNITIES.txt, section 12).

 The public server id: ten characters of a to z and 2 to 9, given at the
 first enrollment and kept for the address. It names the server on the
 communities' pages and in portals, and is no secret; like the key it is kept
 on the server only in h9_presence.key, never in a shipped file.

 The key file, addons\amxmodx\data\h9_presence.key, is the server's secret:
 whoever has it can report players onto that server. The client package
 (stage-h9xash.ps1) and git leave *.key out; export.bat and xash.bat never
 copy it. Delete it to make the server enroll again.

 4b. WHAT THE ANSWER TO A REPORT SAYS
 ------------------------------------
 h9web answers every report it takes with
   { "ok": true, "players": <n>, "serverId": "<id>",
     "actions": { "<slot>": { "kick": "<reason>" } or { "mute": true } } }
 and "names" when the report asked for them (section 10).
   kick   a ban of the account in the server's community or H9-wide, or a
          one-off kick (docs\H9_COMMUNITIES.txt, section 5). The plugin runs
          kick #<userid> "<reason>", the reason cut to letters, digits,
          spaces and . , : ! ? ( ) -
   mute   the plugin drops the player's say and say_team (and so
          h9_community's .relay) until an answer no longer says so
   proven   [slot, ...]: the slots that proved a havoc9.org account (section 4c)
   avatars  { "<slot>": { "a": account, "v": version } } for each proven player.
          The plugin sends it to every client in the H9Avatar message; H9XASH
          (engine-h9-avatars.patch) fetches
          https://havoc9.org/api/presence/avatar/<a>/<v>.png, a 64 x 64 PNG, for
          the scoreboard (docs\PLAYER_LIMIT_128.txt 11.7), and keeps it. A
          picture it could not fetch (no answer, a timeout, 429 or a 5xx, as
          while h9web restarts) is asked for again while the slot names it: 15 s,
          60 s and 5 minutes after the first three tries, then every 10 minutes;
          one that is not there or no use waits 10 minutes. Each map starts the
          plugin's table afresh, so the map's first answer names every slot's
          picture again, and a game asks again at once for one it could not
          fetch.
   accounts { "<slot>": account } for the same slots as "avatars" (the green
          chain): each one's own account number, a player on the site's default
          picture included. The plugin (1.7) sends it to every client in the
          H9Account message (byte slot, long account; 0 none), a joining client
          the whole table; H9XASH keeps it for h9_profile, the scoreboard's
          double-click on a linked player's picture.
   usernames { "<slot>": "<username>" } for the same slots: each account's
          current username on havoc9.org (h9_presence 1.9, h9p_account_name)
   roles  { "<slot>": "<words>" } for those of the same slots that have any,
          comma-separated: "h9_admin" or "h9_moderator" (the account's role on
          the site), then its words in this server's community: "owner",
          "staff" (the owner and the admins the owner names) and "member"
          (h9_presence 1.9, h9p_roles)
 The scoreboard's picture, slot by slot:
   * An account with a picture gets their picture: the middle square of their
     forum profile picture at 64 x 64. h9web makes it from a PNG or a GIF (its
     first frame); a JPEG or WebP picture is decoded by its owner's browser,
     which the ACCOUNT page has make the 64 x 64 PNG and send it (POST
     /api/presence/avatar, checked as a PNG of exactly 64 x 64 and kept with
     that picture's version), right after the upload, or the next time the
     owner opens the ACCOUNT page for a picture uploaded before.
   * An account with no picture gets the site's default picture, the one the
     forum and the site show for it (havoc9.org\assets\avatar-default.png;
     the module keeps a copy, modules\presence\default-picture.png, which a
     test holds to the site's). It goes under one address for everybody,
     account 2147483647 and a version that changes only when the picture does,
     so every game fetches it once. So does a JPEG or WebP picture until its
     copy has come.
   * The silhouette is for players with no havoc9.org account, and for
     players who cannot be proven: a game that did not prove the player id
     (section 8), and Steam clients.
 The link icon, slot by slot: a small, half-transparent icon over the lower
 right corner of each row's picture (the whole picture in the shortest rows,
 8 to 12 pixels), drawn by H9's client.dll (reTS):
   * a green chain: a proven havoc9.org account on this server -- the same
     players the answer's "avatars" names, their own picture or the default;
     h9_presence tells every client in the H9Link user message (byte slot,
     byte 1 linked, 0 not, 2 a bot), a joining client the whole table;
   * a red broken chain: anyone else -- no account, a game that did not prove
     the player id, a Steam client; on a server without h9_presence, everyone;
   * H9's helmet in grey: a bot, never a chain. h9_presence says which slots
     are bots (H9Link 2, from is_user_bot: RCBot's bots carry no *bot key on
     Xash); on a server without it, *bot 1 in the userinfo still counts.
 A double-click on a picture with a green chain (a first click brings up the
 pointer) opens that player's havoc9.org profile in the web browser, your own
 row's yours. H9XASH's h9_profile <slot> (engine-h9-avatars.patch) opens
 <site>/api/link/profile/<account>: the site is the game's own (havoc9.org, or
 cl_h9_site's test site), the account the number the server named for that
 player in H9Account (h9_presence 1.7), or else for the picture in H9Avatar, so a
 server gives a number and nothing else. h9web sends the browser on to the
 account's forum profile, whose card shows only what the account's switches let
 others see (section 6). On a server whose h9_presence is older than 1.7, a
 player with the site's default picture comes as account 2147483647,
 everybody's, so no profile opens for them there. A single click on such a
 picture mutes nobody; the rest of the row mutes as before. On an engine without
 h9_profile (Steam's) the picture mutes like any other cell.
 A game whose link ends while it plays (h9_unlink in it, or REVOKE on the
 ACCOUNT page, which the game hears within 5 minutes, as in a game it asks its
 link's site again a few seconds into each map and every 5 minutes, and answers
 with a new id) loses its chain at once on h9_presence 1.7: its h9_clientid, _h9idv or _h9lnk changes, the
 plugin drops its proof and tells every client (H9Link 0, the silhouette, no
 account, no level), challenges the game again and reports soon; h9web counts
 no proof from that game's device made before the link ended, so its next
 answer leaves the slot unlinked, and the new id is no account's.
 Steam (GoldSrc) players with H9's client.dll see the same icons: green for
 the proven H9XASH players, red for the rest. A GoldSrc game cannot prove its
 own id, so its own row is always red. cl_h9_linkicons 0 in a client leaves
 the icons out. The icons are ts\gfx\vgui\h9_link.tga, h9_unlink.tga and
 h9_bot.tga, 64 x 64 TGA with alpha, H9's own drawing and H9's helmet
 (havoc9.org\h9helmet.png) in grey (tools\make_link_icons.py makes them; the
 main menu may use the same files); a client without them draws no icon.
 For h9_community.amxx and other plugins, h9_presence also offers natives
 (include\h9_community.inc): h9p_ready, h9p_server, h9p_server_id, h9p_api,
 h9p_sign (the live key's signature of a body; the key never leaves the
 plugin), h9p_nonce, h9p_report_soon, h9p_muted and h9p_challenge, and the
 h9p_proof forward.
 And from 1.9, the players' accounts (include\h9_presence.inc), for a plugin
 that gives rights by account (an admin plugin, a members' area):
   h9p_account(id)                  the slot's proven havoc9.org account, its
                                    number on the site (accounts.id), 0 for none
   h9p_account_name(id, out, len)   that account's current username
   h9p_roles(id, out, len)          its roles as "roles" above, comma-separated
   h9p_has_role(id, role)           a stock: whether h9p_roles holds the word
   forward h9p_account_changed(id, account)
                                    any of the three changed for the slot: the
                                    answer that proves it, a rename or another
                                    role on the site, an id that changes in
                                    game (account 0), the player leaving
                                    (account 0)
 Only the players with the green chain have an account: a game that proved its
 player id (section 8), a second or two after it is in game, and again after
 each map change, which starts with nothing known. With neither
 h9_presence_challenge 1 nor h9_require_account 1, nobody has one.

 4c. ACCOUNTS-ONLY SERVERS (H9_REQUIRE_ACCOUNT)
 ---------------------------------------------
 h9_require_account 1 in a server's h9_presence.cfg (h9_presence 1.5) lets in
 only games that prove a havoc9.org account:
   * every game is challenged (section 8), whatever h9_presence_challenge says;
   * a game that cannot prove an account -- no _h9idv 1 in its userinfo, or no
     h9_clientid: a Steam client, an H9XASH from before the proof, a game with
     no player id -- is kicked at once;
   * any other gets h9_require_account_grace seconds (45; 10 to 300) and is
     kicked if h9web has not counted it as a proven account by then (the
     answer's "proven" slots, or its picture in "avatars").
 The kick reads "This server requires a havoc9.org account: link your game
 from the main menu". It fails open: while h9web has taken no report for two
 report intervals (it is down, or the server has no key), and while h9web has
 given a player no challenge, nobody is kicked for it, and the check comes
 again a grace period later. The listen server's own player and bots are never
 kicked for it. Switched on in the middle of a map, it reaches the players
 already in at the next report tick. h9_presence_status says "accounts only:
 on" or "off", and whether h9web is answering.
 The cvar is FCVAR_SERVER, so it is in the server's rules (A2S_RULES, for the
 site's lock icon), and an H9XASH server says auth 1 in its server-browser
 answer while it is 1 (engine-h9-serverinfo.patch), for the browser's account
 icon. A newly linked game (Link your Account) may prove its account at once:
 h9web allows its device beside the account's bound one when it is linked
 (core's account-link event), and takes it away when the link is revoked.

 4d. THE OFFICIAL PRESET: AUTHENTICATED SERVERS, AND THE BROWSER'S CHAIN
 ----------------------------------------------------------------------
 H9's server browser, in the game and on the site, draws a chain beside each
 server, the same two the scoreboard draws for a player (section 4b):
   a green chain         havoc9.org vouches for the server: it reports to h9web
                         with a live key and what it runs is H9's official
                         preset, or it is on a roleplay map, where that check
                         does not apply
   a red broken chain    it does not: the server runs something beside the
                         preset, listed nothing, opted out, or does not report
                         to havoc9.org at all
 Nothing is blocked, kicked or hidden for it. Anyone may modify H9 or run
 third-party plugins and edits; such a server simply is not authenticated
 ("unauthenticated (modified)" on the site, never anything harsher), and its
 matches are not ranked (h9web answers a match start 409 not_rated,
 docs\H9_COMPETITIVE.txt section 6). H9 keeps offering third-party support and
 tools: these docs, the include files and the build scripts.

 WHAT A SERVER SAYS IT RUNS
 From h9_presence 1.10 the report lists what the server runs, at each map
 start and every 20 minutes:  "plugins": [ { "k", "f", "v", "h" }, ... ]
   k "amxx"    every AMX Mod X plugin that loaded (not one that failed to):
               f its file name, v its version, h the SHA-256 of the file
   k "module"  every *_amxx.dll, *_amxx.so and *_amxx_i386.so in the modules
               folder
   k "meta"    every file that Metamod's plugins.ini names and that is there
 h9web keeps the last list a server gave. A list is the server's own word: it
 catches unofficial setups and mistakes, not a determined operator with a
 modified h9_presence.

 WHICH PRESET. From h9_presence 1.12 the report also names the game-mode preset the
 server runs, when it has been told:  "preset": "Siege"  (a word of letters,
 digits, _ and -, 24 at most). The server is told by the file
 H9XASH\presets\h9_preset.<Tag>.cfg, which h9_presets.bat copies to
 configs\h9_preset.cfg with the preset's other files (plugins.<Tag>.ini,
 ts_matchmode.<Tag>.cfg ...) when a profile is applied; it holds one line,
 h9_preset "<Tag>", and h9_presence runs it after h9_presence.cfg at each map start.
 A server that names none, as every older h9_presence and every server that was not
 set up by h9_presets, is judged against every game mode's list together (below).
 The name is the server's own word, like the list: it can only narrow the check.

 A NEW PLUGIN IN THE PRESET. A build that adds a plugin to presets\plugins.<tag>.ini
 (ts_assault.amxx and ts_ctf.amxx, 2026-11-05, are the latest) makes a server that runs it read as
 modified until the allowlist has that file's hash: re-seed it from the build (the
 command below, mode "add"). Servers that have not updated run without the plugin and
 stay authenticated. The same holds for a rebuilt ts_matchmode.amxx or h9_presence.amxx.

 PER GAME MODE. Beside official-preset.json (everything every mode ships) the folder holds one
 official-preset-<Mode>.json for each presets\plugins.<Mode>.ini (Assault, Siege, TeamElimination): what that one mode
 ships, that is the plugins its plugins.<Mode>.ini switches on, every module and every Metamod plugin. A server that
 runs a mode's official preset is checked against that mode's file, so a plugin that is on the allowlist but is not
 in that mode's list reads as modified, and a mode's list changes only when its own plugins.<Mode>.ini does (today
 the three lists are the same, so the three files are). The hyphen is deliberate: h9_presets.bat takes a name with
 three dot-parts for a preset to copy over a config. tools\preset-check.mjs writes and checks all of them; each
 per-mode file also says "gameMode": "<Mode>" (preset-check writes it from the next build on), which the site's
 import takes. The site keeps a list per game mode and judges a server by the one it names (THE ALLOWLIST, THE
 VERDICTS).

 EVERY UPDATE. The file an admin imports is committed beside the preset lists:
 H9XASH\presets\official-preset.json (what preset-seed.js writes, with the
 build's note). build.bat rewrites it at every build, from the plugins, modules
 and Metamod plugins it has just put into H9XASH and before export.bat carries
 it to the git copy, and prints what changed; tools\preset-check.mjs compares it
 with the files (--write rewrites it); and the GitHub workflow
 .github\workflows\preset-hash.yml runs that comparison for every push and pull
 request that touches the plugins, the modules or the preset lists, so a binary
 cannot reach the repository without its hash. What stays by hand is the
 import: once a release is published, an admin sends the files to the site
 (below), each per-mode file as the list of the game mode it names, mode "add" to
 keep the older builds' hashes official or "replace" to drop them. The build a
 plugin belongs to is the version it registers (the
 "v" of the report; ts_matchmode's is its BUILD line, 1.59). With no h9web running yet
 (no site deployed) there is nothing to import into: the files only stay committed and in
 step with the build (tools\preset-check.mjs checks that), and the import is a step of
 putting a site up, or of a local test copy.

 THE ALLOWLIST (an H9 site admin's)
 presence_preset (migrations 12 and 15): the kind, the file's name, the SHA-256 of
 its bytes and the game mode whose list it is on, one row per file an
 authenticated server may run on that list. It is made from a build's own files:
   node modules/presence/bin/preset-seed.js --h9xash <the build's H9XASH folder>
        --out preset.json [--presets Siege]  (the plugins its presets\plugins.<tag>.ini
                                           switch on, its modules, its Metamod plugins;
                                           with one tag the file says "gameMode": that tag)
 and imported with POST /api/presence/admin/preset/import, signed in as an
 admin, the file as the body ({ "mode": "add" | "replace", "gameMode": "<tag>" | "*",
 "entries": [...] }), or straight into the database, as the service's user with the
 service's config (h9web-admin.js's way), the same tool with --import:
   node modules/presence/bin/preset-seed.js --h9xash <the build's H9XASH folder>
        --import --config /etc/h9web/config.json [--mode replace] [--live] [--game-mode <tag>|*]
 (--live adds the plugins.ini the build's server runs now; the audit log says
 "(command line)"; the site reads the table again every cacheSeconds, 15, so
 it needs no restart).
 GET /api/presence/admin/preset lists the entries (each with its gameMode) and, for
 each server that reports, its verdict, the preset it names, the list it was judged by
 and the files that are off it; POST .../remove { kind, file, sha256, gameMode? } takes
 one away, off the list gameMode names, or off every list without it. Both changes are
 in the audit log (presence.preset.import, presence.preset.remove).
   * "add", the default, keeps the hashes of older builds official, so a server
     that has not updated yet stays authenticated until an admin removes them;
     "replace" first drops every entry that is not optional from the list the
     import is for (the command line tool: from every list);
   * an entry with "optional": true (a community's own plugin, say) stays
     through a replace;
   * with no entry at all no preset is kept, and every server that reports
     counts as authenticated until one is imported.
 The lists. An entry is on the list of one game mode (a preset tag: Assault, Siege,
 TeamElimination; compared without regard to case) or on the shared list "*", which
 every mode accepts. The import's "gameMode" says which list it fills; left out, or
 "*", it fills the shared one. preset-seed.js --import fills each mode's list from its
 own plugins.<Mode>.ini (the plugins it switches on, every module, every Metamod
 plugin) and --live's plugins go on the shared list; --game-mode puts the whole build
 on one list (* gives it to every mode). Migration 15 put every entry that existed
 when it ran on the shared list, so no server's verdict changes by the update itself. The
 older, shared entries are accepted in every mode, so to judge by mode import each
 mode's list and then drop them: the command line tool with --mode replace does both
 at once; through the route, import each mode's file and take the shared entries off
 with POST .../remove (name gameMode "*": without one it takes an entry off every list).

 THE VERDICTS
   ok    reports, and everything it lists is on the allowlist
   rp    reports, on a roleplay map (rp_ or tsrp_ at the start of its name, _rp_
         or _tsrp_ in it): authenticated, and nothing there is ranked; the
         browser says "[UNRANKED: roleplay]" beside it
   mod   reports, but a file it lists is not on the list it is judged by (a file
         of its own, another build's: "not the official file (another hash)", or
         another game mode's: "not on the official list for Siege"), a file could
         not be read, or it has listed nothing yet
   opt   reports, and its operator set h9_authenticated 0 (below)
   off   does not report: not enrolled, or silent and not answering (below), or a
         private community's server or a listen server (never shown)
 ok and rp are the green chain; mod, opt and off the red one.

 WHICH LIST A SERVER IS JUDGED BY
   * a server whose report names a preset that has a list (Siege, say) is judged
     against that list and the shared one, and against nothing else;
   * a server that names none, or one that no list exists for, is judged against
     every list together;
   * the name only narrows the check: a mode's list is part of the whole, a roleplay
     map is still rp, h9_authenticated 0 is still opt, and a file that is on no list
     is mod whatever the server says it runs.

 A VERDICT IS HELD. A report earns the verdict, and the verdict stays while the server
 is there: a server that has been judged ok or rp does not turn red because reports
 are late. It stays what its last report made it
   * for 10 minutes after that report (authFreshSeconds; 25 minutes when the report
     said nobody was on the server, authQuietSeconds), and
   * beyond that for as long as the site's own status poll hears the server answer,
     for up to a day (authHoldSeconds, 86400): a map loading, a plugin that reports
     an empty server rarely, a request that failed and the time h9web itself was
     down (never counted against a server) change nothing.
 It changes when the server says something else: a list with a file off the allowlist
 makes it mod at that report, h9_authenticated 0 makes it opt, a revoked key or an
 admin's block ends it, and a server that is neither answering nor reporting is off.
 Rated play never looked at the clock: it asks only what the last list was.

 h9_authenticated 0 | 1   (h9_presence.cfg; default 1; FCVAR_SERVER)
 0 opts the server out on purpose: its report says "authenticated": false, so
 h9web lists it as not authenticated (the red chain, whatever it runs, a
 roleplay map included) and rates none of its matches; the next report with
 the cvar back at 1 undoes it. 1 asks for nothing: h9web judges what the server
 runs. A server cannot make itself more authenticated than that, so no setting
 here turns a red chain green. h9_presence_status says which it is.

 WHAT THE BROWSER READS
 GET /api/presence/servers/auth (public, cached like the other public reads):
 the line "H9SRV 1", then "<address> <code>" for each server that reports and
 is not private (code ok, rp, mod or opt; a server not named is off).
 H9XASH's engine (cl_h9auth.c, engine-h9-serverauth.patch) fetches it with the
 command h9_servers, which the browser runs when it opens and each time it
 refreshes (every 20 seconds, once in 20 at the most), over https with the
 certificate checked, and puts it in the cvars _h9srv and _h9srv_gen for the
 menu (mainui-h9-browser.patch). It asks the site and never the servers, because
 a server cannot say that it is authenticated. Before the first answer, on the
 LAN list, and in the web client, no chain is drawn. cl_h9_servers 0 turns the
 fetch off; cl_h9_site names a local test site (docs\CUSTOM_XASH_USERID.txt).
 The site's own server page draws the same chains from the auth field of
 /api/servers. A game that cannot reach the site simply shows none.

 5. WHAT THE SITE SHOWS: THE STATES
 ----------------------------------
 A player is in one state at a time, the highest that is true and that they
 show (section 6):

   1. IN GAME, from a game server's plugin or the web client's relay:
        PLAYING ON <server> / <map> (<mode>) / <n> MIN
      with the map's picture where the site has one. "UNVERIFIED" is added
      when the game did not prove the player id (section 8).
   2. IN THE WEB CLIENT: the web client's page is open, the game running or
      not, on no listed server: the page says so every minute (POST
      /api/presence/web; three minutes without, webClientSeconds, and it no
      longer counts), and the relay's socket for the account counts too.
   3. ON THE SITE: the account made a signed-in request to havoc9.org in the
      last 5 minutes (any page load counts: every page asks who is signed in).
   4. OFFLINE: "LAST SEEN <time> AGO", or nothing when the player hides it.

 The downloaded game in its own main menu reports to nobody (it only talks to
 a server once it joins one), so that reads as offline, or as on the site if
 the player is browsing too.

 Where it shows, through havoc9.org\assets\presence.js:
   * beside every forum post: a dot and the state, the badge, the playtime;
   * a player's card, which opens from any name marked for it;
   * "who's playing": each server with its map picture, "<map> (<mode>)" and
     its players; then players in game who hide the server, and who is in the
     web client or on the site;
   * "online now": one line with the counts and the names;
   * the player's own ACCOUNT page: everything about them, and the switches.

 5a. The badge and the numbers
   PLAYS IN GAME   the account has been seen in game, verified
   playtime        the counted time, in total and per server
   first seen      the first verified sighting
   last seen       the last time in any state the player shows

 6. THE PRIVACY SWITCHES
 -----------------------
 On the ACCOUNT page, each saved as soon as it is changed:

   SHOW THAT I'M IN GAME        others see state 1
   SHOW WHICH SERVER AND MAP    with it, the server, map, mode and picture;
                                without it, just IN GAME / <n> MIN
   SHOW WHEN I'M IN THE WEB CLIENT   state 2
   SHOW WHEN I'M ON THE SITE         state 3
   SHOW MY PLAYTIME             the playtime, first seen, the per-server
                                list, and the badge
   SHOW "LAST SEEN"             state 4's time

 All six are on for a new account (moduleSettings.presence.privacy sets the
 defaults; an account that never chose follows a changed default). A hidden
 state is skipped, never faked: with "in game" off a player in game shows the
 next lower state that is true, or offline. A hidden kind never shows through
 "last seen" either: a session still open counts from the one before it, and
 the site counts only when "on the site" is shown.

 Every read honours the switches before anything leaves h9web: the card
 (/api/presence/account/<name>), the batch read for a forum thread
 (/api/presence/accounts?u=...), and who's playing (/api/presence/now). The
 player always sees all of their own (/api/presence/me). Admins see more only
 where an admin action needs it: the flags list and the admin view of one
 account (section 9).

 7. PRIVACY: WHAT IS KEPT, FOR HOW LONG, AND WHO SEES IT
 -------------------------------------------------------
 Kept, only for accounts:
   sessions now        server, since when, the in-game name (owner and
                       admins only), counted seconds
   finished sessions   90 days (sessionRetentionDays), owner and admins only
   playtime            per server, first and last seen: while the account exists
   devices             a hash of each device id that proved the account's
                       player id (never the id itself); admins only
   networks            a keyed hash of the player's network cut to /24 (IPv4)
                       or /48 (IPv6), 30 days (netRetentionDays); admins see
                       only "known network" or "new network" on a flag
   flags               until resolved, then 90 days (flagRetentionDays)
   privacy switches    while the account exists
 Never kept, never logged:
   * any h9_clientid that is not an account's, with its name;
   * names sent only for the name check (section 10);
   * raw IP addresses: the plugin sends a coarse prefix only with a proof,
     and h9web hashes it at once with a key of its own (net-key in its data
     folder) and keeps nothing else;
   * player ids, keys, signatures, proofs, nonces, device ids.
 Deleting an account deletes all of its presence. A hand-made key never
 leaves h9web's data folder and the server's own config; an enrolled key is
 stored nowhere on the VPS (it is worked out again from enroll-key and a
 salt) and on the server only in h9_presence.key.

 8. THE ID PROOF: CHALLENGE AND RESPONSE (THE ENGINE'S SIDE)
 -----------------------------------------------------------
 Why: h9_clientid is the same for a player on a server every time, and every
 player on that server receives it in the player's userinfo. Anyone who reads
 it can send it as theirs. So h9_clientid says who a player claims to be; the
 proof shows they hold the raw player id it was made from.

 Status: built. h9web, the plugin (h9_presence 1.3) and the engine
 (engine-h9-idproof.patch, engine\client\cl_idproof.c) all have their part.
 Turn h9_presence_challenge 1 on once the H9XASH build with the patch is the
 one players have: until then an older game is never challenged (it has no
 _h9idv), its sightings stay unverified and count for nothing (no playtime,
 badge, last seen or session), and web client players (verified by the relay)
 are the only ones counted.

 The exchange
   1. The client says it can answer: userinfo key _h9idv "1" (a key starting
      with "_" is not sent to other players), set when cl_h9_userid is set
      and the device id is available.
   2. The plugin, at client_putinserver and again every 5 minutes, asks h9web
      for a nonce (POST /api/presence/server/nonce, signed with the server's
      key: 16 random bytes as 32 lowercase hex, kept with the server and the
      time) and sends it to the client as a server command:
        h9_idchallenge <nonce>
      A new one on every map, since the plugin starts over.
   3. The client answers with a client command, which only the server sees:
        h9_idproof <nonce> <devmask> <proof>
   4. The plugin takes an answer only to the nonce it gave that slot, once,
      and puts nonce, devmask and proof in that player's entry in every report
      until the next answer replaces it. h9web checks it with the account's
      player id. Every well-formed answer also goes to other plugins (the
      h9p_proof forward), and h9p_challenge sends a plugin's own nonce
      (include\h9_community.inc).

 The engine's side (engine-h9-idproof.patch, engine\client\cl_idproof.c)
   * A per-install device id: 16 random bytes from the OS (RtlGenRandom on
     Windows, from advapi32, which the engine already links; /dev/urandom
     elsewhere), made on first use and kept in H9XASH\device_id.ini ([device]
     then id=<32 hex>), apart from user_id.ini. A device_id.ini that holds no
     valid id is left alone and the game answers no challenge.
     enter_userid.cmd and h9_regenerate_userid.bat never touch it; it is never
     sent anywhere in the clear. Deleting it makes a new device (section 9).
     The .gitignore files and the client package (stage-h9xash.ps1) leave
     device_id.ini out.
   * _h9idv is a cvar of the engine's (FCVAR_USERINFO, FCVAR_PRIVILEGED), 1
     while the device id is there.
   * Register h9_idchallenge so that it runs when the server sends it with
     svc_stufftext, cl_filterstuffcmd 1 included. On it:
       - ignore it unless connected, cl_h9_userid is 32 hex and the nonce is
         32 lowercase hex; answer at most 4 a minute;
       - P = cl_h9_userid as text (32 ASCII bytes): the HMAC key below;
       - S = the address the client is connected to, "a.b.c.d:port" (the
         same address h9_clientid is salted with);
       - mask = the first 16 bytes of HMAC-SHA256(P, "h9dev1:" + nonce);
       - devmask = hex(device id XOR mask), 32 lowercase hex;
       - proof = hex(HMAC-SHA256(P, "h9proof1:" + nonce + ":" + S + ":" +
         devmask)), 64 lowercase hex;
       - send "h9_idproof <nonce> <devmask> <proof>" as a clc_stringcmd.
     FWGS has MD5 but no SHA-256: the patch adds one (FIPS 180-4).
   * The browser build does not set _h9idv and does not register the command:
     its presence comes from the relay, which knows the signed-in account.
   * An old client has no _h9idv and is never challenged; it stays
     unverified. A client that never answers is left out of reports for 8
     seconds, then reported unproven.

 Test vectors (h9web's tests check the same numbers):
   P (player id)  0123456789abcdef0123456789abcdef
   device id      fedcba9876543210fedcba9876543210
   nonce          6724a2c000112233445566778899aabb
   S              203.0.113.10:27015
   mask           c3795fccc8d837c61d1edf9a2827c855
   devmask        3da5e554be8c05d6e3c265025e73fa45
   proof          cc3fd059d636b90d80456c1692ac059047bd208076deffdf336a3a4bf1db6af4
   h9_clientid    6f25203910203f1f3c7e4f98e15fe7ae (MD5(P + 4 IP bytes))
   device hash    9dca7efc8a5cfe1677a2df1cf4731c6f (what h9web keeps:
                  SHA-256("h9device1:" + the 16 bytes), first 32 hex)

 h9web's checks: the proof matches the account's player id for that server's
 address; the nonce is one h9web issued to that server, no more than 10
 minutes ago (proofMaxAgeSeconds 600), so a server that saw a player once
 cannot go on reporting them as proven; the device is the account's (section
 9). A proof that does not match, or answers a nonce issued too long ago, is
 refused and flagged (bad_proof, stale_proof); the player then shows nothing
 at all. A proof for a nonce h9web never issued (an older plugin makes its
 own) is not refused and not flagged: the sighting is unverified.
 "Proven" therefore means proven in the last 10 minutes, and it is what the
 members-only servers' proof switch (docs\H9_COMMUNITIES.txt section 2a) and
 the scoreboard's pictures (section 4b) go by.

 A copied id. Every player on a server can read the others' h9_clientid, so an
 id that two slots announce is a copy on one of them. The plugin lists each
 slot of such an id whose game holds a proof with the id, and the others by
 slot alone (a members-only server's report lists them, and names on does too;
 otherwise they are left out). h9web keeps the one entry whose proof matches
 the account's player id: that is the account's, with its presence, chain and
 level as ever, and the others count for nothing, with no flag against the
 account. When no entry proves the id, or two do (one game open twice), none
 is kept: the server cannot say which is real, and a members-only server
 turns each of them away. h9_community.sma sends a ".relay" line only for a slot
 h9web has proven (h9p_account), so a copy cannot speak as the real player, nor as
 one who is not in game; a community whose owner switched CHAT NEEDS PROVEN PLAYERS
 off (docs\H9_COMMUNITIES.txt section 2) takes the announced id, except from
 a slot whose id another player announces too. h9_compete.amxx names only proven
 players to h9web, as the roster, the killer or the victim of a kill, so the id a
 player takes for the moment of a kill credits and blames nobody; h9_rank.amxx
 and /find name only a proven game as the asker.

 8a. CREATE GAME: A LISTEN SERVER, ITS OWN PLAYER AND ITS KEY
 ------------------------------------------------------------
 A game started with Create Game is a listen server: the player who starts it
 plays on it, and others may join. Presence works there for both, with H9XASH
 from 2026-11-02 on (engine-h9-listen.patch) and h9_presence 1.4.

 Its own player. That player joins over "loopback", which has no address, and
 both h9_clientid and the proof are tied to the address a player joins
 (section 2, section 8). So h9_presence tells that player's game the address
 it reports as:
   h9_idlisten <a.b.c.d:port>          sent as the player joins: the game salts
                                       its h9_clientid with that address, as a
                                       player joining from elsewhere has it,
                                       and tells the server (setinfo)
   h9_idlisten <a.b.c.d:port> <nonce>  in place of h9_idchallenge: the same,
                                       then the proof's answer with S = that
                                       address
 The game answers only over loopback, never in a demo, so no server elsewhere
 can choose the address a player's id is salted with or signed for. The
 userinfo key _h9idl is 1 in a game that has it; a listen server's own player
 without it is never challenged (its proof would sign "loopback").

 Its key. A listen server with no hand-made key enrolls once its own player is
 in game, and differently from a dedicated server:
   1. The plugin POSTs { "v": 1, "port": <hostport>, "listen": true } to
      /api/presence/enroll. h9web answers with an inactive key for the
      caller's own IP and that port, always the caller's own (whatever
      enrollSameIp says), and a nonce.
   2. The plugin sends its own player h9_idlisten <address> <nonce>, and the
      game answers.
   3. The plugin calls /api/presence/enroll/status, signed with the new key,
      with that answer: { "host": { id, nonce, devmask, proof } }. h9web checks
      that the nonce is the one it issued for this enrollment (used once, 10
      minutes at most), that h9_clientid is an account's on that address, that
      the account is not suspended, that the proof is that account's for that
      address, and that the device is one the account's id may be proven from
      (section 9). Then the key is live at once: no rules probe, no admin.
 Why that is safe: h9web counts only proven players on a listen server (as
 requireProof does everywhere), so such a server can show nobody who is not
 really there with a game holding that player's id; it cannot invent anyone.
 Its address is a player's own, so it is never shown: its players are "in
 game" with no server, map or address (as a private community's server, docs\
 H9_COMMUNITIES.txt section 3), it is left off the site's server board, and the
 admins see it (H9 ADMIN, ENROLLED SERVERS) as a listen server with the account
 that proved it. A listen server keeps its key in
 addons\amxmodx\data\h9_presence_listen.key, apart from a dedicated server's.
 Players joining from elsewhere need its address to reach it (a forwarded
 port); players on the same LAN joining by a LAN address are, as on any
 server, not recognised.

 How h9web knows the listen server's own player: the report names that
 player's slot ("host"), and the answer says "proven", "known" (the account,
 no proof yet) or "unknown" (no account has that h9_clientid here: the game's
 cl_h9_userid is not the account's player id). The plugin logs each change in
 the AMXX log ("[PRESENCE] havoc9.org does not know this game's own player
 ..."), and h9_presence_status shows it as "this game's own player". The
 player id is the one the site gives the account (GET /api/player, the web
 client's; the ACCOUNT page shows its start), never the account's uid.

 A hand-made key (h9_presence_server and h9_presence_key in h9_presence.cfg)
 still wins on a listen server, as on a dedicated one: the server reports as
 that address, its own player is told that address, and h9web treats it as
 any server with a hand-made key. The local test set-up uses one
 (D:\temp\LOCAL-PRESENCE-TEST.txt).

 9. DEVICES, TWO PLACES AT ONCE, AND THE ADMIN PANEL'S HOOKS
 -----------------------------------------------------------
 Devices. The first device whose proof checks out for an account is bound to
 it. A proof from any other device is refused: no presence, no playtime, no
 badge, no name in game, and a second_device flag for the admins, with
 whether it came from a network the account has used in the last 30 days (a
 second PC at home looks like that; a leaked id rarely does). An admin may
 allow the extra device, or unbind one.

 Two places at once. An account counted on one server is held anywhere else
 at the same time: not shown, not counted, and flagged (concurrent). When the
 first place ends, the held one takes over and counts from then. An
 unverified sighting beside a verified one is not shown either (it is most
 likely a copied h9_clientid) and is flagged the same way.

 The admin panel's hooks (h9web routes, admins only, every change written to
 the audit log; the admin panel's PRESENCE tab uses them, docs\H9WEB_ADMIN.txt
 section 16):
   GET  /api/presence/admin/flags?status=open|resolved|all&page=N
   POST /api/presence/admin/flags/<id>/resolve           { note }
   GET  /api/presence/admin/accounts/<name>   devices, flags, sessions, state
   POST /api/presence/admin/accounts/<name>/devices/<device>/allow    { note }
        an extra device for the account; its open second_device flag closes
   POST /api/presence/admin/accounts/<name>/devices/<device>/unbind   { note }
        with no device left, the next one to prove the id is bound
   POST /api/presence/admin/accounts/<name>/move-id   { to, confirm, password }
        the player id, and its presence history and devices, move to the
        account "to": the same install, unchanged, now counts as that account;
        <name> gets a new player id, and "to"'s old one stops working.
        confirm is <name>, typed
   POST /api/presence/admin/accounts/<name>/reset-id  { confirm, keepDevices,
                                                          password }
        a new player id, so a leaked one dies at once; every game linked to
        the account unlinks itself at its next start, and the owner links it
        again (or enters the new id with enter_userid.cmd). keepDevices
        (default true) keeps the bound device
 move-id and reset-id use core's movePlayerId and resetPlayerId
 (modules\presence\README.txt); without them they answer 503. Both need the
 acting admin's own password in the same request (password), checked as the
 admin panel checks its other confirmations; the panel asks for it.

 10. NAMES IN GAME
 -----------------
 With h9_presence_names 1 (which needs h9_presence_challenge 1, and h9web's
 core to check proofs), on every map but roleplay maps and stock TS maps:
   * a player whose account is verified (a proof, or the relay's signed-in
     session) plays under the account's havoc9.org username. The plugin sets it
     on join and on every map change, puts it back at once if the player
     changes it, and says why in one chat line ("[H9] On H9 maps you play
     under your havoc9.org name, Neo."). A rename on the site (an admin
     approves it; docs\H9WEB_ADMIN.txt) follows at the next report;
   * anyone else whose name is an account's username, or a name held after a
     rename, without regard to case or look-alikes ("Ne0" is "Neo", the same
     rule as sign-up), plays as "Player 1234" for the rest of the map, with
     "[H9] That name belongs to a havoc9.org account. On H9 maps you play as
     Player 1234." The space in it means no account can ever own it.
 Free maps: a roleplay map (rp_ or tsrp_ at the start, _rp_ or _tsrp_
 anywhere: roleplay_map() in ts_matchmode.sma, copied exactly into
 h9_presence.sma) and a stock ts_ map. Elsewhere names are fixed.
 How it travels: a report on a fixed map says "names": true and gives each
 player's slot; players without an h9_clientid go in as slot and name only.
 h9web answers per slot { "set": "<username>" } or { "taken": true }. Those
 names are checked and dropped; they are never stored or logged. Off by
 default; until the engine answers the challenge nobody is proven, so with it
 off every player keeps their own name.

 11. WHAT THIS PROTECTS AGAINST, AND WHAT IT DOES NOT
 ----------------------------------------------------
 What a game server can know of a player, plainly:
   * not a MAC address. It never reaches a game server, and a client can send
     any value it likes in its place. Binding to a MAC cannot be done.
   * the IP address, which changes: home connections are reassigned, phones
     move between networks, VPNs and the relay put many players behind one
     address. An IP is a soft signal for an admin to read, never a lock.
   * h9_clientid, which is client-asserted, the same on every visit, and
     received by every other player on that server. Whoever has a player's
     h9_clientid for a server can appear as them on that server. On its own
     it identifies honest players; it cannot stop a copy.

 Protected:
   * forged, changed or replayed reports: each is signed with that server's
     key and must be newer than the last;
   * a copied h9_clientid beside the real, proven player, once the challenge
     is on: without the raw player id no proof can be made, so the copy counts
     for nothing, earns nothing, gets no name, cannot take the real player's
     name or place (the real player is not dropped, nor kicked from a
     members-only server), and cannot speak as the player in community chat;
   * a proof captured on the way: it answers one nonce the plugin gave one
     slot, for one server's address; another slot, another server, or a day
     later it is refused;
   * a leaked or handed-over raw player id: the device binding refuses
     another install (and flags it); an admin resets the id and the leak dies;
   * one account in two places: only the first counts, and admins are told;
   * a registered name in game: protected on H9 maps by section 10;
   * players without an account: nothing about them is kept.

 Not protected:
   * a copied install, partly. user_id.ini and device_id.ini together are the
     account to H9's servers. On Windows user_id.ini is protected for its
     Windows user (DPAPI, docs\CUSTOM_XASH_USERID.txt section 2), so a copy of
     the folder taken to another PC or user is not the account there; malware
     running as that same user still is. Under Wine and Proton the protection
     is keyed to the user name alone. Keep the H9XASH folder to yourself, as
     you would a saved password, and REVOKE a game you no longer have on the
     ACCOUNT page.
   * a game server's key, or the server itself. A server holding a key can
     report anything about the players it really sees; it cannot make proofs,
     so with requireProof it cannot invent verified players. Revoke an
     enrolled key, or rotate a hand-made one, when a server changes hands.
   * a copied h9_clientid beside a player whose game cannot prove (an older
     H9XASH, or h9_presence_challenge 0): the server cannot say which is real,
     so neither is counted, and a members-only server turns both away. The
     copy of the id of a player who is not in game is that player's unproven
     sighting: it counts for nothing, and ".relay", /find, .rank, a rated kill and
     a community's shared data leave it out too, since each needs a proven game,
     unless the community's owner switched its proof off for chat or for data.
   * presence before the challenge ships: game sightings are unverified until
     then, shown as such, and never counted.
   * the downloaded game in its own menu: nothing reports it.
   * what other players see in game. h9_clientid stays readable by everyone
     on the server; moving it to a "_" key would hide it from other players,
     but would change what existing plugins read, so it is not done here.

 12. TROUBLESHOOTING
 -------------------
 Nothing shows for a player
   - Does their game use the account's player id (section 2)? The ACCOUNT
     page shows what each server sees as their h9_clientid.
   - Are they hiding it (section 6)? The ACCOUNT page shows their switches.
   - Before the challenge ships they show as unverified and earn nothing.
 h9_presence_status says "not reporting"
   - "enrollment: not enrolled": h9web cannot read the server's rules over
     UDP at the address it enrolls (a LAN or NAT server, a firewall in the
     way, or a server players reach through another address). It keeps
     asking, less and less often.
   - "waiting for an H9 admin": approve it on havoc9.org/community/.
   - On a listen server, "a listen server: enrolled by its own player's ID
     proof": it enrolls once its own player is in game, with H9XASH from
     2026-11-02 on (section 8a). "Not reporting: this listen server's own
     player's game does not answer h9_idlisten" in the AMXX log: an older game.
   - With a hand-made key, the AMXX log says why: an address that is not
     IPv4:port, or a key that is not 64 hex characters.
 h9web refused the report
   401 bad_signature   the key does not match: copy it again, or rotate it
   401 stale           the server's clock is off: fix NTP
   403 unknown_server  h9_presence_server is not on servers.json, or differs
   403 no_key          presence-key.js add was never run for that address
   403 not_enrolled    the address has no live key yet: it is enrolling
   403 pending_approval   proven, waiting for an H9 admin
 Enrolling a listen server (section 8a), the status call's answer
   403 not_an_account  the server's own player has no account (or is suspended)
   403 bad_proof       the proof is not that account's for that address
   403 stale_proof     a nonce of another enrollment, or older than 10 minutes
   403 second_device   a device the account's id may not be proven from
   409 replay          harmless once, after a map change in the same second
   429                 too many reports: the plugin backs off for a minute
   503 not_ready       h9web's core lacks the hooks (section 3)
 The self-test failed
   - The plugin's own SHA-256 disagrees with the test vectors. It reports
     nothing. Rebuild it with build.bat and tell whoever maintains it.
