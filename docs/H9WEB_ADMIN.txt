===============================================================================
 H9WEB ADMIN -- RUNNING HAVOC9.ORG'S ACCOUNTS, WEB CLIENT AND SERVER LIST
===============================================================================

 For the people who run havoc9.org: what the site does, what each role is,
 and the command for every admin job. How the service is built and set up
 is in h9web\README.txt; the web server, the certificate and the web
 client's build are in havoc9.org\webclient\DEPLOY.txt.

 Nothing in this file is secret, and nothing secret may be added to it: no
 passwords, nothing from secrets.json, no rcon passwords, no player's
 details. It is in the public repository.

 1. WHAT THE SITE DOES
 ---------------------
   * Pages: HOME, PLAY, DOWNLOADS, SERVERS, FORUM, JOIN, MUSEUM and CREDITS.
     Every page's nav has SIGN IN and CREATE ACCOUNT, or, once signed in, the
     username and ACCOUNT, and ADMIN for moderators and admins.
   * Accounts. Anyone can make one with a username and a password; there is
     no email. A sign-in lasts 30 days, or 14 days unused.
   * PLAY is the web client: H9XASH in the browser, from the main menu to
     the server browser to a game. It starts only for a signed-in account
     that is not suspended. Its game traffic goes through the relay on the
     VPS, and the relay talks only to the servers on the server list
     (section 6).
   * SERVERS lists the servers on the server list that answered recently,
     with their map, mode and players. h9web asks each one every 30
     seconds.
   * Each account has a player id. The web client hands it to the game as
     cl_h9_userid, so a server sees the same player the same way every time
     (its h9_clientid). The ACCOUNT page shows the first 8 characters of the
     id and what each listed server sees, and the whole id on SHOW (or COPY) in
     that PLAYER ID row,
     for a player who puts it into the downloaded H9XASH with
     enter_userid.cmd so both clients count as the same player
     (docs\CUSTOM_XASH_USERID.txt, section 2).
   * FORUM is the forum (section 11): categories, threads and posts, with
     profile pictures (section 13).
   * ACCOUNT has DISCORD: a player links their Discord account once and gets
     the registered role in H9's Discord (section 15).
   * Presence (section 16): who is in game on H9's servers, in the web
     client or on the site, shown beside forum posts, on a player's card,
     as "online now" on HOME and "who's playing" on SERVERS, with playtime
     and a PLAYS IN GAME badge. Each player chooses what others see.
   * ADMIN is the admin panel (section 12), for moderators and admins: the
     forum's reports and tools, suspensions, accounts, name changes (section
     14), presence (section 16) and the audit log. The admin command on the
     VPS (section 3) does the rest, and is the only way to make or unmake an
     admin.


 2. ROLES
 --------
   Every account has one of three roles:
     user        every new account: a player
     moderator   set by an admin, in the admin panel or with the admin command
     admin       set only with the admin command on the VPS
   PLAY and the server list treat all three the same. On the forum and in the
   admin panel (sections 11 and 12):
     moderator   the forum's tools (pin, lock, move, remove and restore threads
                 and posts; the report queue), posting off and on, removing a
                 profile picture, and suspending a player for up to 7 days
     admin       all of that, and the forum's categories, suspensions of any
                 length and lifting them, signing an account out, password
                 resets, deleting accounts, making players moderators and back,
                 name changes, and the audit log
   Nobody acts on an account of their own role or above: nobody suspends,
   deletes or demotes themselves, and moderators act on players only.

   The real admin power is the VPS: whoever can log in to it and run the
   admin command can do everything in section 4, whatever role their own
   account has. Keep that to the people who run the site.

   The first admin: sign up on the site like anyone else, then on the VPS
     $A set-role <your username> admin


 3. THE ADMIN COMMAND
 --------------------
   Log in to the VPS (ssh), then set this once per shell:

     A="sudo -u h9web /usr/bin/node /opt/h9web/bin/h9web-admin.js --config /etc/h9web/config.json"

   and run each command as  $A <command> ...  for example  $A list

   * It runs as the service's own user with the service's settings, so it
     works on the same database. Keep the "sudo -u h9web": run as root it
     can leave files in /var/lib/h9web that the service cannot write.
   * The service must have started once: it makes the database.
   * A change counts on the site at once. A web client player already in a
     game notices within 60 seconds: a suspension or a sign-out cuts them
     off then.
   * It never takes a password as an argument (the shell would keep it in
     its history). The passwords it makes are printed once and cannot be
     shown again.


 4. EVERY ACCOUNT COMMAND
 ------------------------
   $A list [--limit N] [--offset N]
       The accounts, oldest first, 100 at a time: id, username, role, when
       made, last sign-in, suspension. --offset 100 shows the next 100.

   $A show <username>
       One account: role, made, last sign-in, last password change,
       suspension, how many sessions are signed in now, and the first 8
       characters of its player id.

   $A create <username> [--role user|moderator|admin]
       A new account with a random password, printed once (four groups of
       five letters and digits). For a staff account, or a player who
       cannot use the form. The username rules of section 10 apply here
       too.

   $A reset-password <username>
       A new random password, printed once, and every session of the
       account ends. Send it to the player privately; they change it under
       ACCOUNT, CHANGE PASSWORD.

   $A set-role <username> <user|moderator|admin>

   $A ban <username> [--days N] [--reason "TEXT"]
       Suspends the account: it cannot sign in, every session ends, and a
       web client game it is in is cut off within 60 seconds. With --days N
       it ends by itself after N days; without, it lasts until unban. The
       player sees the end and the reason the next time they sign in with
       the right password ("This account is suspended until ... Reason:
       ..."), so write the reason for them to read.

   $A unban <username>
       Lifts a suspension at once.

   $A revoke-sessions <username>
       Signs the account out everywhere: every browser, and the web client.

   $A delete <username> --yes
       Deletes the account and its sessions for good; nothing brings it
       back. Its player id never comes back either, and its username can be
       taken again. Without --yes it refuses and says what it would delete.

   $A rename <username> <new name>
       Changes a username at once, with the sign-up checks; the old name is
       held for 30 days (section 14).

   $A backup <file>
       A copy of the whole database, safe to make while the site runs
       (section 8).

   Every command here that changes an account goes into the audit log, as
   "(command line)" (section 12).


 5. EVERYDAY JOBS
 ----------------
 A player forgot their password
   There is no email, so the site cannot tell who is asking: you do. Make
   sure the person asking owns the account (for example, the Discord account
   they are known by), then
     $A reset-password <username>
   send the password by direct message, never in a channel, and have them
   change it under ACCOUNT straight away.

 A player thinks someone else is in their account
     $A revoke-sessions <username>
     $A reset-password <username>
   and send the new password privately, as above.

 A player breaks the rules
   On the site and in the web client:
     $A ban <username> --days 7 --reason "Cheating. Appeal on Discord."
   or in the admin panel, ACCOUNTS (section 12). For the forum alone, turn
   their posting off instead (section 11).
   Every web client player reaches the game servers from the relay's one
   address, so never ban a web client player by IP on a game server: that
   bans every web client player at once. Ban the account here. A player on
   the downloaded client is banned on the game server as usual.

 Telling who a web client player is, on a game server
   Each account shows on a server as one h9_clientid, the same every time;
   the player can see theirs under ACCOUNT, WHAT THE SERVERS SEE. It tells
   honest players apart. It does not prove who someone is: a modified
   client can send any value (h9web\README.txt, section 4).

 A wave of junk accounts
   Sign-ups are limited to 5 an hour from one address. Delete the junk
   accounts (delete ... --yes). If it keeps up, lower
   limits.signupPerIp.max in config.json (section 7).

 A player asks for their account to be deleted
   The ACCOUNT page tells players to ask an admin on Discord. Make sure the
   owner is asking, then
     $A delete <username> --yes
   The service's logs keep its sign-ins for up to 30 days after that, as
   the privacy note on the ACCOUNT page says; then they are gone too.

 Adding, hiding or removing a game server
   Edit servers.json (section 6). The site, the relay and the web client's
   server browser follow within 2 seconds; nothing needs a restart.

 A game server that web client players will use
   Besides putting it in servers.json, set on that server
     sv_connect_max_per_ip 0
     sv_query_rate_limit 30
     sv_timeout 120
     sv_connect_timeout 600
     sv_connect_timeout_ban 0
   (H9XASH's server.cfg has the last two) and open its UDP port to the
   relay's address (havoc9.org\webclient\DEPLOY.txt, section 7).


 6. THE SERVER LIST (servers.json)
 ---------------------------------
   /etc/h9web/servers.json is the one list of H9's servers. The relay sends
   game traffic to these and to nothing else, the web client's server
   browser lists them, SERVERS shows them, and the ACCOUNT page shows what
   each one sees. Edit it with  sudo nano /etc/h9web/servers.json ; it is
   read again within 2 seconds of being saved.

     {
       "servers": [
         { "name": "HAVOC 9", "address": "203.0.113.10:27015" },
         { "name": "HAVOC 9 (on this VPS)", "address": "198.51.100.20:27015",
           "target": "127.0.0.1:27015" },
         { "name": "HAVOC 9 test", "address": "203.0.113.10:27016", "listed": false }
       ]
     }

   (Those addresses are documentation examples, not H9's.)

   name     the name shown on the site (default: the server's own)
   address  the server's public IPv4 address and port, numbers only: the
            browser game looks up no host names
   target   where the relay really sends, when that differs: 127.0.0.1:port
            for a game server on the VPS itself
   listed   false: joinable through the web client with "connect
            address" in its console, but not in the server browser or on
            SERVERS (a test server)
   gamedir  "ts" unless set
   notes    anything; not read

   A file with a mistake in it leaves the last good list working, and a bad
   entry is skipped; both are noted in the log (section 8).

   The JOIN shortcuts under PLAY are separate: settings.json in the site's
   webclient folder (DEPLOY.txt, section 4).


 7. SETTINGS (config.json)
 -------------------------
   /etc/h9web/config.json. A setting it leaves out keeps its default
   (h9web\lib\config.js, DEFAULTS). After a change:
     sudo systemctl restart h9web
   A restart keeps everyone signed in, but drops every web client player
   from the game they are in (they join again), so pick a quiet moment.

   The ones an admin may want:
     session.days, session.idleDays   how long a sign-in lasts: 30 days,
                                      14 unused
     password.minLength               10
     limits.loginPerIp                sign-in tries per address
     limits.loginPerUser              failed sign-ins per username
     limits.signupPerIp               sign-ups per address
     limits.passwordPerAccount        wrong current passwords per account
                                      Each is max tries in windowSeconds,
                                      then a block of blockSeconds that
                                      doubles up to maxBlockSeconds.
     relay.enabled                    false: the relay is off; PLAY starts,
                                      but the game reaches no server
     relay.maxSocketsPerAccount       4: web client connections one account
                                      may hold at once
     relay.maxSocketsTotal            512: web client connections for
                                      everyone at once
     status.pollSeconds               30: how often SERVERS is refreshed
     admin.modSuspendMaxDays          7: the longest suspension a moderator
                                      gives
     admin.auditRetentionDays         90: how long the audit log keeps a row
     admin.renameHoldDays             30: how long an old username is held
     admin.renameCooldownDays         30: the wait between name changes
     moduleSettings.forum             the forum's: guestRead, posting limits,
                                      picture sizes (h9web\README.txt, 15)
     moduleSettings.discord           Discord linking: clientId, guildId, the
                                      role, the reconcile (README.txt, 18)
     logLevel                         "info"

   Never on the VPS: insecureCookies (it strips the sign-in cookie's
   protection), devStatic, or a dataDir inside the site's folder (the
   service refuses that). allowedOrigins stays the site's own address,
   ["https://havoc9.org"].


 8. KEEPING IT RUNNING
 ---------------------
   Where things are
     /opt/h9web/                  the code
     /etc/h9web/config.json       the settings (section 7)
     /etc/h9web/servers.json      the server list (section 6)
     /var/lib/h9web/              secrets.json, data.key, h9web.db (the
                                  accounts, the forum, the audit log),
                                  backups/, modules/forum/avatars/
                                  (pictures); the h9web user's only, the
                                  folders 0700, the files 0600

   Is it up?
     systemctl status h9web
     curl -s https://havoc9.org/api/me          answers {"signedIn":false}

   Its log, live
     journalctl -u h9web -f
   One line per sign-up, sign-in, failed sign-in, sign-out, password change
   and web client connection, and per forum post, report, moderator step and
   admin panel action (never what a post says). Never a password, a cookie
   or a token.

   Restart
     sudo systemctl restart h9web               (section 7's warning)

   Backups
     The daily backup timer (havoc9.org\webclient\DEPLOY.txt, section 13)
     backs up the database, the forum's pictures and the presence keys into
     /var/lib/h9web/backups and keeps the newest 14. Only encrypted copies
     leave the VPS, never the whole of /var/lib/h9web. Backing up by hand,
     restoring, and moving the forum or the communities: section 18.

   The data key (data.key)
     Made on the first start, with the log line datakey.created. It seals
     what the database keeps that should not be readable from a copy of the
     database alone: each Discord link's Discord user id and display name.
     Keep one copy offline, apart from the database's backups; a backup and
     its key in one place is a backup anyone can open. Lost with no copy:
     only the Discord links are lost; the log says discord.datakey and
     Discord linking is off until "dropUnreadable" lets them go
     (h9web\README.txt, section 10), after which the players link again.

   Updates
     Copy the new code into /opt/h9web, then restart. A change to the
     database's layout is made at start, after a copy of the database goes
     into /var/lib/h9web/backups.

   The certificate
     It renews by itself; sudo certbot certificates shows when it runs out
     (DEPLOY.txt, section 8).

   Logs are kept 30 days at most, as the ACCOUNT page promises: journald's
   MaxRetentionSec=30day and nginx's logrotate (h9web\README.txt,
   section 10).


 9. RULES FOR ADMINS
 -------------------
   * /var/lib/h9web/secrets.json holds the key behind every player id and
     the pepper mixed into every password. Keep one copy offline (a password
     manager or an encrypted drive) and nowhere else: never in git, the
     site, Discord or a screenshot. If it is lost, every password and every
     player id is lost with it. If it leaks, tell the players: with it and
     a copy of the database, passwords can be guessed offline.
   * /var/lib/h9web/data.key: the same care as secrets.json, kept apart
     from the database's backups (section 8).
   * Backups of the database hold every username and password hash. Keep
     them as private as the VPS, and encrypted wherever they are copied to.
   * The VPS's disk: turn on the provider's disk or volume encryption where
     it offers it, so a disk that leaves the provider (a snapshot, a resold
     drive) holds nothing readable; it does not protect a running server.
   * Never ask a player for their password. No admin job needs it.
   * Send a reset password by direct message, never in a channel.
   * Run the admin command as written in section 3 (sudo -u h9web).
   * Ban web client players by account, never by IP on a game server.
   * Only the people who run the site get a login on the VPS.


 10. WHAT PLAYERS DO FOR THEMSELVES
 ----------------------------------
   * Make an account: a username of 3 to 20 letters, digits, dots, dashes
     and underscores, and a password of at least 10 characters. Usernames
     are unique without regard to case or look-alikes ("Ne0" cannot sit
     beside "neo"), and staff-looking names are refused for everyone, the
     admin command included: admin, moderator, staff, official and havoc9
     anywhere in the name, names that start with h9 or msr, and a few more
     (h9web\lib\usernames.js has the lists). The sign-up page tells players
     to use a password they use nowhere else.
   * Sign in and out, and SIGN OUT EVERYWHERE.
   * Change their password (ACCOUNT, CHANGE PASSWORD); their other sessions
     end.
   * See the first 8 characters of their player id and what each server
     sees of them; show or copy the whole id (SHOW and COPY in the PLAYER ID
     row) to put into
     the downloaded H9XASH with enter_userid.cmd, so the servers see both
     clients as the same player. Optional; they keep it to themselves.
   * PLAY.
   * Write on the forum (section 11) and add a profile picture (section 13).
   * Ask for a new username under ACCOUNT; an admin decides (section 14).
   * Choose what others see of their presence under ACCOUNT, WHAT OTHERS SEE:
     in game, which server and map, the web client, the site, playtime and
     "last seen", each on or off (section 16). They always see all of their
     own under IN GAME AND ONLINE. Their career level and ELO rating are not
     behind a switch: everyone sees them (section 19).
   * Make a community, join one, ask to join, accept an invitation, leave,
     and chat in the communities they belong to (section 17).
   They cannot get a forgotten password back or delete their account: an
   admin does those (sections 4, 5 and 12).


 11. THE FORUM, FOR MODERATORS
 -----------------------------
   The forum is at havoc9.org/forum/ (h9web\README.txt, section 15). Anyone reads it
   (unless guestRead is off); a signed-in, unsuspended account whose posting is on
   writes. Moderators and admins get a MODERATE bar on every thread and the forum
   tabs of the admin panel (section 12). Each step goes into the audit log.

   On a thread
     PIN / UNPIN          pinned threads stay at the top of their category
     HIDE / UNHIDE        a hidden thread is seen only by moderators and admins
                          (marked HIDDEN); for everyone else it is gone until
                          UNHIDE. Also on the thread's first post (HIDE THREAD) and
                          in the category list's row tools. Audit log:
                          forum.thread.hide, forum.thread.unhide
     LOCK / UNLOCK        locked: no new replies, except from moderators and admins;
                          the authors cannot edit or remove their posts in it
     RENAME               a new title
     MOVE                 to another category
     REMOVE THREAD        hidden from everyone but moderators and admins; RESTORE
                          THREAD on the same bar, or in the panel, brings it back
   In a category's list
     PIN / UNPIN, LOCK / UNLOCK on each thread's row, without opening it
   On a post
     EDIT                 any post, any time; readers see "edited by a moderator"
     REMOVE               leaves "Removed by a moderator." in its place; you still see
                          the text and a RESTORE button. Removing a post closes its
                          reports
     ACCOUNT TOOLS        opens the panel's ACCOUNTS tab for its author
     CLEAR SIGNATURE      in the author box: empties the author's signature, with your
                          reason in the audit log (forum.signature.clear)
     REMOVE PICTURE       under a picture: takes that one picture out of the post
                          (it reads "(picture removed by a moderator)"), with your
                          reason in the audit log (forum.post.picture.remove)
   Likes and dislikes: every signed-in member has one vote per post (not on their
   own post, not while suspended or with posting off). Everyone sees each post's
   likes and dislikes, and the author's likes in all beside their picture. A removed
   post keeps its votes hidden until it is restored.
   Removing is never final: a removed post or thread is kept and can be restored. A
   thread whose posts were all removed hides itself, and comes back when one of its
   posts is restored.

   Reports: REPORT under a post sends it to the panel's REPORTS tab, with the reason
   and a copy of the post as it was then (an author editing it afterwards does not
   change the copy). DISMISS closes a report (write what was done, if anything);
   REMOVE THE POST removes it and closes its reports. The reporter's name is shown to
   moderators only.

   Pictures in posts are links to pictures on other sites, shown from there: nothing
   is uploaded to havoc9.org. A picture shows only from the picture hosts on the list
   (i.imgur.com, i.redd.it, i.postimg.cc, i.ibb.co, media.giphy.com, i.giphy.com,
   upload.wikimedia.org, images.steamusercontent.com); any other link stays a link.
   A post shows up to 25 pictures, the rest as links. Both are settings:
     the number:  config.json "moduleSettings": { "forum": { "maxImagesPerPost": 40 } }
                  (0 to 200), then restart h9web
     the hosts:   IMAGE_HOSTS in h9web/modules/forum/markup.js AND img-src in the
                  Content-Security-Policy line of havoc9.org/forum/index.html and the
                  four forum/*/index.html pages; change both together (h9web's tests
                  fail while they differ), deploy both, restart h9web
   The site a picture is on sees the address of everyone who reads the post, as any
   website does; the forum's front page tells players so.

   Suggestions: a category for players' ideas (address suggestions), open to every
   member like General. The "What we need" page links to it.

   MEDIA (havoc9.org/media/): members post YouTube videos of their games; members
   comment, guests only watch. On each post, for moderators and admins:
     PIN / UNPIN          pinned posts stay at the top of the front page
     HIDE / UNHIDE        seen only by staff (marked HIDDEN), there and in the archive
     REMOVE               gone for everyone
   and REMOVE under any comment. Each goes into the audit log (forum.media.*). The
   front page shows the pinned posts and the newest 30 others; older ones move to
   the ARCHIVE by month. The number is a setting:
     "moduleSettings": { "forum": { "mediaFrontCount": 50 } }   (1 to 200)
   Videos show as pictures until someone presses play; then YouTube's privacy mode
   (youtube-nocookie.com) plays them.

   DEVELOPER: a flag an admin gives under ACCOUNTS, open the account, DEVELOPER (MAKE
   DEVELOPER, REMOVE DEVELOPER; audit log forum.developer.add and .remove). It goes
   with any role, shows the name in purple with a DEVELOPER tag across the forum, and
   lets the account edit the "What we need" page. It gives no moderation powers.

   Signatures: a member sets a few lines under ACCOUNT, FORUM SIGNATURE; they show
   under each of their posts (not under removed ones, never in quotes), with bold,
   italic, links and a picture from the picture hosts. A new account's shows as plain
   text. A reader can turn everyone's off there too (SHOW SIGNATURES). Moderators, on
   accounts below their role, from the member page:
     CLEAR SIGNATURE      empties it (also in a post's author box)
     BLOCK SIGNATURE      the account cannot set one, and its signature is hidden,
                          for some days or until LET SIGNATURE BACK; the player sees
                          your reason. In the audit log as forum.signature.block and
                          forum.signature.unblock
   The limits are settings (config.json, then restart h9web):
     "moduleSettings": { "forum": { "signatureMaxChars": 300, "signatureMaxLines": 4,
       "signatureImages": 1, "signatureImageHeight": 100 } }
   (characters 0 to 2000, 0 switching signatures off; lines 1 to 20; pictures 0 to
   10; picture height 16 to 480 px.)

   Posting off: for an account that keeps breaking the forum's rules but may still
   play. The panel's ACCOUNTS tab, POSTING ON THE FORUM: a username, an optional
   number of days, and a reason the player reads when they try to post. They still
   sign in, read, report and play. TURN POSTING BACK ON lifts it. Moderators do this
   to players only.

   What the forum keeps, and the rules, are on its front page. It stores no IP
   address with a post. An account's posts stay when the account is deleted, shown
   as from a deleted account; remove them one by one first if they must go.


 12. THE ADMIN PANEL
 -------------------
   havoc9.org/admin/, the ADMIN link in the nav of a moderator or an admin. The server
   checks every click again: the panel shows only what a role may do, and a link
   alone opens nothing. Nobody acts on an account of their own role or above, so
   nobody suspends, deletes or demotes themselves, moderators act on players, and
   admins on players and moderators.

   Moderators
     REPORTS      the forum's report queue (section 11)
     FORUM        removed threads, with RESTORE
     ACCOUNTS     PLAYERS: the players, newest first, with a search that filters
                  as you type (the start of a name, any case, look-alikes too) and
                  SUSPENDED or POSTING OFF badges; a click fills the name into the
                  forms below
                  SUSPEND AN ACCOUNT: a player, 1 to 7 days (config admin.
                  modSuspendMaxDays), with a reason the player sees when signing in
                  POSTING ON THE FORUM: section 11
                  REMOVE A PROFILE PICTURE (section 13)
                  RANK: an account's career level, experience and tables, and the
                  adjustments made to them, to look at (section 19)
   Admins, also
     FORUM        the categories: name, description, who starts threads, who
                  replies, visible or hidden (a hidden one is for staff only), order
                  (UP, DOWN), ADD A CATEGORY, DELETE (refused while it holds threads,
                  unless you pick where its threads move)
     ACCOUNTS     the list shows every account at once, newest first; sort it
                  (oldest, last sign-in, name), search as you type, show one role,
                  or the suspended, or those with posting off. Click one to open
                  its details, its
                  audit trail, and:
                    suspend for any time; empty DAYS means no end
                    LIFT THE SUSPENSION
                    SIGN OUT EVERYWHERE
                    RESET PASSWORD: a new random password, shown once in the panel;
                      send it privately, as in section 5
                    SET ROLE: player or moderator
                    DELETE THE ACCOUNT: type its username exactly
                    RANK: its career level and experience, each table's rating and
                      place, and every adjustment made; ADJUST THE RANK sets or moves
                      a table's rating or the career's experience (section 19)
     NAME CHANGES WAITING FOR A DECISION: APPROVE or DENY (section 14);
                  SHOW DECIDED lists those approved, denied or cancelled
     PRESENCE     the presence flags, and one account's presence: its devices,
                  RESET THE PLAYER ID and MOVE THE PLAYER ID (section 16)
     LEVELS       the career level's settings with the road to Lv 99 they give,
                  RANKED SERVERS (UNRANKED, with a void) and the COMPETITIVE SEASON
                  (reset, back to season 1) (section 19)
     WHAT WE NEED the "What we need" page (havoc9.org/join/needs/): its title,
                  intro and items (category, status, title, description; pictures
                  from the forum's picture hosts, as in posts), ADD ITEM, UP, DOWN,
                  REMOVE, a live preview, SAVE (into the audit log as
                  forum.needs.edit). Admins, moderators and developers by default;
                  the page itself has EDIT THIS PAGE for them. Who besides admins:
                  "moduleSettings": { "forum": { "needsEditors": ["moderator", "developer"] } }
                  ([] leaves it to admins)
     AUDIT LOG    every moderator and admin action, the latest first, all or by a
                  name; kept 90 days (config admin.auditRetentionDays)

   Your own password: a suspension with no end, RESET PASSWORD, SET ROLE, DELETE,
   APPROVE, RESET THE PLAYER ID, MOVE THE PLAYER ID and ADJUST THE RANK ask for it
   when pressed: a small prompt opens under the button, says why, and the password
   goes with that one action only; it is never kept.
   Five wrong ones in 15 minutes block those buttons for 15 minutes.

   Admins are made and unmade only with the admin command on the VPS
     $A set-role <username> admin        (or user / moderator)
   never in the panel, so a stolen admin session can neither make admins nor lock
   the real ones out. Everything the admin command changes is in the audit log too,
   as "(command line)".


 13. PROFILE PICTURES
 --------------------
   A player adds, replaces and removes their own under ACCOUNT, PROFILE PICTURE. It
   shows beside their forum posts and on their forum profile; without one, the forum
   shows the H9 default picture.
   * PNG, JPEG, WebP or GIF (a GIF or WebP may move), never SVG, never a link to a
     picture elsewhere. Up to 10 MB, 512 x 512, 300 frames (config, the forum's
     pictureMax* settings). The file's own bytes decide its type, not its name.
   * The details a picture file carries (camera, place, date, comments, editing
     history) are removed before it is kept; nothing is re-drawn. A photo that only
     looked upright because of its EXIF orientation shows sideways: the player saves
     it upright and uploads it again.
   * Kept on the VPS under /var/lib/h9web/modules/forum/avatars, never in the site,
     at most 1 GiB in all (pictureQuotaBytes); 10 uploads an hour per account.
   * A moderator removes a picture that breaks the rules: in the panel, ACCOUNTS,
     REMOVE A PROFILE PICTURE, or REMOVE PICTURE on the member's forum profile. The
     audit log records it, with the reason.
   * Beside posts, a picture over 512 KB (a long GIF, say) shows the default one
     until the reader hovers or taps it, so a page of posts stays light.
   * nginx needs the location of h9web\README.txt, section 15, for the upload.
   * On the in-game scoreboard (docs\H9_PRESENCE.txt section 4b) a proven player
     shows the middle square of their picture at 64 x 64; a player with none shows
     the H9 default picture; the silhouette is for players with no account and
     games that did not prove the player id. h9web makes the game's copy of a PNG
     or GIF itself; for a JPEG or WebP the owner's browser makes it on the ACCOUNT
     page and sends it. Removing a picture removes its game copy with it.


 14. USERNAME CHANGES
 --------------------
   A player asks under ACCOUNT, CHANGE USERNAME; an admin decides under NAME CHANGES
   in the panel.
   * The new name has to pass the sign-up rules (section 10) when asked for and again
     at APPROVE: no other account's name in any case, nothing that looks like one, no
     name still held. Two players may ask for the same name; the first one approved
     gets it, and the other approval fails.
   * APPROVE asks for your own password. The account keeps its sign-in, its sessions,
     its player id and its forum posts, under the new name.
   * The old name is held for 30 days (config admin.renameHoldDays): nobody else can
     take it, or a look-alike, to pass as that player. Its owner may take it back.
   * DENY with a reason the player sees under ACCOUNT.
   * One request waiting per player; after a change, the next request only after 30
     days (admin.renameCooldownDays).
   * On the VPS, at once, with the same checks and the hold:
       $A rename <username> <new name>
   * The audit log records the old and the new name.


 15. DISCORD AND THE REGISTERED ROLE
 -----------------------------------
   A player links their Discord account under ACCOUNT, DISCORD (SYNC YOUR DISCORD):
   Discord asks them to share their name, and the registered role in H9's Discord
   follows. A player who is not in H9's Discord yet gets the role once they join,
   within 15 minutes. One Discord account per HAVOC 9 account and the other way round;
   the player cannot unlink or replace it. A SYNC finishes only in the browser that
   started it (a short-lived cookie ties the two together), so nobody can start one and
   get another player to finish it on Discord to take that player's Discord account; a
   refused attempt links nothing, sends the player back to ACCOUNT to start again, and
   is in the audit log as discord.link.refused.

   Freeing a link (admins): when a player has lost their Discord account and needs to
   link a new one. Admin panel, ACCOUNTS, open the account, DISCORD, FREE THE LINK (a
   reason is optional). The registered role is taken from the old Discord account at
   once (or at the next reconcile, if Discord is busy), the link goes, and the player
   can SYNC again. The audit log records it.

   Automatic: a suspension takes the role away and lifting it gives it back; a deleted
   account loses it. Every 15 minutes the reconcile puts the role back where a link
   says it belongs and takes it where none does (a change made by hand in Discord is
   undone for linked players). People with the role and no link keep it unless
   removeUnlinked is switched on, so staff can still give it by hand. RECONCILE NOW in
   the panel runs it at once.

   Setting it up is in h9web\README.txt, section 18: the redirect address in the
   Discord Developer Portal, the bot's Manage Roles permission with its role ABOVE the
   registered role, and the secrets file (the client secret and the bot token) in
   /var/lib/h9web/modules/discord/secrets.json, mode 0600. Without that file Discord
   linking is off and everything else works.


 16. PRESENCE: WHO IS PLAYING, DEVICES AND THE PLAYER ID
 -------------------------------------------------------
   The site shows who is in game on H9's servers ("PLAYING ON <server> / <map>
   (<mode>) / <n> MIN"), in the web client, on the site, or when they were last
   seen, with their playtime and a PLAYS IN GAME badge: beside forum posts, on the
   card a click on a name opens, as "online now" on HOME and "who's playing" on
   SERVERS. Only accounts count: a player whose game uses the account's player id
   (the web client does by itself; H9XASH after enter_userid.cmd). Everyone else's
   id is thrown away on arrival. Each player picks what others see under ACCOUNT,
   WHAT OTHERS SEE. docs\H9_PRESENCE.txt is the whole story: the game server plugin,
   what is kept and for how long, what it does and does not protect against, and
   troubleshooting (its section 12).

   Turning it on (the VPS): "presence" in "modules" in /etc/h9web/config.json, then
     sudo systemctl restart h9web
   Its tables are made on that start. An update that brings presence migrations
   (14: community chat and shared data need proven players, 15: the official
   preset per game mode) applies them at the next restart, after a copy of the
   database in <dataDir>/backups; nothing else is needed.

   A key for each game server. A server reports who is on it, signed with a key of
   its own; h9web refuses a report without the right signature. A dedicated server
   gets its key by itself: it enrolls with havoc9.org and proves its address
   (docs\H9_PRESENCE.txt, section 4a); one not on servers.json waits for an admin
   to approve it (section 17). A key made by hand still works for a server on
   servers.json, and wins over its enrollment. As the service's user:
     P="sudo -u h9web node /opt/h9web/modules/presence/bin/presence-key.js"
     P="$P --config /etc/h9web/config.json"
     $P add 203.0.113.10:27015       a key for that server, printed once
     $P rotate 203.0.113.10:27015    a new key (a server that changed hands)
     $P remove 203.0.113.10:27015    the server reports no more
     $P list                         which servers have a key (never the keys)
   The address must be the server's as servers.json lists it (section 6). add and
   rotate print two lines for that server's
   ts\addons\amxmodx\configs\h9_presence.cfg; copy them there and nowhere else, and
   never into git or a chat. The keys live in
   /var/lib/h9web/modules/presence/server-keys.json (mode 0600) and are read again
   when the file changes: no restart.

   The admin panel's PRESENCE tab (admins only; every action is in the audit log):
     FLAGS        OPEN FLAGS, RESOLVED, ALL. Each says who, what, where, how often:
                    SECOND DEVICE       an install that is not the account's proved
                                        its player id and was refused. "From a
                                        network the account has used" usually means
                                        a second PC at home: ALLOW THIS DEVICE.
                                        From a new network, it may be a leaked id:
                                        ask the player, and RESET THE PLAYER ID if
                                        it leaked.
                    TWO PLACES AT ONCE  the account was counted on one server and
                                        seen on another at the same time; only the
                                        first counted. Two PCs, or a copied id.
                    BAD PROOF,          a game sent an id check that does not match,
                    STALE PROOF         or answers an old challenge: most likely a
                                        copied h9_clientid. It counted for nothing.
                  RESOLVE closes a flag, with a note for the audit log.
     AN ACCOUNT   type a name and OPEN (or OPEN <NAME> on a flag): where it is now,
                  its playtime, its devices and its flags.
                    UNBIND        a device stops counting as the account. With no
                                  device left, the next install to prove the id is
                                  bound to it.
                    RESET THE PLAYER ID
                                  a new player id for the account: the old one,
                                  and every h9_clientid made from it, stops working
                                  at once, so a leaked id is dead. Its open
                                  sessions end. Type the username, keep or drop the
                                  bound device, then your own password. The player
                                  copies the new id from the ACCOUNT page into
                                  enter_userid.cmd; the web client needs nothing.
                    MOVE THE PLAYER ID
                                  for a player whose game counted on the wrong
                                  account (a second account they made): the id,
                                  with its presence history and devices, goes to
                                  the account you name, so the same install
                                  counts as that account. The account you opened
                                  gets a new id. WARNING: the other account's own
                                  player id is thrown away for good; any game set
                                  up with it stops counting as anyone, and nothing
                                  brings it back. Type the opened account's
                                  username, the account that gets the id, then
                                  your own password.
   Audit log actions: presence.flag.resolve, presence.device.allow,
   presence.device.unbind, presence.id.reset, presence.id.move,
   presence.preset.import, presence.preset.remove.

   The official preset (admins only; docs\H9_PRESENCE.txt section 4d is the
   whole story): the files an authenticated server may run are kept as one list
   per game mode (Assault, Siege, TeamElimination, from H9XASH\presets\
   plugins.<Mode>.ini) and one list shared by every mode. After each release,
   import each mode's file, H9XASH\presets\official-preset-<Mode>.json, which
   names its "gameMode", with POST /api/presence/admin/preset/import (signed in
   as an admin; "mode": "add" keeps the older builds' hashes official, "replace"
   drops them from that list), or on the VPS as the service's user:
     node /opt/h9web/modules/presence/bin/preset-seed.js --h9xash <the release's
       H9XASH folder> --import --config /etc/h9web/config.json [--mode replace]
   which fills each mode's list at once. A server whose report names a preset
   (h9_preset, set by presets\h9_preset.<Mode>.cfg through h9_presets.bat) is
   judged against that mode's list and the shared one; a server that names none
   is judged against every list together. The shared entries every earlier import
   made keep every mode's verdict what it was until they are replaced (--mode
   replace, or POST .../preset/remove with "gameMode": "*"). GET
   /api/presence/admin/preset shows each entry's game mode, and for each reporting
   server the preset it names and the list it was judged by.

   What admins see, and do not: the in-game names and finished sessions of an
   account, its devices as hashes, and whether a flagged network was one it has
   used, never the network itself or an IP address. Nobody sees a player id or
   a device id.

 17. COMMUNITIES: ENROLLED SERVERS, MEMBERS, PRIVATE COMMUNITIES
 ---------------------------------------------------------------
   A community is an account's group of game servers with one chat across them
   and the site, members, and its own admins; havoc9.org/community/ is its page.
   docs\H9_COMMUNITIES.txt is the whole story. What is an H9 admin's (role admin):

   Enrolled servers (havoc9.org/community/, H9 ADMIN, ENROLLED SERVERS). Game
   servers enroll by themselves. One on servers.json goes live once it proves its
   address; any other shows as "pending approval" until APPROVE. REVOKE stops a
   key at once (the server may enroll again, and waits again); BLOCK stops an
   address from enrolling at all; UNBLOCK lifts that. "re-enrolled" flags a key
   that a new enrollment replaced; RESOLVE FLAGS once looked at. Approve only a
   server whose host you know: an approved server reports players and, linked to
   a community, reaches its chat and data.
   A "listen" server is a player's own game (Create Game), live without anyone's
   approval because its own player proved their H9 id for it; the list names that
   account. Its reports count proven players only and its address is never shown
   (docs\H9_PRESENCE.txt section 8a). REVOKE and BLOCK work on it as on any other.

   Every community, whatever its settings: an H9 admin sees a private community's
   page, servers, members and chat, and may do whatever its owner may (settings,
   members, requests and invitations, bans, mutes and kicks, announcements,
   deleting chat lines, putting its data back, deleting it). Membership does not
   apply to H9 admins: they read and write any community's chat without joining,
   and a members-only server always lets them in. Use that for moderation, not to
   read private chats out of interest.

   H9-wide (H9 ADMIN): BANS, MUTES AND KICKS on every enrolled server and in every
   community (a ban also keeps the account out of every community: it cannot join,
   ask or be invited), and ANNOUNCE to every server and every community's chat.

   The Discord bridge, an H9 admin's alone: on a community's own page, DISCORD
   BRIDGE (H9 ADMIN) takes a Discord channel's id. The community's chat (its
   servers' .relay lines, its page's chat, its announcements) then goes to that
   channel through H9's bot, and what people write there comes to every server of
   the community and to its page as [Discord] lines; mentions never ping, and
   Discord's formatting is taken literally. Give it to a community you trust with
   a channel H9 runs or knows: the bot posts as H9. The bot needs View Channel,
   Read Message History and Send Messages in that channel and the Message Content
   intent on in Discord's developer portal; the panel says how the channel last
   answered. STOP ends it. docs\H9_COMMUNITIES.txt section 3a.

   What a community's own settings do, in short: JOIN open (anyone signed in),
   request (its admins approve) or invite; VISIBILITY listed, unlisted (by link
   only) or private (members only; its servers are left out of the site's public
   lists, the SERVERS page and /find for anyone else); CHAT OPEN TO EVERYONE (the
   owner's switch: every signed-in player may use the page's chat; never in a
   private community); CHAT NEEDS PROVEN PLAYERS and DATA NEEDS PROVEN PLAYERS (on
   from the start: only a game that proved the player id may relay a line, or have
   shared data read or written; off, an announced h9_clientid, which any player
   on the server can copy, is taken for that feature; only the owner switches
   them off); MEMBERS-ONLY SERVERS (whoever is not a
   member is kicked, Steam clients always), which a copied h9_clientid can fool
   unless WHITELIST NEEDS PROVEN PLAYERS is on: then only games that proved the
   player id get in (H9XASH with the ID proof, on a server with
   h9_presence_challenge 1, and the web client), and an older H9XASH does not.

   Audit log actions: community.create, .settings, .delete, .server.link,
   .server.update, .server.unlink, .staff.add, .staff.remove, .member.approve,
   .member.refuse, .member.invite, .member.uninvite, .member.remove,
   .sanction.<kind>, .sanction.revoke, .announce, .chat.delete, .data.rollback,
   .discord; presence.server.enroll, .reenroll, .listen, .approve, .revoke, .block,
   .unblock, .flags_resolve; presence.sanction.<kind>, .sanction.revoke;
   presence.announce.
   A member joining or leaving by themselves is not in the audit log.


 18. BACKUPS AND RESTORE
 -----------------------
   One command does every backup job. Set it once per shell, like $A
   (section 3):

     B="sudo -u h9web /usr/bin/node /opt/h9web/bin/h9web-backup.js --config /etc/h9web/config.json"

   Every option is in h9web\README.txt, section 10; the VPS's timer, copies
   off the VPS and moving to a new VPS in havoc9.org\webclient\DEPLOY.txt,
   section 13.

 What a backup holds
   One file, h9web-<host>-<date>-<time>.h9backup (the time in UTC): the
   database (accounts, the forum, the communities, presence, the Discord
   links, the audit log), the forum's profile pictures, the presence keys,
   and a list of all of it with checksums. It is taken while the site runs.
   Not in it: secrets.json and data.key (the keys), unless you ask for them
   with --with-keys, which works only with --encrypt. Keep one copy of the
   keys offline, apart from the backups (section 8): a backup and its keys
   in one plain file is a backup anyone can open.

 Backing up by hand
     $B backup                    into /var/lib/h9web/backups
     $B backup --keep 14          the same, and the older ones beyond 14 go
     $B list                      what is there, each one checked
     $B verify <file>             one backup checked through
   Encrypted, for copies that leave the VPS: the passphrase in the first
   line of a file only h9web can read (or in H9WEB_BACKUP_PASSPHRASE), then
     $B backup --encrypt --passphrase-file /etc/h9web/backup-passphrase
   The command refuses a passphrase typed on the command line. Lose the
   passphrase and its backups are lost with it: keep it offline with the
   keys.

 Backing up on a schedule
   The VPS: the daily timer (DEPLOY.txt, section 13).
   A Windows PC with the local site: h9web\backup.cmd makes a backup now
   (double-click it; into Documents\h9web-backups, the newest 30 kept). For
   a schedule, in PowerShell in the h9web folder:
     .\backup-task.ps1 -Install                  every day at 04:00
     .\backup-task.ps1 -Install -Hourly          every hour
     .\backup-task.ps1 -Install -Time 22:30 -Keep 60 -Out D:\h9web-backups
     .\backup-task.ps1 -Status                   the last run and its result
     .\backup-task.ps1 -RunNow                   the same backup, now
     .\backup-task.ps1 -Remove
   It runs as you, only while you are signed in, so it needs no password and
   no admin; a run missed while the PC was off runs when it is next on.
   -WhatIf shows what -Install or -Remove would do and does nothing. Each
   run is logged in h9web-backup.log beside the backups.

 Restoring everything
   Stop the site first; restore refuses while it runs:
     sudo systemctl stop h9web
     $B verify <file>
     $B restore <file>
     sudo systemctl start h9web
   It shows what it will replace and asks you to type yes. Before it changes
   anything it saves the data as it is to
   /var/lib/h9web/backups/pre-restore-<time>.h9backup: to undo the restore,
   restore that file. secrets.json and data.key stay as they are unless the
   backup holds them, and they must be the ones the backup was made with:
   restore refuses another secrets.json (every password would stop working).
   A restore also brings back the sessions the backup holds: after restoring
   past a security incident (a stolen password, a hijacked account), sign the
   accounts involved out before starting the site again, with
   $A revoke-sessions <username> or reset-password (section 4); to sign
   everyone out, h9web\README.txt section 10 has the command.

 Restoring only the forum, or only the communities
     $B restore <file> --only forum
     $B restore <file> --only community
   That part goes back to how it was in the backup; the accounts and
   everything else stay as they are now. The forum comes with its profile
   pictures; the communities with their members, requests, invitations,
   admins, linked servers, bans and mutes, chat and data. An account deleted
   since the backup stays deleted: its posts come back as from a deleted
   account, its votes, signature and memberships do not come back. It works
   only between the same h9web version and says so otherwise (restore with
   the version the backup was made with, then update). --only accounts puts
   back the accounts alone, with sessions, the audit log and username
   changes.

 Moving the forum or the communities to another site (export, import)
     $B export --only forum --out /var/lib/h9web/forum.json
     $B export --only community --out /var/lib/h9web/community.json
   Copy the file to the other site, stop that site, and there
     $B import forum.json
   The import replaces that site's forum (or communities) with the file's.
   Accounts are matched by username and none is made. Posts by a name the
   other site does not have show as from a deleted account; that name's
   votes, signature, memberships, requests and invitations are dropped.
   Profile pictures stay with each site's accounts and do not travel this
   way. Like restore, it takes a safety backup first (pre-import-<time>).

 Moving to a new VPS
   In this order (DEPLOY.txt, section 13, has the commands):
     1. Set up the new VPS with the same h9web version; do not start it.
     2. Put the old secrets.json and data.key into /var/lib/h9web (owner
        h9web, mode 0600), unless the backup holds them.
     3. Stop h9web on the old VPS, take a last backup there, copy it over.
     4. $B restore <file> on the new VPS, start h9web there, check it.
     5. Point the DNS at the new VPS. Keep the old one stopped, with its
        data, until the new one has run well for a few days.


 19. RATED PLAY: THE LADDER
 --------------------------
   havoc9.org/ladder/ shows the ratings of rated play: xjiro's compts Elo, per kill and
   per match, on havoc9.org accounts. docs\H9_COMPETITIVE.txt is the whole story.
   Ranked play is always on. Every mode but roleplay, on every server enrolled with
   havoc9.org, counts for the server's own table, its community's ladder (where the
   community's staff count the server) and the H9 ladder, and feeds each player's
   career level. Only proven players count: bots, and games that do not prove the
   player id, change nothing.
   What is an H9 admin's (role admin):
     UNRANKED          a server's table on the LADDER page (MARK IT UNRANKED), or ADMIN,
                       LEVELS, RANKED SERVERS, which lists every enrolled server: the
                       match under way ends, and none of the server's matches count,
                       anywhere, from then on. RANK IT AGAIN counts them again. AND
                       VOID PAST MATCHES (a first and a last day, and VOID typed) takes
                       back its matches from those days too, one void each. A server
                       reports its own kills and results: mark one whose operator you
                       do not trust
     VOID              on any match page: takes back exactly what the match gave and
                       took, in every table, and the career experience it gave
     DISPUTES          on the H9 ladder: the open disputes players filed (48 hours
                       after a match), with RESOLVE
     LEVELS            ADMIN, LEVELS: what a match, a rated win and a kill give in career
                       experience, the bounds of the factors it is multiplied by, the
                       level curve (the experience for Lv 2 and its steepness), and
                       whether Lv 0 shows. The table beneath works out about how many
                       hours of play reach Lv 10, 25, 50, 75 and 99 at those settings.
                       SAVE works every account's level out again at once
     SEASONS           ADMIN, LEVELS, COMPETITIVE SEASON. RESET THE COMPETITIVE SEASON
                       (type RESET) archives the standings and starts the next season
                       with everyone unrated; the levels and the experience stay. SET
                       THE SEASONS BACK TO SEASON 1 (type SEASON 1) drops every archived
                       season with its standings, and the season under way becomes
                       season 1. Each copies the database into the data folder's
                       backups first, and says which file
     RANK              ADMIN, ACCOUNTS, open an account, RANK (a moderator: ACCOUNTS,
                       RANK, a name, SHOW): the career level and experience, the next
                       level's, each table's rating, place and numbers, and every
                       adjustment. ADJUST THE RANK sets a table's rating, or the
                       career's experience, or moves it by an amount (below 0 takes
                       away), with a note of 3 to 200 characters and your own password;
                       never on your own account or another admin's. The level is worked
                       out again at once
   Everyone sees every account's career level (the badge) and ELO rating (the forum, the
   ladder, .rank): no privacy switch hides them. SHOW MY PLAYTIME hides the playtime and
   presence only.
   A community's staff turn their own ladder on, tick the servers that count for it
   and void a match on it, from their ladder's page.
   Audit log actions: presence.compete.server.unranked, presence.compete.void,
   presence.compete.dispute.resolve, presence.compete.levels,
   presence.compete.season.reset, presence.compete.season.restart,
   presence.compete.adjust (in the account's own trail), community.compete,
   community.server.compete, community.compete.void.
