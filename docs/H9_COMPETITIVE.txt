===============================================================================
 H9 COMPETITIVE: COMPTS'S ELO AND SCOREBOARD, ON HAVOC9.ORG ACCOUNTS
===============================================================================

 Who this is for: whoever runs an H9 server whose matches should count,
 whoever runs havoc9.org, and any player who wants to know how the numbers on
 havoc9.org/ladder/ are made.

 Status: built (2026-11-02), ranked play on every server and the career level
 since 2026-11-03. h9_compete.amxx 1.2 and h9_rank.amxx 1.0 on the game
 servers, compete.js in h9web's presence module, the LADDER page and the
 admin panel's LEVELS tab on havoc9.org. Section 13 lists what is left for
 later.

 The short version
   * xjiro's Competitive TS (compts\) rated TS players per kill, by SteamID,
     on its own web service. H9 has no SteamIDs, so compts could never run
     here. h9_compete.amxx keeps compts's rule and its face (a ranking from
     1000) and puts the ratings on havoc9.org accounts instead.
   * Ratings move per kill, as in compts, and a rated match adds +100 to
     each winner and -70 to each loser, as compts's README planned. Every
     kill and match is kept, so each player has a match history.
   * Ranked play is always on: every mode but roleplay, on every server
     enrolled with havoc9.org, counts for its own table, its community's
     ladder where the staff count it, and the H9 ladder, unless H9's admins
     mark the server UNRANKED.
   * Only proven players count: an account whose game proved its player id
     on that server in the last 10 minutes (h9_presence's challenge), or a
     web client player on the relay. Anyone else, bots included, plays as
     ever, moves nothing and holds up nothing.
   * A server signs its reports with its h9_presence key, so there is no API
     key to set. A server havoc9.org does not know sends nothing.
   * Every account has a level, Lv 0 to 99: its career, overall experience
     from kills and matches in every mode, on top of the compts rating,
     which stays the skill figure. The badge shows by the name on the
     in-game scoreboard, the forum and the ladder, for everyone: no privacy
     switch hides a level or a rating (section 8a).
   * .rank in game, and a read-only API, give anyone's rank (section 8c).

 1. WHAT COMPTS DID, AND WHAT CARRIED OVER
 -----------------------------------------
 compts\ is xjiro's "Competitive TS" 1.0 (MIT; the repository's copy has his
 CREATOR.MD and LICENSE.MD). It is a 177-line AMX Mod X plugin and a Flask
 and SQLite service. The plugin sent one HTTP request per kill, and the
 service kept one number per SteamID (from 1000) and showed a top 100. It
 had no matches and no history. It stays in compts\ exactly as xjiro
 shipped it.

 It could not run on H9. An H9XASH server's get_user_authid() is the
 engine's ID_<hashed cd key>, not a SteamID, so every report would have
 failed. It also had four faults, which h9_compete does not repeat:
   * the kill bonus had the wrong sign: killing a worse player paid more,
     and a much worse victim even gained. Here the bonus is for killing a
     better player, as compts's README says;
   * its /cron route ran decay for anyone who called it. Here decay runs
     inside h9web on its own timer, with no route at all;
   * decay was -5 a day where the README says -10. Here it is -10;
   * its player loop stopped at slot 31. Here every slot counts, up to
     get_maxplayers().

 Carried over: the rule (section 4), /rank, /elo, !rank and !elo (now
 h9_rank's .rank), the rating told to everyone when a player joins, numbers
 from 1000, and decay.
 Replaced: SteamIDs by proven havoc9.org accounts, the API key by the
 server's h9_presence key, the service by h9web, and one global number by
 a table per server, per community and for H9.


 2. TURNING IT ON: A SERVER, A COMMUNITY, THE H9 LADDER
 ------------------------------------------------------
 A server: nothing to turn on.
   1. h9_presence.amxx with a live key (docs\H9_PRESENCE.txt, section 4a),
      and h9_presence_challenge 1, so that H9XASH players can prove their
      ids. Web client players are proven by the relay either way.
   2. h9_compete.amxx in plugins.ini below h9_presence (build.bat builds and
      registers it; the presets list it). configs\h9_compete.cfg, executed
      on every map, has h9_compete 1. It is a server rule (FCVAR_SERVER),
      so server browsers can see it.
   3. Its matches count from then on: its own table, and the H9 ladder.
 A server without a live key, one havoc9.org does not know, sends nothing and
 says nothing: no match starts, no join line is told, and h9web refuses
 anything it might send (403) before keeping any of it. When havoc9.org
 does not answer, a match's start is asked again after 30 seconds, then 60,
 up to 5 minutes apart, and a refused match is logged once a map.

 A community (its owner or admins, signed in on havoc9.org):
   1. Open the community's ladder: havoc9.org/ladder/?scope=c:<short name>.
   2. TURN THE LADDER ON.
   3. For each linked server you trust, COUNTS FOR THE LADDER: YES. A server
      shows there once it has reported a match.
 Turning either off stops new matches counting. What is already there
 stays, unless it is voided.

 The H9 ladder counts every enrolled server. An H9 site admin marks one
 UNRANKED (ADMIN, LEVELS, RANKED SERVERS, or the server's table on the
 LADDER page): its match under way ends, cancelled, and from then on its
 matches count nowhere, not even on its own table (h9web answers a start
 409 not_rated, and the plugin drops that match). The same switch, with a
 first and a last day and VOID typed, voids its matches from those days,
 one void each. RANK IT AGAIN counts it again from then on.

 The scopes are fixed when a match starts. Revoking or blocking a server's
 key stops it counting anywhere at once. The audit log records each switch
 as presence.compete.server.unranked, community.compete or
 community.server.compete.


 3. WHO COUNTS: PROVEN PLAYERS ONLY
 ----------------------------------
 h9web reads each player's h9_clientid with core's clientIdIndex, as
 presence does. That alone proves nothing: everyone on a server can read the
 value and send it as their own. So a player counts only while presence has
 them in game on that server, verified and not held:
   * verified: their game answered a nonce that h9web issued to that server
     no more than proofMaxAgeSeconds (600) ago. h9_presence challenges each
     player again every 5 minutes. Or they are a web client player whose
     signed-in relay socket is on that server;
   * not held: an account in two places at once counts in the first place
     only (docs\H9_PRESENCE.txt, section 9).
 h9web checks this for both players of every kill, when the batch arrives,
 and for every player at the start and the end of a match. A copied
 h9_clientid proves nothing, so it rates nothing. A server that keeps
 reporting a player who has left can do so for 10 minutes at most.
 The plugin keeps the same rule on its side (h9_compete 1.3): it names a
 player to h9web, on the roster, as a killer or as a victim, only while
 h9_presence says that player's own game is proven (h9p_account), because
 h9web cannot tell two slots that announce one id apart and the plugin can.
 A player who takes another's id for the moment of a kill is unproven, so the
 kill is nobody's: the player whose id it was is not credited, and not blamed
 for a death. A player proven in the middle of a match joins its roster then.

 Anyone else plays as ever and is never stored: an H9XASH on its own random
 id, a game that cannot answer the challenge, a Steam client. A kill by or
 of such a player, a bot, a team kill or a suicide moves nothing. Nothing
 kicks them either.

 Bots never count. Only proven havoc9.org accounts are tracked: bots and
 players who are not signed in get no rating and no level, and change
 nobody's. A bot proves nothing, so a kill of a bot or a death to one is
 dropped before anything is kept (applyKill in compete.js): no rating
 moves, no experience is given, the kills and deaths that career
 experience's kills-to-deaths factor reads do not see it, and no level
 changes. The kills between proven players in the same match still count.
 A match with bots on its sides, by the plugin's count at its start or at
 its end, has no rated result (no +100 or -70, no win's experience), but
 each proven player who plays it out still has the experience for playing
 it (section 8a). Unproven humans hold up nothing either: they are left out
 of a match's sides, and the proven players' match is rated as if they were
 not there. This holds whatever a server reports, since only a proof makes
 a player count.


 4. THE RULE
 -----------
 compts's, from its README:
   start        1000 in every table a player enters
   a kill       the killer +1, the victim -1
   a headshot   the killer +1 more
   the bonus    for each 100 points the victim is above the killer, the
                killer +1 more, and the victim -1 more for each 2 of those
                (bonus = (victim - killer) / 100, rounded down, never
                below 0; the victim loses 1 + bonus / 2, rounded down)
   a match      a rated match on the MATCH ladder: +100 to each winner,
                -70 to each loser; a player who left after a round or more
                loses, and so does a side that forfeits
   staying away 30 days without a counted kill or match: -10 a day, once a
                day, from the 31st
   the floor    nobody goes below 0
 One account's kills on one other count for at most 30 a day
 (pairKillsPerDay). Past that a kill is kept in the match's numbers and moves
 nothing, so two friends cannot farm each other.

 Example: a 1000 kills a 1301 with a headshot. The bonus is 3, so the killer
 gets 1 + 3 + 1 = +5, and the victim loses 1 + 1 = 2.

 Why per kill and per match: compts moved its number per kill, and its
 README planned the match result on top ("+100 on win, -70 on
 loss/disconnect"; "match outcome should be worth hours of DM activity").
 winPoints and lossPoints (section 11) set to 0 make results history only.


 5. MATCHES AND THE TWO LADDERS
 ------------------------------
 Each table has two ladders:
   MATCH  a ts_matchmode match, wherever its match mode plays (tsm_enabled
          1): Team Elimination, Siege, Uplink, Assault, Capture the Flag, Mech Warrior
          and Wave Survival. Kills, and the result when the match is
          rated
   DM     every other map: TS's own game on its own rules, deathmatch or
          teamplay (the stock ts_ and ctb_ maps, h9_dm_, h9_tdm_, h9_ctb_ and the
          rest). Kills only; each map is one match, ranked by frags minus
          deaths for the history
 Roleplay maps (rp_ or tsrp_ at the start, _rp_ or _tsrp_ inside, as
 ts_matchmode's roleplay_map has it) are never rated: the plugin sends
 nothing from them, and h9web refuses a start on one (409 not_rated).
 h9_compete_ladder picks a ladder by hand.

 A MATCH-ladder match runs from its first round going live to its end:
   finished   ts_matchmode's tsm_match_complete
   forfeit    tsm_match_forfeit: a side voted .forfeit, or left its side
              empty while the other still had players
   cancelled  anything else that stops it: an admin's restart or cancel,
              both sides empty, a side out of humans, a map change. Not
              rated, and no experience; its kills stay counted
 A DM map's match ends 20 seconds before the map's time runs out.

 A result is rated when:
   * the match finished or a side forfeited, and it has a winner;
   * no bot played on either side;
   * at least 3 rounds were played, and it lasted at least 5 minutes; a mode
     that plays its match as ONE round (Assault and Capture the Flag by
     default: h9_assault_rounds 0, h9_ctf_rounds 0) says so in its end
     report (oneRound), and is asked one round and the 5 minutes;
   * on the H9 ladder: at least 2 proven players on each side. On a
     server's table or a community's ladder: at least one proven player on
     each side. Unproven players are not counted either way;
   * a player counts if they played at least half its rounds, or left
     after a round or more.
 Each table decides for itself, so a match can be rated on its server's
 table and not on the H9 ladder. The answer says why not, and the match page
 shows it. A match that h9web hears nothing of for 6 hours is abandoned.
 Its kills stay counted.

 Assists: ts_matchmode counts them for the scoreboard's A column (TSM_ASSIST_MIN
 damage to a victim an enemy other than the killer finishes, within 10
 seconds). It keeps a second count for ranked play (tsm_assists_ranked) that
 leaves out an assist on a kill a bot had a part in, as victim or killer, as
 kills of bots and by them count for nothing; the scoreboard counts them all.
 h9_compete reads the second count (the first from a ts_matchmode without it)
 and sends each player's assists in the match in its end report: what the
 count added between their joining the match and its end or their leaving,
 summed over each time they were in it. They are summed into each of the match's tables, as kills are,
 and a void takes them back. A ts_matchmode without tsm_assists leaves the
 native unbound, and the report says null: the site shows assists only where
 a server counted them.


 6. WHAT THE PLUGIN SENDS: H9WEB'S API
 -------------------------------------
 All four calls are POSTs to /api/presence/compete/..., signed as
 h9_community's calls are (docs\H9_COMMUNITIES.txt, section 12): the body is
 { "v": 1, "server", "ts", "nonce", ... }, with X-H9-Server and
 X-H9-Signature made with h9_presence's live key (h9p_sign).

   start   { ladder: "match" | "dm", map, mode, humans, bots,
             players: [ [h9_clientid, side], ... ] }
           -> { ok, match, scopes: [ "server", "community", "network" ],
                proven }
           Starting a match closes any match still open on that server as
           cancelled. 409 not_rated on a roleplay map or an UNRANKED server,
           and on a server that is not authenticated: it runs something
           beside H9's official preset, or its operator set
           h9_authenticated 0 (docs\H9_PRESENCE.txt section 4d).
   kills   { match, seq, players: [ [h9_clientid, side], ... ],
             kills: [ [killer id, victim id, headshot 0|1, team kill 0|1],
                      ... ] }
           -> { ok, seq, counted, unrated }
           seq counts the batches from 1. A batch already taken answers
           { duplicate: true }, and one that skips ahead gets 409
           out_of_order. Batches go every 10 seconds while kills wait, at
           most 150 kills a batch, and every 60 seconds with none.
   end     { match, seq, result: { how: "finished" | "forfeit" |
             "cancelled", winner, score1, score2, rounds },
             players: [ [h9_clientid, side, rounds, seconds, left 0|1,
                          assists | null], ... ],
             others: { "1": n, "2": n }, bots }
           -> { ok, match, rated, why, changes: { "<h9_clientid>":
                { server, network } } }
           others counts the humans on each side without a proven h9_clientid.
           The plugin tells each player their own change.
   rating  { ladder, ids: [ h9_clientid, ... ] }  at most 64
           -> { players: { "<h9_clientid>": null | { public,
                server: { elo, rank }, network: { elo, rank } } } }
           For the join line. null: not proven here now. public: always
           true, since no switch hides a rating.
   rank    { asker: h9_clientid, id: h9_clientid } or { asker, name }
           -> { ok, account: null | rankView, unknown }
           For h9_rank's .rank (section 8c): a player here by their id, or
           an account by its username (any case). account null: an id that
           is no account proven here (not signed in), or, with unknown, a
           name that is no account. rankView is GET /api/presence/compete/
           rank/:username's, with this server's tables and the H9 ladder
           only.

 Headshots: kills come from DeathMsg, which ts_matchmode relies on too. A
 kill is marked a headshot when TSX's client_death reports a head hit for
 the same kill. Where TSX does not fire, every kill counts as a body shot.
 Limits: callsPerServer (240 a minute) after the signature, and presence's
 serverCallsPerIp before it. The plugin keeps up to 256 kills while h9web
 does not answer, and counts any beyond that as dropped (h9_compete_status).


 7. WHAT H9WEB KEEPS
 -------------------
 The presence module's migration 5 (modules\presence\migrations.js says what
 each column means):
   compete_servers      a server's flags: UNRANKED (migration 11; the old
                        NETWORK LADDER column is no longer read), and the
                        community it counts for
   compete_communities  a community's LADDER switch
   compete_matches      each match: server, community, scopes, ladder, map,
                        mode, times, how it ended, winner, score, rounds,
                        rated and why, kills that counted and that did not
   compete_players      a proven account's part in a match: side, kills,
                        deaths, headshots, assists (migration 10), team
                        kills, rounds, seconds, result or place. Nobody else
                        gets a row
   compete_ratings      per table, ladder and account: rating, kills,
                        deaths, headshots, assists, wins, losses, matches,
                        last played
   compete_deltas       what each match gave and took, per table and
                        account, assists too: what a void takes back
   compete_xp           each match's career experience per account, its
                        kills' and its end's (migration 8)
   compete_adjustments  every rank change an admin made: a table's rating
                        or the career experience, before and after, the
                        note, who and when (migration 11)
   compete_pairs        kills per pair per day, for the pair cap (2 days)
   compete_disputes     players' disputes, until an H9 admin resolves them
 Never kept: an unproven player's id or name, in-game names (the site shows
 usernames), proofs, nonces or addresses.

 A deleted account: its ratings go, and its rows in matches stay as "a
 deleted player", so the other players' matches still add up. Everything
 else stays as long as the ladder does: it is the history. h9web's backups
 hold it with the rest of the database.


 8. THE SITE: HAVOC9.ORG/LADDER/
 -------------------------------
   ladder/                        the H9 ladder
   ladder/?scope=c:<short name>   a community's ladder
   ladder/?scope=s:<server id>    a server's own table
     &ladder=dm                   the DM ladder; &page=N further down
   ladder/?p=<username>           a player: each rating and rank, and the
                                  latest 20 matches
   ladder/?m=<match>              a match: sides, score, rounds, and each
                                  player's numbers and change per table
 Tabs along the top lead to the H9 ladder, each community ladder that is on,
 and each rated server's table. The SERVERS page links to it.

 Staff see their switches on the same page:
   * H9's site admins: MARK IT UNRANKED on a server's table, the open
     disputes (RESOLVE) on the H9 ladder, and VOID on any match;
   * a community's staff: TURN THE LADDER ON/OFF and COUNTS FOR THE LADDER
     per linked server on their ladder, and VOID on a match that counted
     there. Their void takes the match off their ladder only;
   * a player of a match: DISPUTE, for 48 hours after it ends.
 A void takes back exactly what the match gave and took in the tables
 voided, and the audit log records it (presence.compete.void,
 community.compete.void).

 The API behind the page (ratings and levels show for every account; matches
 follow SHOW WHICH SERVER AND MAP and SHOW "LAST SEEN"):
   GET  /api/presence/compete/board?scope=network|c:<slug>|s:<server id>
        &ladder=match|dm&page=N              50 to a page
   GET  /api/presence/compete/player/<username>
   GET  /api/presence/compete/me             signed in: all of one's own
   GET  /api/presence/compete/match/<id>
   GET  /api/presence/compete/servers        rated servers and their flags;
        ?all=1, an H9 admin's: every enrolled server
   POST /api/presence/compete/servers/<server id>   { unranked, void: { from,
        to }, confirm: "VOID", note }  (admins)
   POST /api/presence/compete/communities/<slug>           { ladder }
   POST /api/presence/compete/communities/<slug>/servers/<server id>
                                                           { counts }
   POST /api/presence/compete/matches/<id>/void            { note }
   POST /api/presence/compete/matches/<id>/dispute         { reason }
   GET  /api/presence/compete/disputes?status=open|resolved|all  (admins)
   POST /api/presence/compete/disputes/<id>/resolve        { note }
   GET  /api/presence/compete/seasons    the season under way and the past ones
   GET  /api/presence/compete/board?...&season=N    a past season's standings
   POST /api/presence/compete/season/reset    { confirm: "RESET" }  (admins)
   POST /api/presence/compete/season/restart  { confirm: "SEASON 1" }  (admins)
   GET  /api/presence/compete/levels   (admins) the settings and the estimate
   POST /api/presence/compete/levels  { matchXp, winXp, killXp, kdaMin,
        kdaMax, eloMultMin, eloMultMax, xpBase, xpPower, showZero }  (admins)
   GET  /api/presence/compete/accounts/<name>   (moderators) a whole rank,
        its experience and its adjustments
   POST /api/presence/compete/accounts/<name>/adjust   (admins) { field:
        "elo" | "xp", scope, ladder, set | by, note, password }
   GET  /api/presence/compete/rank/<username>   anyone's rank (section 8c)
 A private community's ladder, its servers' tables and their matches are
 for its members (and H9's site admins) only.


 8a. ACCOUNT LEVELS: LV 0 TO 99
 ------------------------------
 Every havoc9.org account's level is its career: overall experience from
 play, on top of the compts rating, which stays the skill figure. The badge
 always shows the career level; the H9 ladder's MATCH rating shows beside it
 as the ELO figure, in thousands ("1.2K ELO": one decimal under 10K, a ".0"
 dropped, "5K ELO"), on the forum (a post's author and the profile), in the
 RANK block, on the ladder and in .rank.

 Experience, for proven players only, where the match counts for the H9
 ladder (not on a roleplay map, not on an UNRANKED server):
   a kill       killXp (1) to the killer, for each kill of a proven player
                (not a team kill, not past the pair cap)
   a match      each proven player who plays it out: half its rounds or
                more, and not leaving; a match that finished (not
                cancelled) and lasted minSeconds (5 minutes)
   a DM map     each proven player there at its end who played minSeconds
                of it
 A match's or a map's experience is (matchXp 100, + winXp 50 for a result
 rated on the H9 ladder and won) x the kills-to-deaths factor ((kills + 1) /
 (deaths + 1), proven players only, kept between 0.5 and 2) x the rating
 factor (the player's H9 ladder rating for that ladder / 1000, kept between
 0.5 and 2). So a match with bots, or Wave Survival, gives the experience for
 playing it out and no win. A leaver gets none, a voided match's experience
 (its kills' too) is taken back, and a season's reset keeps it: it is the
 account's, over every season. Admins can adjust it (section 8d).

 The level: Lv = 1 + (experience / xpBase) ^ (1 / xpPower), rounded down,
 from 1 to 99, so Lv L needs xpBase x (L - 1) ^ xpPower experience; Lv 0
 with none at all. It only rises from play. Defaults xpBase 20 and xpPower
 2.3, the road the user asked for: early levels in a few evenings, the
 middle in months, Lv 99 in years of regular play. A typical active hour
 (3 matches or DM maps, half of them with a rated result and half of those
 won, and 40 kills of proven players, at a factor of 1 and a rating of 1000)
 gives about 378 experience. At the defaults:
   Lv 10   3 132 experience      about 8 hours of active play
   Lv 25   29 890                about 79 hours (two months at 10 a week)
   Lv 50   154 341               about 409 hours (nine to ten months)
   Lv 75   398 349               about 1 055 hours (two years)
   Lv 99   760 064               about 2 013 hours (four years)
 The LEVELS tab works the same table out live from the settings in force
 (compete.js levelEstimate; TYPICAL_HOUR holds the typical hour). Saving the
 settings works every account's level out again at once (the audit log:
 presence.compete.levels).

 No privacy switch hides a level or a rating: SHOW MY PLAYTIME hides
 playtime and presence only. Lv 0, an account with no experience yet, shows
 its Lv 0 badge everywhere, the game included, unless the admins set AN
 ACCOUNT WITH NO EXPERIENCE to "No badge or level at all" (showZero, on by
 default).

 Where it shows:
   * in game, as the level's badge before the name on the scoreboard:
     h9web's answer to each presence report gives each proven player's
     level ("levels", per slot), and h9_presence (1.6) tells every client in
     the H9Level user message (byte slot, byte level, 255 for none; a
     joining client gets the whole table, and a slot that empties is
     cleared). H9's client.dll draws it (reTS cl_dll\vgui_ScorePanel.cpp,
     H9 LEVELS and H9 LEVEL BADGES): the picture
     gfx\vgui\h9_levels\lv-<N>.tga, scaled to the row as the player's
     picture is, or the text "Lv N" where that picture is missing. It shows
     on every server that reports, rated or not. Bots, players without an
     account and games that did not prove their player id show none;
   * on the forum, as a badge beside the name: each post's author (with
     its ELO figure), the thread and category lists (author and last
     poster), "Started by" on a thread, and a large badge with its ELO
     figure on the member profile, the page the game's profile link opens;
     the player's card and the ACCOUNT page too;
   * on the ladder: the LEVEL column of every table, and the player's page;
   * the RANK block, on the ACCOUNT page under the player's card and on the
     member profile under theirs: the badge (72 px), "LV N" and the ELO
     figure, "SEASON N, SINCE <date>", the H9 ladder's rating and place,
     this season's matches won and lost, kills, deaths (and assists) and
     K/D, and the career's experience. With no rated match it says "No
     ranked matches yet this season." It comes in the presence views'
     "rank" (compete.js, rankOf), the same for everyone; the batch read for
     authors leaves it out. presence.js's renderRank draws it, and a
     profile's data-h9-presence="rank" shares the card's one read.
 One renderer draws every badge on the site: presence.js's levelBadge,
 which fills any element marked data-h9-level="<username>" from the presence
 views' "level", read in batches and cached. The pictures are
 havoc9.org/assets/levels/lv-<N>-24.png, -48.png and -96.png, Lv 0 to 99 (a
 picture that does not load leaves its alt and title, "Lv N"), and the
 game's copies gfx\vgui\h9_levels\lv-<N>.tga (64 x 64 with alpha), in the
 Xash overlay, H9XASH and reTS\binaries\ts; export.bat takes them into the
 package, and from there they reach the repo and the web client.
 modelling/make-level-badges.mjs draws them all. Its CONFIG, TIERS and
 UNRANKED decide the look: a new shape and more ornament every ten levels,
 in H9's purples, and for Lv 0 the first tier's disc, darker, with a dashed
 rim and a lavender number. A rerun takes about fifteen seconds, and
 D:/temp/level-badges-sheet.png shows them all, Lv 0 in its last cell.

 Kept: compete_levels (each account's level and experience, worked out again
 whenever its experience or the settings change), compete_xp (each match's
 experience per player, its kills' and its end's) and compete_config (the
 settings), the presence module's migration 8; compete_adjustments (an
 admin's changes to the experience add into it), migration 11.


 8b. SEASONS
 -----------
 The ladder plays in seasons, numbered from 1. Each table shows "SEASON N,
 SINCE <date>", with links to every past season's final standings.

 An H9 site admin ends one in the admin panel: ADMIN, LEVELS, COMPETITIVE
 SEASON, RESET THE COMPETITIVE SEASON, confirmed by typing RESET. Then,
 in order:
   1. h9web copies its database into the data folder's backups
      (pre-season-reset-<N>-<time>.db, the same kind of copy a migration
      makes). If it cannot, nothing is reset;
   2. every table's standings are archived as season N's
      (compete_season_standings), readable on the ladder ever after;
   3. season N ends and season N+1 begins, with everyone unrated: no
      ratings. The career levels and their experience stay, since they are
      each account's over every season;
   4. the audit log records it (presence.compete.season.reset).
 Each account's next rated kill or match starts it again from the normal
 starting rating, 1000. The matches themselves stay, each marked with its
 season; a void of an earlier season's match takes its experience back and
 changes no rating in the current one.

 BACK TO SEASON 1 (the same box, typed SEASON 1): h9web copies its database
 first (pre-season-1-from-<N>-<time>.db), then every archived season goes,
 with its final standings, and the season under way becomes Season 1 from
 when it started. Its tables, the levels and the career experience stay as
 they are, and every match and adjustment counts as season 1's. The audit
 log records it (presence.compete.season.restart).


 8c. ONE ACCOUNT'S RANK: .RANK IN GAME, AND THE API
 ---------------------------------------------------
 In game, h9_rank.amxx (configs\h9_rank.cfg, COMMANDS.txt RANKS):
   .rank          the asker's own rank
   .rank <name>   the player on this server named <name> (an exact name
                  first, else the one name with <name> in it; several
                  such names are listed back), else the havoc9.org account
                  named <name>
 /rank, !rank, /elo and !elo do the same (they were h9_compete's say /rank).
 The answer goes to the asker alone, a chat line and the whole readout in
 their console, and what they typed is not shown in the chat: the career
 level and its experience, the season, and for the H9 ladder and this
 server's table the rating and place, the season's matches won and lost,
 kills, deaths, headshots, assists where a server counted them, and K/D. A
 bot, or a player not signed in to a havoc9.org account proven on this
 server, is "not signed in: no rank". It asks h9web through the signed call
 rank (section 6), with h9_presence's address and key, and h9_rank_cooldown
 (5 s) between one player's asks. Only a proven game is named to h9web, as
 the player asking and as the player asked about (h9_rank 1.1).

 On the site, GET /api/presence/compete/rank/<username>, read-only, any
 case, rate-limited per address (presence's readPerIp):
   { username, private: false, level, rule: "career", xp, elo, season:
     { number, started, ended }, ladders: [ { scope, kind, name, ladder,
     elo, place, matches, wins, losses, kills, deaths, headshots, assists,
     kd } ] }
 level the career level as publicLevel has it (null for Lv 0 with showZero
 off); xp its experience; elo the H9 ladder's MATCH rating, null with no
 rating yet; ladders every table the viewer may see (a private community's
 only to its members), the H9 ladder first, then servers', then
 communities', MATCH before DM; place among the players of that table; kd
 kills per death to two places, a player with no deaths their kills;
 assists a number where a server counted them, else null. The same answer
 for everyone, whatever the account's switches; cacheable for a reader who
 is not signed in. No such account: 404.


 8d. AN ADMIN'S RANK ADJUSTMENT
 ------------------------------
 On an account's page in the admin panel (ADMIN, ACCOUNTS, an account), the
 RANK box shows its career level and experience, the next level's
 experience, each table's rating, place and numbers, and every adjustment
 made. Moderators look it up in ACCOUNTS, RANK, and see the same, read-only.
 An H9 site admin ADJUSTS: a table's rating (the H9 ladder's, a server's or a
 community's, MATCH or DM) or the career's experience, set to a value or
 moved by an amount, with a note of 3 to 200 characters and their own
 password; never on their own account or another admin's. The change is
 kept (compete_adjustments: before, after, the note, who and when), the
 level is worked out again at once, and the audit log records it against
 the account (presence.compete.adjust), so it shows in the account's trail.
 An experience adjustment adds into the career's sum from then on; a
 rating adjustment sets that table's rating as it is now.




 9. INTEGRITY: WHAT A SERVER COULD FAKE, AND WHAT H9WEB CHECKS
 -------------------------------------------------------------
 Whoever holds a server's key, files or rcon can report any kill or result
 between players who really are proven there. They can change the game
 itself, or leave a player out. They cannot rate an account that is not
 proven on that server in the last 10 minutes. They cannot pass a bot off
 as an account, or replay or alter a call: the signature, the time and the
 one-time nonce stop that.

 A player can copy someone's h9_clientid, but the copy proves nothing, and
 neither rates nor takes the kills of the player whose id it is (section 3). A
 leaked raw player id is refused on any other device and flagged
 (docs\H9_PRESENCE.txt, section 9). Two accounts farming each other hit the
 pair cap. Client cheats are out of h9web's sight: H9XASH has no
 anti-cheat.

 What h9web checks: the signature, the time and the nonce; that each player
 is proven at that moment; the batch order; the match rules of section 5;
 the pair cap. What it cannot check is what really happened in a match.
 Each table is only as honest as the servers it counts, and the LADDER
 page says so. The remedies are DISPUTE, VOID, unticking COUNTS FOR THE
 LADDER, marking a server UNRANKED (with its past matches voided if need
 be), an admin's rank adjustment, and revoking its key.

 9a. What h9web holds a server to, whatever its plugin says
 ----------------------------------------------------------
 A plugin is code on a machine its operator controls, so a modified one, or
 a forged call made with a stolen key, says whatever its author likes. These
 checks are the site's own: none of them rests on the plugin telling the
 truth.
   * Asked at every call. A match is rated only while its server is rated:
     authenticated (the official preset, docs\H9_PRESENCE.txt section 4d),
     not UNRANKED, not on a roleplay map, and not a listen server. That is
     asked when the match starts and again by every kills and end call, not
     only at the start. A server that stops being authenticated in the
     middle of a match (its operator set h9_authenticated 0, or it lists a
     plugin off the official list) has the whole match voided: its kills and
     its result taken back with the experience they gave, the match marked
     voided, an audit entry made. An unauthenticated server never starts a
     match, so it gives no rating and no experience.
   * Listen servers rate nothing. A Create Game server runs its plugin on a
     player's own PC, where nothing can vouch for what it sends, and it
     enrolls with no admin to look at it. It feeds no table and gives no
     experience. listenRated 1 (a site setting) rates it like any other.
   * Kills have a pace. A match makes at most killBurst plus
     matchKillsPerMinute for each minute of the match's own time (the site's
     clock, from the match's start), and one player at most killBurst plus
     playerKillsPerMinute. The excess is dropped, counted as unrated, and
     written to the audit log, once an hour for each server.
   * Matches have a length. A match whose rounds ran faster than
     minRoundSeconds each is recorded and not rated, and no player's time in
     a match is more than the match's own.
   * Accounts have a day. An account is given at most xpPerDayMax experience
     and gains at most eloGainPerDayMax points on the H9 ladder in a UTC day.
     The kills and results still count in the match's numbers and in the
     server's own table; the limit is only on the two things that are worth
     something on every server. A server that fakes a thousand matches
     cannot lift any account past it.
   * The audit log. Every void the site makes, every kill rate no hand
     makes, and every account that reached its day (presence.compete.*), is
     in the admin panel's audit log. An entry blocks nothing by itself.
 Each limit is a setting (section 11) and 0 turns one off. The defaults sit
 above what a busy honest day reaches (20 matches, 300 kills) and far below
 what a script reaches in an hour.

 What this does not stop: an authenticated server whose operator holds the
 key, with real proven players, can still agree results among themselves
 inside those limits. The site cannot see that alone, which is why the
 remedies above stay, and why a community's server waits for an admin's
 approval before it reports at all (docs\H9_PRESENCE.txt section 4a).

 9b. The players' own games vouching for a match (not built)
 -----------------------------------------------------------
 The one check no server can touch is the one the players' games make. A
 sketch of it, using what the proof already shows works (docs\H9_PRESENCE.txt
 section 8: a challenge h9web issues, an answer only the account's player id
 can make, bound to the server and the time):
   * when a match ends h9web's answer to the server carries a nonce for the
     match; each H9 game (the engine's cl_ code, and the web client's page)
     sends h9web its own score line for it, the kills, deaths and rounds it
     saw, as HMAC-SHA256(player id, "h9match1:" + nonce + ":" + server + ":" +
     the line), straight to the site over HTTPS, never through the server;
   * h9web counts a player's experience and rating only where their game's
     line agrees with the server's within a tolerance (a game that dropped
     a packet misses a kill, a server that invents ten is 10 kills off), and
     raises an audit entry for the server and the account where it does not;
   * no server can make a line for a player who is not in the match, or
     change one that is, and the plugin needs no change.
 Cost: an engine patch and a page change for the line, one route and one
 table on the site. Games that send none (the Steam client, an H9XASH from
 before it) would keep counting as they do now until a date the site names.


 10. PRIVACY
 -----------
 Rank data shows for every account, whatever its switches: the career level,
 the ratings, places and numbers on the boards, the player's page, .rank and
 the RANK block, and the level in game. The ACCOUNT page's switches
 (docs\H9_PRESENCE.txt, section 6) hide where and when a player plays:
   SHOW MY PLAYTIME           the playtime and presence only
   SHOW WHICH SERVER AND MAP  off: the player's matches are not listed, and
                              a match page shows them as "a hidden player"
   SHOW "LAST SEEN"           off: the player's matches are not listed
 Hidden matches still count, and still move other players' ratings. A
 player always sees all of their own (GET .../me, or their own ?p= page),
 and H9's site admins see all of it. The plugin tells a joining player that
 the server is rated; a player who wants nothing kept plays on H9XASH's own
 random id.

 13. LEFT FOR LATER, AND DECISIONS
 ---------------------------------
 Not built yet:
   * a LADDER tab on the community page. It belongs to other work, so the
     LADDER page carries the community's switches for now;
   * h9web reading a server's rules (A2S_RULES) when a match starts, and
     flags for opponents on one network (an unusual kill rate is flagged
     already, 9a);
   * the players' own games vouching for a match (9b);
   * an end report that survives a map change. An end lost that way leaves
     the match abandoned, with its kills counted and its result lost;
   * Steam players, and match results sent to Discord.
 Decisions taken: Elo as compts has it, per kill, with match results on top
 (the README's +100 and -70). There is one MATCH ladder and one DM ladder.
 Ranked play is always on: every mode, Wave Survival and TS's own maps
 included, on every enrolled server, roleplay maps excepted and UNRANKED
 servers left out. Kill points between proven players always count; results
 only without bots. Unproven players hold up nothing. The badge is the career
 level, overall experience on top of the rating, and no privacy switch hides
 a level or a rating. Steam players are left out, and a deleted account shows
 as "a deleted player". Leavers and forfeits lose.
 Open:
   * should kills in a cancelled match keep counting, as compts's did?
   * is the pair cap of 30 kills a day right?
   * the typical hour behind the estimate (3 matches, 40 kills) is a guess
     until real play shows the numbers.
