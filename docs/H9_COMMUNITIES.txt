===============================================================================
 H9 COMMUNITIES: SERVERS THAT TALK TO EACH OTHER, AND TO HAVOC9.ORG
===============================================================================

 Who this is for: whoever runs an H9 game server or a community of them,
 whoever writes an AMX Mod X plugin that keeps data for players, and whoever
 runs the havoc9.org VPS.

 The short version
   * What it is for: a home on havoc9.org for a group of players -- a clan or
     a team, a project such as a map pack or a mod, a roleplay group, a
     network of game servers. It gets a page listed on havoc9.org/community/
     for anyone to find, so it is also how a group shows itself or its project
     to everyone on H9: its members, its linked servers and who is on them,
     its announcements, and a chat on its page that reaches the game.
   * A community is a havoc9.org account's group of game servers, run by that
     account (its owner) and the admins the owner names. Its page is
     havoc9.org/community/?c=<short name>.
   * A server joins in two steps. It enrolls with havoc9.org by itself
     (h9_presence does that: docs\H9_PRESENCE.txt, section 4a), then its
     console's h9_community_claim prints a one-time code that the owner or an
     admin enters on the community's page.
   * A community has members: anyone signed in joins an open one, asks to
     join one that takes requests, or is invited (section 2a). It can be
     listed, unlisted (by link) or private (members only), and its servers
     can be for members only.
   * Players chat across all the community's servers and its page: ".relay
     <text>" in game, the chat box on the site for its members (or for every
     signed-in player, when the owner opens it). H9's site admins can bridge
     that chat with a Discord channel (section 3a). "/find <name>" says where
     a player is. Portals on a map lead to the community's other servers.
   * The community's admins ban, mute and kick across all its servers, and
     announce to all of them. H9's site admins do the same H9-wide.
   * Plugins keep per-account data for the community through
     include\h9_community.inc: shared by every server of the community, safe
     against a server that is not in it.
   * Two plugins do the game's side: h9_presence.amxx (enrollment, the key,
     reports, kicks and mutes) and h9_community.amxx (everything else here),
     in that order in plugins.ini. Both are in every H9 preset; until a
     server has a key they do nothing and print nothing.

 1. SETTING UP A SERVER
 ----------------------
   1. Enrollment first: docs\H9_PRESENCE.txt, sections 4 and 4a. A dedicated
      server with h9_presence.amxx enrolls by itself. "h9_presence_status" in
      its console says "enrollment: live" and the public server id once it
      has a live key. A server on h9web's servers.json goes live as soon as
      havoc9.org has seen its enrollment code; any other waits for an H9
      admin to approve it (on havoc9.org/community/, H9 ADMIN).
   2. h9_community.amxx in plugins and in plugins.ini, on the line after
      h9_presence.amxx. build.bat builds, deploys and registers it; the H9
      presets (H9XASH\presets) list it.
   3. include\h9_community.inc goes into scripting\include (build.bat syncs
      it), for plugins that use the shared data.
   4. addons\amxmodx\configs\h9_community.cfg: the settings (section 13).
      Nothing in it is secret; build.bat copies TSM's over the server's on
      every build.
   5. Link the server to a community (section 2).
   6. "h9_community_status" in the server's console says whether h9web is
      answering, which community the server is in, and its portals.

 h9_community needs nothing else: no key of its own and no address. It signs
 every call with h9_presence's key through h9_presence's natives; the key
 itself never leaves h9_presence. Without h9_presence loaded it stays inert.

 2. MAKING A COMMUNITY AND LINKING SERVERS
 -----------------------------------------
 Making one. Signed in on havoc9.org/community/: a short name (3 to 32 of
 a to z, 0 to 9 and -, starting with a letter or digit; it never changes and
 is the page's address) and a name (up to 40 characters). The account that
 makes it owns it. An account owns at most 3 (communitiesPerAccount); H9's
 site admins have no limit.

 Linking a server.
   1. On the server's console, or over rcon: h9_community_claim
      (in game: amx_h9_claim, for admins with the rcon flag). It prints
        [H9] Link code: abcd-2345 (good for 15 more minutes, once).
      Over rcon the answer comes after the command has returned, so it shows
      on the server's own console; run the command again to see the same code
      (h9_community_claim new asks for a fresh one).
   2. On the community's page, RUNNING IT, LINK A SERVER: the code and a tag
      for the server (1 to 12 letters, digits, space, _ . -, starting with a
      letter or digit). The tag marks its players' chat lines: [Tag] Name.
 The code is only a proof that whoever enters it can see the server's
 console. It works once, for 15 minutes (claimMinutes), and h9web keeps only
 its hash. A server is in one community at a time: one linked elsewhere
 stays there until that community's staff unlink it. Linking it again to the
 same community changes its tag.

 Each linked server, on the community's page (staff only): its tag, READ-ONLY
 DATA (the server may read the shared data and not write it, section 8), and
 UNLINK, which cuts it off from the community's chat and data at once.

 The community's settings (staff): its name; JOIN (open, request or invite)
 and VISIBILITY (listed, unlisted or private), section 2a; CHAT ON (the
 community's chat, on by default); CHAT NEEDS PROVEN PLAYERS and DATA NEEDS
 PROVEN PLAYERS (on by default): only players whose game proved its player
 id (h9_presence's challenge, docs\H9_PRESENCE.txt section 8) may relay a
 line, or have data read or written for them. An announced h9_clientid alone
 is anyone's: every player on a server can read it and copy it. A game that
 cannot prove (an older H9XASH, a Steam client, a server with
 h9_presence_challenge 0) keeps the server's own chat and everything else, and
 is told why when it tries .relay. Switching one of the two off takes the
 announced id for that feature, from any game: do it only for a community
 whose players cannot be proven, and know that anyone on its servers can then
 speak, or write data, as an account whose id they can read. MEMBERS-ONLY
 SERVERS and WHITELIST NEEDS PROVEN PLAYERS (off by default), section 2a.
 Migration 14 of h9web's presence module switched both on for every community
 that existed when it ran (the setting holds on or off and nothing else, so a
 choice cannot be told from the default; the copy of the database taken before
 the migration, <dataDir>/backups/pre-migrate-presence-v*.db, still has each
 community's old values in presence_communities); an owner who wants one off
 sets it off again on the community's page.

 Admins: the owner names them by username (ADMINS) and removes them. They do
 everything on the page except naming admins, putting data back, deleting the
 community, opening its chat to everyone and switching a proof requirement off
 (CHAT NEEDS PROVEN PLAYERS, DATA NEEDS PROVEN PLAYERS), which only the owner
 (and H9's site admins) can do. An admin may switch one back on.

 Deleting: the owner types the short name. The community, its servers'
 links, its members, requests and invitations, its chat, its bans and mutes
 and its shared data go; the servers stay enrolled with havoc9.org.

 2a. MEMBERS, JOINING AND PRIVATE COMMUNITIES
 --------------------------------------------
 Members. The owner and every admin always belong. Anyone else becomes a
 member as the community's JOIN setting allows:
   open      (the default) JOIN on the community's page: a member at once
   request   REQUEST TO JOIN: the request waits under MEMBERS, REQUESTS TO
             JOIN, until an admin approves or refuses it; the asker can
             withdraw it meanwhile
   invite    only accounts an admin invites by username (MEMBERS,
             INVITATIONS); the invited account sees the invitation on
             havoc9.org/community/ and on the community's page, and accepts
             or declines it. An invitation works in any mode.
 A member LEAVEs on the community's page; an admin who leaves stops being
 one. The owner cannot leave (delete the community instead). Staff remove a
 member under MEMBERS; only the owner removes an admin, and nobody the
 owner. An account banned in the community or H9-wide cannot join, ask or be
 invited, and an invitation it had does not let it in.

 What shows: the member count, on the communities list and the community's
 page (not for a private community); the member list, to members, staff and
 H9's site admins; requests and invitations, to staff. On
 havoc9.org/community/ a signed-in account sees YOUR COMMUNITIES (any
 visibility), its invitations, and its requests waiting.

 Joining, asking, accepting, declining and leaving are limited to 30 an hour
 per account (membershipPerAccount); invitations to 60 an hour per admin
 (invitePerAccount). Approving, refusing, inviting, withdrawing an invitation
 and removing a member go into h9web's audit log (community.member.approve,
 .refuse, .invite, .uninvite, .remove), with who did it.

 Visibility:
   listed     (the default) on the communities list; its page is public
   unlisted   not on the list; its page opens for anyone with the link
   private    only members and H9's site admins see its page, servers,
              members and chat. Its servers are left out of the site's
              public lists ("who's playing", "online now", a player's card),
              where its players read as in game with the server hidden, as
              when a player hides which server; off the site's server board
              (the SERVERS page, /api/servers), though a server on servers.json
              stays in the game's own server list; and out of /find for
              anyone who is not a member (section 4).
 What someone who is not a member can still learn of a private community:
   * by its link, its name and how to get in, when it takes members (open
     or request) or the account has an invitation or a request in; with
     invite only and neither, the link answers as if there were no
     community;
   * that its members are in game (not where), if their own switches show
     it; their playtime still counts in their totals, without the server;
   * from inside one of its servers: the server itself, its players and
     everything a game server shows anyone, the community's tag on relayed
     lines and its announcements, and with members-only servers its name and
     short name in the kick message;
   * a server it has that is on h9web's servers.json stays on the site's
     server list (/api/servers is H9's own list, set by servers.json);
     leave such a server off servers.json, or set "listed": false there.

 Members-only servers (MEMBERS-ONLY SERVERS, off by default). The answer to
 each report from the community's servers names everyone who is not a member,
 and h9_presence kicks them through the same path a ban uses:
     This server is for members of Zion. Join at havoc9.org/community/?c=zion
 Turned away: players whose h9_clientid is no account's or no member's, and
 every player with no h9_clientid (a Steam client). The owner, the admins and
 H9's site admins always get in. h9_presence 1.2 or later lists players
 without an h9_clientid while the server is members-only (older ones do not,
 so those players would stay); turning it on makes the servers report at
 once, and anyone already on who is not a member is kicked then.
 WITHOUT THE PROOF SWITCH THE WHITELIST CAN BE FOOLED: an h9_clientid is the
 same on every visit and every player on a server can read it, so a copy
 passes as the member it was copied from. WHITELIST NEEDS PROVEN PLAYERS (off
 by default) lets in only games that proved the player id in the last 10
 minutes (docs\H9_PRESENCE.txt section 8), staff included: H9XASH with the ID
 proof (engine-h9-idproof.patch) on a server with h9_presence_challenge 1, and
 the web client, which its relay vouches for. An older H9XASH cannot prove and
 is turned away while the switch is on, so turn it on once the community's
 players have the H9XASH build with the proof.

 3. COMMUNITY CHAT
 -----------------
 In game: ".relay <text>" in say or say_team (h9_community_prefix sets the
 prefix). The line goes to every other server of the community and to its
 page, and shows here for everyone as the others see it:
     [Tag] Username: text
 From the site: the community's members (and H9's site admins) read its chat
 and write in it, in the chat box on its page; everyone else sees that it is
 there and the community's JOIN or REQUEST TO JOIN. The owner (and only the
 owner, or H9's site admins) may open it with CHAT OPEN TO EVERYONE: then
 every signed-in player reads and writes it, member or not, banned and muted
 accounts still kept out. A private community's chat stays its members'
 whatever the switch says. Off by default. A line shows in game as
     [Web] Username: text
 ".relay" in game does not need membership: anyone a server of the community
 lets in may relay (with a proven game, below), and those lines reach the site
 for its members to read.
 Announcements show as [Community name] text, and H9's as [H9] text.

 Who can relay from a game: a player whose h9_clientid is a havoc9.org
 account's (docs\H9_PRESENCE.txt, section 2) and whose game h9web has proven
 holds that account's player id (the green chain, a second or two after
 joining, so not in the first few seconds), while h9web has that account in
 game on that server by the server's own report, not muted or banned in the
 community or H9-wide. The line carries the account's username, not the name
 in game. A game that cannot prove is told why in chat and sends nothing: it
 keeps the server's own chat. With CHAT NEEDS PROVEN PLAYERS switched off by
 the community's owner, any game whose h9_clientid is an account's relays,
 except one whose h9_clientid another player on the server announces too (one
 of them is a copy), which relays only with a game h9web has proven: the
 plugin says so in chat and sends nothing, until only one game announces the id.

 What a line may hold: h9web cleans every line, and the plugin cleans what it
 shows again: no control characters, no Xash colour codes (^0 to ^9), % made
 a space (a client reads % in a chat line as a format), no # at the start, and
 white space run together; at most 120 characters (chatMaxChars). The plugin
 prints every line from h9web with "%s", never as a format string.

 Limits: one line every 2 seconds per account (chatCooldownSeconds, game and
 site together), 12 a minute per account (chatPerAccount, and chatWebPerAccount
 on the site), 60 a minute per server (chatPerServer); the plugin also keeps a
 player to one line every 2 seconds before asking. Over a limit the player is
 told to wait.

 Moderation: the community's staff delete a line on its page (it goes from the
 page and from what servers have not fetched yet; a line already shown in game
 stays on those screens) and MUTE its writer from there (section 5). The chat
 is kept 7 days (chatRetentionDays), then deleted.

 h9_community_chat 0 on a server shows none of the community's chat there and
 lets nobody relay from it; announcements still show.

 3a. THE DISCORD BRIDGE
 ----------------------
 H9's site admins may bridge a community's chat with one Discord channel, on
 the community's own page (DISCORD BRIDGE (H9 ADMIN): the channel's id, then
 BRIDGE; STOP ends it) or with PUT /api/presence/communities/<name>/discord
 { "channel": "<id>" or null }. It is H9's to give, not the community's: the
 bot posts as H9. Each change goes into the audit log. A channel serves one
 community.
   * Out: every line of the community's chat goes to the channel -- ".relay"
     lines from any of its servers, its page's chat, and its announcements --
     as
         **[Tag] Username:** text      (an announcement: **[Tag]** text)
     Discord's formatting in a line is taken literally (escaped), and nothing
     in it can mention anyone: the bot posts with every mention switched off
     (allowed_mentions empty; @everyone, roles and users alike) and without
     link previews. Lines that come together go in one message; the bot posts
     at most one message a channel every 1.2 seconds (relaySendMs) and keeps at
     most 50 lines waiting.
   * In: what people write in the channel goes to every server of the
     community and to its page, as
         [Discord] Name: text
     with the game chat's own cleaning (section 3: no colour codes, % made a
     space, at most 120 characters) and mentions written out as @name,
     #channel and @role. Bots' and webhooks' messages, the bot's own among
     them, and Discord's system messages are left out, so nothing comes back
     twice; a message with only an attachment shows as "(an attachment)". At
     most 30 lines a minute come in per community (discordInPerCommunity); a
     line more than 10 minutes old (h9web was down) is dropped, as are all
     lines while the community's chat is off. The channel is read every 3
     seconds (relayPollSeconds), from the last message relayed, kept across
     restarts.
   * Who can mute or ban a Discord writer: nobody in the community; they are
     not accounts here. The community's staff delete a [Discord] line on the
     page like any other, and Discord's own moderators keep the channel.
 What it needs, on Discord's side: H9's application (the discord module's,
 README.txt section 18; its bot token stays in that module's secrets file and
 nowhere else) in the server that has the channel, with View Channel, Read
 Message History and Send Messages there, and MESSAGE CONTENT INTENT switched
 on for the bot in Discord's developer portal (Bot, Privileged Gateway
 Intents): without it every message reads empty, and the page says "The
 channel does not answer: message_content_intent". The page shows H9's
 admins how the channel last answered (no_access: the bot cannot see or
 write there; no_such_channel: a wrong id; bad_token: the token).
 The bridge needs h9web's discord module loaded with its secrets file; the
 Discord account linking it also does is not needed for it.

 4. FINDING A PLAYER
 -------------------
 In game: "/find <name>" or "/where <name>" (".find" and ".where" too;
 h9_community_find 0 turns them off). The answer, to the asker only, for the
 exact username and up to four that start with what was typed, this
 community's players first:
     [H9] Neo is on HAVOC 9 RP -- to join, type in the console:
          connect 203.0.113.10:27015                   (one line in game)
     [H9] Neo is here.
     [H9] Trinity is in game.                         (she hides where)
     [H9] Tank is on havoc9.org. / is in the H9 web client. / is offline.
 Each account's own switches on its ACCOUNT page decide what shows
 (docs\H9_PRESENCE.txt, section 6), exactly as on the site. A private
 community's server shows only when the player asking is that community's
 member (h9_community 1.1 sends who asks, 1.2 only for a proven game: an
 announced id is not proof of being a member); to anyone else that player is
 "in game". A player is placed only by a proven game: an account whose only
 sighting on a server is a game that did not prove its player id (a copy of
 the id, say) reads as not in game, not on that server. A server cannot
 move a player to another server (section 9), so the address is given to
 type. One search every 5 seconds per player; 60 a minute per server.

 5. BANS, MUTES, KICKS AND ANNOUNCEMENTS
 ---------------------------------------
 On the community's page (staff), BANS, MUTES AND KICKS: a username, what,
 why and for how long.
   ban    kicked from every server of the community and kept out, until
          revoked or for 1 to 3650 days. A ban also follows the account's
          proven devices: another account playing from a device the banned
          account proved its id on is kicked too.
   mute   the account's chat goes nowhere: in game (h9_presence stops the
          player's say and say_team, and .relay) and on the site.
   kick   once: the account is kicked from the server it is on, if it plays
          on one of the community's servers within the hour.
 The reason (up to 60 letters, digits, spaces and . , : ! ? ( ) -) is what
 the kicked player reads: "Banned from Zion: griefing". Staff cannot sanction
 the owner, and only H9's site admins can sanction a site admin.

 How it reaches the servers: h9web asks each server of the community to
 report at its next poll (a second or so later), and the answer to that
 report names the players to kick and those muted (docs\H9_PRESENCE.txt,
 section 4b). The plugin kicks with "kick #<userid> <reason>". A banned player
 who joins later is kicked at the report after their join, about 3 seconds.

 H9's site admins do the same H9-wide on havoc9.org/community/ (H9 ADMIN): it
 holds on every enrolled server, in every community or none.

 Announcements: ANNOUNCE on the community's page sends a line to every server
 of the community and to its chat; H9's site admins send one to every
 enrolled server and every community's chat.

 Every sanction, revoke, announcement, deleted line and link is in h9web's
 audit log (docs\H9WEB_ADMIN.txt), with who did it.

 6. SHARED DATA FOR PLUGINS (H9_COMMUNITY.INC)
 ---------------------------------------------
 A community keeps a small store per account: named text values that every
 server of the community reads and writes for its players, so a roleplay
 server's money, a rank or a preference follows the player across the
 community's servers. A plugin uses it through include\h9_community.inc,
 with h9_community.amxx loaded:

   h9c_ready()                          in a community, and h9web answering
   h9c_server_id(out[], len)            this server's public id
   h9c_community(out[], len)            the community's short name
   h9c_get(id, key[], callback[], data = 0)
       public my_get(id, status, const key[], const value[], version, data)
   h9c_set(id, key[], value[], version = -1, callback[] = "", data = 0)
       public my_set(id, status, const key[], const value[], version, data)
   h9c_delete(id, key[], version = -1, callback[] = "", data = 0)
   h9c_find(name[], callback[], data = 0)
       public my_find(status, index, count, const username[], const state[],
                      const server[], const address[], same_community, data)
 and h9_presence's own: h9p_ready, h9p_server, h9p_server_id, h9p_api,
 h9p_sign, h9p_nonce, h9p_report_soon, h9p_muted.

 Each call returns at once: true when it went out (its callback will run),
 false when it could not (no live key, id not a player here with an
 h9_clientid, a bad key name, no callback for a read, a value over 1023
 bytes, or 24 calls already in flight, or, in a community that wants proven
 players, a player whose game has not proven the player id: h9p_account(id) is 0,
 as it is for the first second or two after a join). In the callback, id is 0
 when the player left before the answer came. A value is the account's, kept by
 the id the game announces; h9web ties the id to the account only for a proven
 game, and with DATA NEEDS PROVEN PLAYERS switched off it does not: do not give
 rights from such a value.

 status in a callback:
   H9C_OK          done
   H9C_NOT_FOUND   h9c_get: the key is not there (value "", version 0)
   H9C_CONFLICT    the version given is not the one there: value and version
                   are what is there now
   H9C_DENIED      no community, a read-only server, a banned account, or a
                   community that wants proven players and a game that has not
                   proven the player id
   H9C_LIMIT       a limit below, or too many calls a minute
   H9C_ERROR       havoc9.org did not answer, or not as expected
   H9C_NO_ACCOUNT  the player's h9_clientid is no account's
   H9C_NOT_HERE    h9web has not seen the player here yet: h9_presence
                   reports a player about 3 seconds after they join

 Limits (h9web's defaults, moduleSettings.presence):
   key        1 to 32 of a to z, 0 to 9, _ . -
   value      text, UTF-8, at most 512 bytes (dataValueMax); numbers as text
   keys       64 per account in each community (dataKeysPerAccount)
   store      200000 values per community (dataRowsPerCommunity)
   calls      per server 600 reads and 300 writes a minute
              (dataReadPerServer, dataWritePerServer); per account 60 writes
              a minute (dataWritePerAccount); a request at most 4 KB

 Conflicts: every value has a version, 0 while it is not there, then one
 more with each write. With version -1 a write goes over whatever is there:
 the last write wins. With the version read, it goes in only if nobody wrote
 since; otherwise H9C_CONFLICT brings what is there, to merge and write
 again. Use the version for anything two servers may change at once (a
 balance); -1 is fine for what one server owns (a preference).

 Latency: one HTTPS request a call; the callback runs 50 to 300 ms later as a
 rule, up to 15 seconds (the timeout, then H9C_ERROR) when havoc9.org is slow.
 Never wait for it inside a game event. Read a player's values once they are
 in (10 seconds after client_putinserver is safe), keep them in the plugin,
 and write a value when it changes, or at round end and on disconnect.

 An example (a balance kept with the version, so two servers never undo each
 other's change):

   #include <amxmodx>
   #include <h9_community>

   new g_money[33], g_ver[33];

   public client_putinserver(id)
   {
       set_task(10.0, "load_money", id);
   }

   public load_money(id)
   {
       h9c_get(id, "rp.money", "got_money");
   }

   public got_money(id, status, const key[], const value[], version, data)
   {
       if (!id)
       {
           return;
       }
       if (status == H9C_NOT_HERE)
       {
           set_task(10.0, "load_money", id);
           return;
       }
       g_money[id] = (status == H9C_OK) ? str_to_num(value) : 0;
       g_ver[id] = version;
   }

   save_money(id)
   {
       new v[16];
       num_to_str(g_money[id], v, charsmax(v));
       h9c_set(id, "rp.money", v, g_ver[id], "saved_money");
   }

   public saved_money(id, status, const key[], const value[], version, data)
   {
       if (id && status == H9C_OK)
       {
           g_ver[id] = version;
       }
       else if (id && status == H9C_CONFLICT)
       {
           // another server changed it since: take what is there now
           g_money[id] = str_to_num(value);
           g_ver[id] = version;
       }
   }

 7. THE TRUST MODEL: WHO CAN DO WHAT
 -----------------------------------
 A game server (whoever holds its key: the server, its host, anyone with its
 files)
   can   report the players it really has, under the names they use;
         relay chat for an account while that account is in game on it;
         read its own community's data, for any account (by username too);
         write its community's data for an account in game on it now,
         unless the server is read-only;
         find players; get a link code for itself.
   can't reach another community's data or chat; write data or relay chat
         for an account that is not in game on it; prove a player it does
         not have (it cannot make the challenge's proof without the player's
         raw id); sanction anyone; see any key, player id, device or IP.
   Note: a server can put words in the mouth of a player who is really on
   it, and write that player's data however it likes. CHAT NEEDS PROVEN
   PLAYERS and DATA NEEDS PROVEN PLAYERS make sure the player was really
   there; they cannot make sure the player typed the line. Link only servers
   you trust, and make a server read-only when it only needs to read.

 A member
   can   read and write the community's web chat; see its member list and,
         when it is private, its page and servers; leave.
   can't see requests or invitations, or change anything of the community.

 A community's admin (named by the owner)
   can   link servers (with a code from the server's console), set tags and
         read-only, unlink; change the settings (join mode, visibility,
         members-only servers among them); approve and refuse requests,
         invite, remove members; ban, mute and kick in the community;
         announce; delete chat lines; read the shared data's history.
   can't name admins, remove an admin, put data back, delete the community,
         switch a proof requirement off; sanction the owner or an H9 site
         admin; touch another community;
         see keys, player ids, devices or players' addresses.

 A community's owner
   can   all of the above; name and remove admins; put the shared data back
         to any time in the last 30 days; delete the community.
   can't touch another community, H9-wide sanctions or enrollment.

 H9's site admins
   can   everything above in every community; H9-wide bans, mutes, kicks and
         announcements; approve, revoke and block enrolled servers; read the
         audit log.

 Whoever runs the VPS: the database, and so everything; backups hold it too.

 A player: chats where not muted (on the site, in communities it is a member
 of), finds others, and decides with the switches on the ACCOUNT page what
 others see of them, on the site and through /find.

 A members-only server trusts the h9_clientid a player's game sends unless
 WHITELIST NEEDS PROVEN PLAYERS is on (section 2a): without it, membership
 keeps out the honest, not a copied id. The same holds for chat and shared data
 once their proof switches are off (section 2).

 8. HOW THE SHARED DATA IS PROTECTED
 -----------------------------------
   * Every call is signed with the server's own key: HMAC-SHA256 over the
     exact body, a time within 2 minutes of h9web's clock, and a one-time
     nonce h9web keeps for 10 minutes in its database (a restart forgets
     none). A forged, changed, stale or replayed call is refused.
   * Nothing in a call names a community. h9web takes the community from the
     server the key belongs to, so a server reaches only its own.
   * A write is only for a player in game on that server now: h9web maps the
     player's h9_clientid to the account with core's own index and checks the
     server's latest report has that account in game, with a game that proved
     the player id unless DATA NEEDS PROVEN PLAYERS is off. A read by the
     player's id asks the same. A banned account's data is not written.
   * Quotas and rate limits, per server and per account (section 6), sizes
     and types (a value is text or nothing), key names checked.
   * The owner (or an admin) makes a server READ-ONLY: it reads and cannot
     write.
   * Versions: a write can be made to fail if anything changed since it was
     read (section 6).
   * Every write is logged: the account, the key, the value before and
     after, both versions, the server that wrote it, and when; kept 30 days
     (dataLogRetentionDays). Staff read the log on the community's page
     (SHARED DATA); the owner puts every value, or one account's, back as it
     was at a time in those 30 days, and that too is logged and audited.
     h9web's daily database backup (docs\H9WEB_ADMIN.txt) is the rest of the
     safety net.
   * A key stops at once: an H9 site admin revokes or blocks an enrolled
     server (H9 ADMIN, ENROLLED SERVERS), presence-key.js removes a
     hand-made one, and unlinking a server cuts it off from its community.

 9. PORTALS
 ----------
 A portal is a ring on a map that leads to another server of the community.
 It is placed with a line in ts\mapconfigs\<map>.cfg, which h9_autoconfig
 runs once the map is up (docs\GAME_MODES.txt, section 4), the way spawns are
 placed for the match mode:

   h9_portal <tag|server id> <x> <y> <z> [yaw] [radius] [walk]

   tag | server id   the destination: its tag in this community, or its
                     public server id (quote a tag with a space in it)
   x y z             where it stands: a player's origin (36 units above the
                     floor), as amx_h9_portal_add records it
   yaw               which way the ring faces (default 0)
   radius            its size, 16 to 256 (default 48)
   walk              1: walking into it offers the trip too (default 0)

 for example
   h9_portal "RP 2" 1024 -512 100 90 48 0

 amx_h9_portal_add <tag|server id> [radius] [walk] (admins with the cfg flag)
 places one where the admin stands, facing where the admin looks, and prints
 its line to paste into the mapconfig; amx_h9_portal_list prints every
 portal's line. At most 16 portals a map.

 In game: the ring (sprites\tsm_zone_ring_0.spr, the uplink zones' ring,
 stood upright) shows only while the destination is one of the community's
 servers; a portal to an unknown tag, or to this server, is hidden. Near it a
 player sees its name and players ("HAVOC 9 RP / 5 / 16 players / Press E
 to travel"), refreshed with each poll. E, or walking in with walk 1, opens a
 confirm menu (1. Go, 2. Stay); after Go the player waits
 h9_community_portal_wait seconds (10) before the next. The ring is precached
 only for a map whose mapconfig has an h9_portal line, and only if the sprite
 is on the server (a missing precached file stops a map from loading). A
 Steam hlds server does not run mapconfigs, so it shows no portals.

 What moves a client: the player's own YES.
   * A server cannot connect a client by itself. FWGS registers connect with
     Cmd_AddRestrictedCommand, so it is CMD_PRIVILEGED, and
     Cmd_ShouldAllowCommand refuses every privileged command that comes from
     the server (stufftext), whatever cl_filterstuffcmd says. Steam's
     Half-Life filters server commands too, and GoldSrc has no "redirect"
     message for a server to send.
   * H9XASH and the H9 web client have h9_travel (engine-h9-travel.patch), a
     command any server may send, which only asks:
         h9_travel <a.b.c.d:port> [name]
     Their userinfo says they have it: _h9travel "1" (a key that starts
     with _ goes to the server only, never to the other players).
   * After Go the plugin sends h9_travel, with the address and the
     destination's name, to a client that says _h9travel "1", and puts the
     address in its console. The engine draws its own prompt over the game:

       Travel to HAVOC 9 RP?
       Address: 203.0.113.10:27016
       Offered by the server you are on: HAVOC 9 Siege, 203.0.113.10:27015
       This closes by itself in 15 s.
                                                  [ YES (Y) ]  [ NO (N) ]

     Y, Enter or a click on YES connects, from the engine's own command
     buffer, as if the player had typed connect. N, Esc, a click on NO, 15
     seconds, a new map or a disconnect drop it. The console key still opens
     the console. The prompt takes its keys before the game and any server
     menu see them, so a server can neither press YES nor answer for the
     player.
   * Every other client (Steam Half-Life, an older H9XASH, or cl_h9_travel
     0) is given the address to type: "[H9] HAVOC 9 RP is at
     203.0.113.10:27016 -- open the console (~) and type: connect
     203.0.113.10:27016", in chat and in the console.

 The engine refuses an offer, with an "H9 TRAVEL:" line in its console,
 when:
   * cl_h9_travel is 0 (the player turned offers off);
   * the address is not a plain IPv4 address and port: decimal octets
     without leading zeros, no names, no IPv6, a port from 1 to 65535;
   * it is a loopback, private, CGNAT or link-local address and the server
     the player is on is not itself on a LAN or the same machine (LAN play
     still works), or it is multicast or reserved;
   * another offer is up, the last one ended less than 10 seconds ago, or
     the server the player is on has made 4 offers in the last 120 seconds.
 An offer to the server the player is already on, or one that comes while
 the game is not in play or a demo is playing, is dropped silently.
 "Offered by" is the name the server gave itself at join (its hostname) and
 the address the game is connected to, which comes from the engine, not
 from the server. The name after "Travel to" is the server's word; the
 address under it is where YES goes.

 Players: cl_h9_travel 1 (the default; archived, and no server can set it)
 shows offers; 0 ignores them, with a console line for each, and sets
 _h9travel "0", so servers give the address to type instead.

 The web client shows the same prompt. Its connects go through havoc9.org's
 relay, which joins only H9's listed servers, so the page tells the engine
 which addresses it can reach: those on the SERVERS page (/api/servers) and
 the page's own JOIN links. For any other address the prompt says "The
 browser cannot reach this server: the web client joins only H9's listed
 servers." and offers only OK. Until the page has the list, a moment after
 it loads, the prompt offers YES and the relay refuses what it does not
 serve.

 Hosts set nothing. h9_community_travel 1 sends h9_travel after Go to every
 client, also to those without _h9travel "1" (they still get the chat line;
 an engine without the command prints that it is unknown). Leave it 0.

 10. LATENCY AND COST
 --------------------
 Each server keeps one call open to havoc9.org: a long-poll that h9web holds
 up to 20 seconds (pollHoldSeconds) and answers at once when there is
 something for it. The next one goes out a second after an answer, or after
 5 seconds to 5 minutes when havoc9.org did not answer (each failure waits
 longer). A server that is waiting for a key or an approval asks nothing.

   game to game     a line reaches the community's other servers in about
                    0.1 to 0.5 seconds, and at most about 1.5 seconds
   site to game     the same
   game to site     the chat box asks every 4 seconds while it is in view
   a sanction       a second or so to the poll, about 3 seconds more to the
                    report whose answer kicks
   portals, /find   the label's players are as fresh as the last poll (20
                    seconds at most); /find asks h9web each time

 Cost per server: about 3 small HTTPS requests a minute when nothing
 happens, one held connection on h9web, and one more request for each line,
 search or data call. On h9web, a waiting poll is a few hundred bytes of
 memory; 100 servers are 100 open connections through nginx. A chat line
 is one database row, kept 7 days.

 11. THE VPS
 -----------
 Nothing to install: communities are part of the presence module
 (h9web\modules\presence); migration 2 makes their tables on the first start
 after an update. Check:
   * nginx's /api/ location keeps proxy_read_timeout 30s or more
     (havoc9.org\deploy\nginx-setup.sh does): pollHoldSeconds (20) must stay
     under it. nginx's own limit, 10 requests a second per address with a
     burst of 60, covers a server's calls; servers sharing one address share
     it.
   * config.json "trustProxy": true behind nginx (as deployed), so h9web
     sees a server's real address: enrollment checks it (enrollSameIp).
   * The VPS may send UDP out to the game servers' ports: that is how h9web
     reads an enrolling server's rules (A2S_RULES).
   * The site page: havoc9.org\community\index.html with
     havoc9.org\assets\community.js, deployed with the rest of the site.

 Settings (moduleSettings.presence; all have defaults):
   pollHoldSeconds 20, chatMaxChars 120, chatRetentionDays 7,
   chatCooldownSeconds 2, dataValueMax 512, dataKeysPerAccount 64,
   dataRowsPerCommunity 200000, dataLogRetentionDays 30,
   communitiesPerAccount 3, claimMinutes 15
   limits: serverCallsPerIp, pollPerServer, chatPerServer, chatPerAccount,
   chatWebPerAccount, findPerServer, dataReadPerServer, dataWritePerServer,
   dataWritePerAccount, claimPerServer, communityPerAccount,
   membershipPerAccount, invitePerAccount
 Enrollment's own settings are in docs\H9_PRESENCE.txt, section 3.

 12. THE API
 -----------
 Game servers (signed; h9_community.sma makes these calls):
   POST /api/presence/server/poll      { since, hold }   the long-poll
   POST /api/presence/server/chat      { id, text }      a relayed line
   POST /api/presence/server/find      { q, id }         where an account is
                                       (id: the asker's h9_clientid, optional)
   POST /api/presence/server/data/get  { id | account, keys }
   POST /api/presence/server/data/set  { id, key, value, version }
   POST /api/presence/server/claim                       a link code
 Each body is { "v": 1, "server": "<ip:port>", "ts": <unix seconds>,
 "nonce": "<16 to 64 hex>", ... }, with X-H9-Server: <ip:port> and
 X-H9-Signature: <hex HMAC-SHA256 of the body with the server's key>.
 A call about a player by h9_clientid is refused 403 unverified when the
 community wants proven players (chat, and data by id) and the game did not
 prove the id; the poll's answer names the community with chatProof and
 dataProof, so the plugin can say why before it asks. /find's id is the
 asker's, and counts only for a proven game.
 The site (signed in; staff = the owner, its admins and H9's site admins):
   GET    /api/presence/communities
   POST   /api/presence/communities                 { slug, name }
   GET    /api/presence/communities/<slug>
   PATCH  /api/presence/communities/<slug>          { name, chat, chatProof,
                     dataProof, joinMode, visibility, whitelist,
                     whitelistProof }                               staff
                     { chatOpen } as well                           owner
   DELETE /api/presence/communities/<slug>          { confirm }     owner
   POST   /api/presence/communities/<slug>/claim    { code, tag }   staff
   POST   .../servers/<serverId>   { tag, readOnly }   DELETE (unlink)  staff
   POST   .../staff  { username }   DELETE .../staff/<username>        owner
   GET    .../sanctions   POST .../sanctions { username, kind, reason, days }
   POST   .../sanctions/<id>/revoke                                     staff
   POST   .../announce { text }                                         staff
   GET    .../chat?since=<id>   POST .../chat { text }          members
                     (every signed-in account while chatOpen, not private)
   POST   .../join   (join, ask, or take an invitation)   POST .../leave
   POST   .../invitation/decline                            signed in
   GET    .../members  (staff also get requests and invites)    members
   POST   .../requests/<username>/approve | refuse              staff
   POST   .../invites { username }   DELETE .../invites/<username>   staff
   DELETE .../members/<username>                                staff
   DELETE .../chat/<id>                                                 staff
   GET    .../data/log?username=                                        staff
   POST   .../data/rollback { to, username }                            owner
 H9's site admins:
   GET  /api/presence/admin/servers?status=all|pending_approval|active|
        pending_proof|blocked
   POST /api/presence/admin/servers/<serverId>/approve | revoke | block |
        unblock | flags/resolve
   GET  /api/presence/admin/sanctions   POST /api/presence/admin/sanctions
   POST /api/presence/admin/sanctions/<id>/revoke
   POST /api/presence/admin/announce  { text }
   PUT  /api/presence/communities/<slug>/discord  { channel: "<id>" | null }
        the Discord bridge (section 3a); the page's answer then carries
        discordChannel and discordStatus for H9's site admins

 14. TROUBLESHOOTING
 -------------------
 h9_community_status says "key not live"
   - h9_presence_status says why: not enrolled (h9web cannot reach the server
     over UDP: a LAN or NAT server stays so), waiting for an H9 admin, or no
     key at all on a listen server. docs\H9_PRESENCE.txt, section 12.
 "havoc9.org: not answering"
   - HTTP 0: the server cannot reach havoc9.org (DNS, firewall, the
     AmxxEasyHttp module or its CA bundle missing).
   - 401 stale: the server's clock is more than 2 minutes off: fix NTP.
   - 401 bad_signature or 403 no_key: the key changed or was revoked;
     h9_presence enrolls again by itself.
 "community: none"
   - Link it (section 2). A code that "is wrong or has run out": ask the
     console for a new one (h9_community_claim new).
 ".relay" says "havoc9.org has not seen you on this server yet"
   - Wait a few seconds after joining; and the player's game must send the
     account's player id (docs\H9_PRESENCE.txt, section 2).
 ".relay" says "Community chat needs a game havoc9.org has proven is yours"
   - The game has not proven its player id: link it (.link, or Link your
     Account in the main menu), and wait a few seconds after joining. A
     Steam client and an H9XASH from before the proof cannot; the server's
     own chat still works for them. "...asks no game to prove its account"
     means the server has h9_presence_challenge 0: nobody is proven there,
     so .relay is off until it is 1 (or the community's owner switches
     CHAT NEEDS PROVEN PLAYERS off).
 A portal does not show
   - Its tag or server id must be one of the community's other servers
     (h9_community_status counts the portals "leading somewhere"); the
     mapconfig must have the line, on an H9XASH server (Steam hlds runs no
     mapconfigs); the ring needs sprites\tsm_zone_ring_0.spr on the server.
 Go shows no travel prompt (H9XASH or the web client)
   - The player's console says why, on an "H9 TRAVEL:" line: cl_h9_travel
     0, not a public address (a portal to a LAN address works only from a
     LAN server), too soon after the last offer, or 4 offers from this
     server in two minutes. No such line and the address in chat: that game
     has no h9_travel (Steam, or an H9XASH from before it).
   - In the web client, "The browser cannot reach this server": the
     destination is not one of H9's listed servers (the SERVERS page).
 A plugin's h9c_ call returns false
   - No live key, the player has no h9_clientid, a key name with capitals or
     spaces, 24 calls in flight, or a player whose game has not proven the
     player id (h9_community_status says whether the community asks for it).
