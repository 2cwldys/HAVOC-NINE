===============================================================================
 PLAYER LIMIT 128: BUILT FOR 128 SLOTS, RUN AT 64
===============================================================================

 Who this is for: whoever decides whether H9 servers go past 32 players, and
 whoever then does the work. It began as research and a plan, describing the
 tree as it stood on 2026-11-01; section 27 records what has been built since.
 File:line references are into D:\Downloads\TSM unless they say otherwise.

 The short version
   * Where it stands, 2026-11-02: built for 128 slots, running at 64. The
     engine, reTS's client and server, Metamod-R, AMX Mod X with H9's TSX,
     every plugin and RCBot (127 bot profiles) all take 128 slots; the server
     launchers and the Create Game menu default to maxplayers 64. Load tests
     at 64 slots with 63 bots ran clean, without AMX Mod X and with it (TSX
     checks 39 of 39), and a bot kicked from slot 48 fires client_disconnected
     and client_remove (2026-11-02, ts_bikini, every slot full). Not yet proven:
       - a server past 64 slots (no test has run there);
       - a human joining a full 64-slot match: the staggered bot join and the
         engine's reliable-burst fix are built, not yet played;
       - a full server's presence report: until 2026-11-02 h9_presence held
         12 KB (about 40 players) and h9web took 16 KB; both now hold all 128
         slots (H9_PRESENCE.txt), live with the next build and site restart;
       - 32 spawn points a side on every map that runs at 64.
   * The plan: build every limit, protocol field and array for 128 slots, and
     run servers at maxplayers 64. The default went to 64 on 2026-11-02, on
     the user's word, ahead of the checklist in section 23 (its change set
     says what moved).
   * Before this work nothing in H9 could run more than 32 players:
       - the engine clamps maxplayers to 32 (xash3d-fwgs engine\server\
         sv_init.c:822-823);
       - lift that clamp alone and AMX Mod X writes past its own 33-entry
         player table the moment someone takes slot 33 (AMXMODX amxmodx\
         meta_api.cpp:72, 922-924);
       - reTS's own slow-motion code writes past a 32-entry table in every
         player (dlls\ts_player.cpp:234-256).
   * It touches every binary H9 ships: the engine, its renderers and menu,
     reTS's client and server, Metamod, AMX Mod X and its modules, TSX, every
     plugin, RCBot; plus configs, map spawn points and the scoreboard. All of it
     is source H9 has (mp.dll included: since 2026-10-29 it is built from reTS
     source; Metamod-R too: TSM\metamod-r, section 7), except reTSX and the AMX
     Mod X core, which come prebuilt from goldsrc-net's fork (section 8.5).
     Expect a period of chasing bugs: bots make most of it testable (section
     19). What is built so far: section 27.
   * Compatibility: a server of 32 slots or fewer behaves exactly as now, for
     every client. Only a server with more than 32 slots needs the new client;
     older and stock Xash clients never list it and cannot join it (cleanly).
   * Performance is the real question. At 64 the server does about four times
     the per-viewer entity work of 32 (twice the viewers, each seeing about
     twice the players), mostly through one path that also runs two Pawn hooks
     per entity per client update. The game simulation cannot be threaded
     (mp.dll, Metamod and AMX Mod X all assume one thread). Order: measure,
     cut single-threaded costs, and thread only the engine's own per-client
     packet encoding, and only if still needed (section 18).
   * Memory: the server is a 32-bit process, large-address-aware since
     2026-11-02: 4 GB on 64-bit Windows, not 2. One table alone is 340 MiB at
     64 slots. Options in section 13.
   * Rough effort to a 64-slot default: 4 to 6 weeks, including testing and a
     first round of single-threaded performance work. Threading, if needed, is
     2 to 3 weeks more.

 2. THE PLAN: BUILT FOR 128, RUN AT 64, DEFAULT 32 UNTIL THE END
 ---------------------------------------------------------------
 Build for 128. Every constant, array, protocol field and bit width is made for
 128 slots:
   * the engine: MAX_CLIENT_BITS 7;
   * reTS: MAX_PLAYERS 128, MAX_PLAYERS_HUD 129;
   * Metamod and AMX Mod X: MAX_PLAYERS 128, and amxconst.inc for the plugins;
   * the plugins: their tables sized from it;
   * RCBot: MAX_PLAYERS 128;
   * delta.lst: iuser2 at 8 bits;
   * the wire: slot numbers as whole bytes.
 Building for 128 costs almost nothing at run time. The large costs (memory,
 bandwidth, CPU) follow the run-time maxplayers, not the build constant, and
 the wire format only changes on a server with more than 32 slots. And it means
 every binary is rebuilt and every client rolled out once, not again on the
 way to 128.

 Run at 64. Servers that go past 32 run maxplayers 64. Raising a server past 64
 is a separate, later decision, made on measurements (section 21).

 The default is 64 (2026-11-02, the user's call, ahead of section 23's
 checklist): H9XASH's server launchers and the Create Game menu start at 64.
 The checklist stays the list of what has to hold for matches past 32.

 The steps (effort in section 22):
   0. Measure today's 32-slot server with bots (section 19, L0).
   1. Engine, renderers, menu, launcher exe: built for 128. Ship H9XASH and the
      web client while servers stay at 32.
   2. reTS mp.dll and client.dll built for 128, including the memory bug, the
      2048-entity cap, the scoreboard and assists. Ship them.
   3. Server side: Metamod, AMX Mod X and its modules, TSX, every plugin, RCBot,
      all built for 128.
   4. Bot load tests at 64 on a test server (section 19).
   5. Single-threaded performance cuts, then steps 4 again (section 18).
   6. Tests that need real clients (section 20).
   7. Only if still needed: the threaded packet encode (section 18.5).
   8. The switch: the default goes to 64 (section 23).

 5. THE ENGINE (XASH3D-FWGS)
 ---------------------------

 5.1 The constant
 MAX_CLIENT_BITS 5 and MAX_CLIENTS (1<<MAX_CLIENT_BITS) are in common\
 xash3d_types.h:20-21; the comment calls 32 the "int32 limit" (the voice mask
 of 5.3). mainui keeps its own copy (3rdparty\mainui\sdk_includes\common\
 xash3d_types.h:20-21). sv_init.c:822-823 bounds maxplayers by it. Arrays sized
 by it: engine\client\client.h:64, 232, 622; engine\client\voice.h:96, 99;
 engine\server\server.h:340; sv_client.c:1374-1375; ref\gl\gl_studio.c:111;
 ref\soft\r_studio.c:103. All follow the constant.

 5.2 The two wire messages that carry a slot
 svc_updateuserinfo writes the slot in MAX_CLIENT_BITS bits (sv_client.c:1303),
 svc_pings one per player (sv_frame.c:504), and the client reads both at the
 same width (cl_parse.c:1371, 1483). Two traps:
   * The GoldSrc protocol path (Steam HLDS through the broker) calls the same
     CL_UpdateUserPings (cl_parse_gs.c:620-622), and GoldSrc sends 5 bits.
   * The width cannot follow svc_serverdata's maxclients. The server copies its
     reliable broadcast, which carries other players' userinfo
     (sv_frame.c:728, sv_client.c:715), to every client at cs_connected or
     later (sv_frame.c:779-786), including one not yet sent svc_serverdata.
 Recommended: two new, self-describing H9 messages (an H9 userinfo update and
 H9 pings, with the slot as a full byte), on two svc numbers protocol.h marks
 reserved (27-29, 54-55), sent only by a server with more than 32 slots.
   * A server of 32 or fewer sends exactly today's bytes.
   * A new client reads both forms.
   * An old client never meets the new ones: it is refused first (5.6).
   * Demos stay readable: every message says its own width.
 Caveat: if FWGS upstream later assigns those numbers, the patch conflicts at
 the next rebase. That is visible, not silent.

 5.3 The voice mask
 Each client's "who hears my voice" is a uint (server.h:228), all ones at
 connect (sv_client.c:511), tested with BIT(i) when routing (sv_client.c:3666),
 set through the game DLL's Voice_Get/SetClientListening (sv_game.c:4538,
 4555-4556). BIT(n) is 1U << (n) (xash3d_types.h:83). For i of 32 or more the
 shift is past the type's width: undefined in C, on x86 it wraps, so slot 40
 shares slot 8's bit. Make it a bit array of MAX_CLIENTS bits (four uint32)
 with helpers at those four places.

 5.4 Delta fields
   * engine-h9-deltabits.patch widens entity_state_t.owner and
     entity_state_player_t.owner to MAX_CLIENT_BITS + 1 when delta.lst is
     parsed (patch lines 33 and 38): 8 bits at 128. It follows the constant.
   * delta.lst:70 sends clientdata_t.iuser2 in 6 bits. reTS puts the
     spectator's target there (dlls\observer.cpp:77, 168; client.cpp:1989),
     and on death the inflictor's index (player.cpp:974). Past 63 the value is
     pinned to 63, so in-eye spectating of slot 64 shows slot 63. Make it 8
     bits, or 13 to carry an inflictor's index too. The server sends its parsed
     tables, so every client follows.

 5.5 Things that look like limits and are not
   * pmove: players go into physents, with room kept for every slot
     (cl_pmove.c:450: MAX_PHYSENTS - maxclients, 472 left at 128).
     MAX_MOVEENTS is for ladders (cl_pmove.c:437). pmove_t, shared with both
     game DLLs, does not change.
   * MAX_GOLDSRC_EDICTS (protocol.h:313) is BIT(13) + MAX_CLIENTS * 15: 10,112 at
     128, past MAX_EDICTS. It only caps GoldSrc servers (cl_parse.c:842), which
     never pass 32. Pin it to 32 * 15.
   * The renderers bound by the run-time maxclients (gl_studio.c:2378-2381):
     ship xash.dll, ref_gl.dll, ref_soft.dll and menu.dll as one set (xash.bat
     builds them together). ref_client_t (engine\ref_api.h:190-201) holds no
     player arrays, so REF_API_VERSION stays.
   * Client-side player queries are bounded by cl.maxclients
     (dll_int\cl_game.c:1874-1880), so client DLL loops past the real slot count
     are harmless.

 5.6 Listing, connecting, refusing
 An old client (MAX_CLIENTS 32) and a server with more than 32 slots:
   * The Internet tab drops the server (cl_main.c:2236, 2345), and presence
     with it (:2239).
   * A typed "connect": svc_serverdata fails the client's own check, which
     prints "invalid playernum or maxclients" and disconnects
     (cl_parse.c:869-876). No crash.
 Recommended: the new client says it takes more than 32 (a bit in the connect
 "ext", added to the mask at sv_client.c:506; protocol.h:283-284; client side
 cl_main.c:1431). A server past 32 refuses any client without it through
 SV_RejectConnection, naming the build and havoc9.org/downloads.

 5.7 The patch chain
 One new tracked patch, engine-h9-maxclients.patch, and
 mainui-h9-maxclients.patch for the submodule, made from the full-chain state
 and registered last in xash.bat (its list is :108-136).
   * cl_main.c and client.h already carry hunks of the cloak, spraypicker,
     spraycmd, userid and presence patches.
   * engine-h9-presence.patch has `if( maxcl > MAX_CLIENTS || ...` as a context
     line (patch line 6). Changing the constant's value leaves that text alone;
     do not edit that line.
   * Verify forward and reverse, add a PATCH_CHANGELOG.md entry, back files up
     first (TSM\CLAUDE.md).
 Browser: robocopy the tree into webclient-build\xash3d-fwgs
 (havoc9.org\webclient\DEPLOY.txt:116), rebuild with emsdk, and serve it so no
 browser keeps the old engine cached.


 6. THE GAME DLLS (RETS MP.DLL AND CLIENT.DLL)
 ---------------------------------------------

 6.1 The constant
 dlls\cdll_dll.h:22, constexpr int MAX_PLAYERS = 32, is shared by mp.dll and
 client.dll. game_shared\voice_common.h:13, 15 derive VOICE_MAX_PLAYERS_DW and
 CBitVec<MAX_PLAYERS> from it.
   * The server's voice manager is written for any size, but caps itself at
     min(MAX_PLAYERS, maxClients) (voice_gamemgr.cpp:101): today slots past 32
     get no voice at all.
   * VoiceMask grows to 32 bytes (:104), a [rules, ban] pair per dword
     (:255-260).
   * pm_shared.cpp:133 and :1773 (rgStuckLast, rgStuckCheckTime) are indexed
     by player (:1709, :1821). Past 32 they are written beyond their end.
 All three are settled by the constant.

 6.2 The 2048-entity cap
 reTS's AddToFullPack refuses any entity with index MAX_EDICTS or more
 (dlls\client.cpp:1320-1323), and reTS's MAX_EDICTS is 2048
 (common\com_model.h:15). The comment explains it: GoldSrc sends entity numbers
 in 11 bits. Xash sends 13 (protocol.h:116), and H9's max_edicts is 4098.
   * At 64 slots on New Byzantium the world, 64 players and 64 icons, and about
     1,450 map entities reach about 1,580 before a shot is fired.
   * Late entities (weapons, grenades, corpses, drops) can then cross 2047 and
     are never sent: invisible to everyone.
 Fix: compare against the engine's real limit (gpGlobals->maxEntities), so
 GoldSrc keeps its 2048 and Xash gets its 8192.

 6.3 Two asserts that stop a plain constant change
   * dlls\triggers.cpp:925 static_assert(MAX_PLAYERS <= 32). trigger_hurt keeps

 11.7 The avatar cell, and how its picture arrives
 Every player row starts with a square cell one row high (12 units, as wide
 in pixels as the row is tall). It shows a default silhouette for everyone,
 drawn by the client (CAvatarBitmap, cl_dll\vgui_ScorePanel.cpp). The client
 keeps a picture field per slot, g_PlayerAvatars[slot]: RGBA pixels, size,
 version, and the bitmap drawn at the cell size. A picture drops in there
 without another layout change. The pipeline, not built:
   1. The server learns whose account a player is: the presence ID proof
      ties the slot to a havoc9.org account. Pieces: the engine (the proof,
      an engine change not built yet) and h9_presence.sma (it already sends
      the challenge, takes the answer and reports to h9web).
   2. h9web knows each account's picture and its version (the forum's
      profile pictures, re-encoded on upload) and serves each as a small PNG
      (64 x 64) at a URL that carries the version.
   3. The server tells clients which picture each slot has: an H9 user
      message, slot, version and account id. The client builds the
      havoc9.org URL itself, so no server can point clients at another host.
      Piece: h9_presence.sma sends it, from h9web's report answer.
   4. The engine fetches the PNG over https from havoc9.org only, size-capped
      (a few KB, 64 x 64 at most), and caches it on disk by account and
      version, so each picture is fetched once. The engine already has the
      parts: HTTP_GetToMemory with mbedTLS and its caps (engine-h9-motd.patch
      uses them) and imagelib's PNG decoder. Piece: the engine, with a client
      extension call that hands client.dll the decoded RGBA by slot.
   5. The client draws it: g_PlayerAvatars[slot] takes the pixels and
      version; the scoreboard scales them to the cell (a box filter over the
      silhouette's background). Piece: reTS cl_dll.
 Steam/GoldSrc clients (the GoldSrc package on HLDS) never get pictures: the
 GoldSrc engine has none of steps 1 and 4. They always show the silhouette.
 The cache: downloads\h9avatars\<site>_<account>_<version>.png, <site> havoc9, or
 local<port> while cl_h9_site names the local test site, so the two never mix. A
 picture that fails says so once in the console (its address, and whether it could
 not be fetched or was not a PNG of 64 x 64 at most) and is not asked again until the

 13. MEMORY: THE 32-BIT ADDRESS SPACE
 ------------------------------------
 sv_init.c:838-839 allocates svs.clients and one ring of packet entities,
 maxplayers x MULTIPLAYER_BACKUP (64) x NUM_PACKET_ENTITIES (256) x 340 bytes
 (netchan.h:75, 79: "170 Mb for multiplayer with 32 players"): 170 MiB at 32
 slots, 340 at 64, 680 at 128, in one block. Each slot also has two
 NET_MAX_MESSAGE netchan buffers and a 16 KB datagram, about 400 KB a slot.
 HAVOC 9.exe, which h9xash_server.bat runs with -dedicated, is a 32-bit PE
 without IMAGE_FILE_LARGE_ADDRESS_AWARE (characteristics 0x0102); no wscript
 sets it. So the server has 2 GB, with New Byzantium's 46 MB BSP, the DLLs,
 AMXX and RCBot in it. engine-h9-phsbudget.patch exists because that map once
 ran a 32-bit listen server out of memory.

 The options:
   a. Nothing, at 64. 340 MiB should fit. Measure private bytes and the largest
      free block with 63 bots on New Byzantium (section 19).
   b. Large address aware. /LARGEADDRESSAWARE on HAVOC 9.exe (a link flag in
      game_launch's wscript) gives 4 GB on 64-bit Windows.
      Risk: code that treats a pointer, or the difference of two pointers, as
      a signed int. On 32-bit Xash a string_t is the string's address minus a
      static "" (sv_game.c:3135), so a string allocated above 2 GB gives a
      negative string_t. Any `> 0` or `< 0` test on one, in mp.dll, AMXX,
      RCBot or a plugin, then misbehaves.
      Test: on a test PC only, set Windows' top-down allocation
      (AllocationPreference) so high addresses come first, then run the full
      chain with bots on every mode.
   c. A smaller ring. NUM_PACKET_ENTITIES 128 on the server (or a cvar sizing
      svs.num_client_entities) halves it: 170 MiB at 64.
      Safe by construction: a delta base that has rolled off the ring is
      detected and a full update sent instead (sv_frame.c:244-252).
      Risk: more full updates (bandwidth spikes) when many entities are in
      view; count "delta request from out of date entities" (-dev) in the bot
      runs.
      Do not touch MULTIPLAYER_BACKUP: it is the client's frame history too
      and tied to the protocol (netchan.h:75, 83-88).
   d. A 64-bit server: not available. mp.dll, Metamod, AMXX and RCBot are
      32-bit Windows DLLs. reTS builds amd64 for Linux, but AMXX and RCBot do
      not.
 Recommended: (a) at 64, (c) if tight, (b) after its own test. Past 64, (b)
 and (c) both.
 Decided and built: (c), in engine-h9-slots128.patch: past 32 slots the
 ring holds NUM_PACKET_ENTITIES / 2 a frame, 170 MiB at 64, 340 at 128; at
 32 or fewer it is as before. And (b), on the user's word (2026-11-02):
 engine-h9-largeaddress.patch links HAVOC 9.exe /LARGEADDRESSAWARE. A scan
 of reTS, Metamod-R, AMX Mod X, RCBot and the plugins found no signed test
 on a string_t or a pointer on a live path (the patch's PATCH_CHANGELOG.md
 entry has the two near misses).
 An in-process high-address stress (the free address space below 2 GB reserved,
 then a map change) could not run on the build PC: Avast's behaviour shield
 quarantines a test server a script starts (IDP.Generic). The top-down test on a
 spare PC, above, stays the check.


 14. AROUND THE GAME
 -------------------

 The h9web relay
   * One UDP socket, on its own port, per engine socket (h9web\lib\relay.js:
     107, 121).
   * Caps: 512 sockets in all, 12 per IP, 4 per account (config.js:58-69).
     Enough for 64 browser players.
   * Only page-to-server traffic is rate-limited (relay.js:143); server-to-page
     is bounded by 1 MiB of backpressure a socket. 64 browser players at 30 to
     60 KB/s is 2 to 4 MB/s of egress through one Node process and nginx.
 The game server's per-address rules. Every browser player arrives from the
 relay's one address (or 127.0.0.1 on the same box, servers.example.json), and
 NET_IsLocalAddress is true only for the engine's internal loopback
 (engine\common\net_ws.h:82-85). So all of them share:
   * sv_connect_max_per_ip, default 3 (sv_main.c:158; sv_client.c:466);
   * sv_query_rate_limit, default 1 (sv_main.c:157);
   * one challenge and one connect a second per address, a burst of 5, not a
     cvar (sv_client.c:944-990).
 DEPLOY.txt:340-372 and H9WEB_ADMIN.txt:211-212 already say
 sv_connect_max_per_ip 0, sv_query_rate_limit 30, sv_timeout 120. After a server
 restart, 64 browser players rejoin over about a minute because of the fixed
 connect bucket. A map change makes nobody reconnect.

 The server list bot, the website and h9web
 They read A2S_INFO only, counts as bytes (serverlist-bot\h9_serverlist.py:
 110-121; h9web\lib\servers.js:171-191; havoc9.org\servers\index.html:183).
 Fine to 255.

 A2S
   * INFO counts are bytes (sv_query.c:46-48).
   * PLAYERS is about 41 bytes a player in one 8,188-byte buffer
     (sv_query.c:127-171; common.h:135): 2.6 KB at 64, 5.3 KB at 128.
   * It goes as one datagram, never split (net_ws.c:1455-1460, 1582-1585), so
     it is IP-fragmented, and some NATs and firewalls drop fragments: a
     tracker may see no player list.
   * It is on: sv_expose_player_list 1 (config.cfg:289).

 Discord presence
 It takes numcl and maxcl from the same info reply (engine\client\
 cl_presence.c:445-447), after the client's MAX_CLIENTS filter
 (cl_main.c:2236-2239). New clients show 64-slot servers.

 The browser build
 Both the engine (DEPLOY.txt:116) and reTS's wasm client (:156-159) are rebuilt
 and served fresh.


 15. COMPATIBILITY
 -----------------
   new client -> any server of 32 slots or fewer (old H9, stock FWGS, new H9):
                 works; the bytes are unchanged
   new client -> Steam HLDS through the broker: unchanged (GoldSrc keeps 5 bits)
   new client -> an H9 server of 33 to 128 slots: works
   old H9XASH or stock FWGS client -> a new server of 32 or fewer: works
   old or stock client -> a server past 32: not listed (cl_main.c:2236);
                 refused at connect, with the server's message (5.6) or its
                 own (cl_parse.c:869-876). No crash.
   Steam GoldSrc client -> any Xash server: never (protocol 48 against 49,
                 "STEAM validation", docs\NETWORKING.txt)
   H9's GoldSrc package on HLDS: stays at 32; the 128-built reTS DLLs work
                 there (6.8)
   demos recorded past 32: replay only in the new client
   mixed DLLs: xash.dll, ref_gl.dll, ref_soft.dll, menu.dll and client.dll ship
                 as one set (5.5)
 Ship the client well before any default changes (steps 1 and 2), so most
 players already list and join 64-slot servers when they appear.


 16. NETWORK LOAD AT 64
 ----------------------
   * H9's shipped client config: cl_updaterate 20, cl_cmdrate 30, rate 25000
     (H9XASH\ts\config.cfg:130, 91, 260). The engine allows rate up to 100,000
     (netchan.h:33); sv_maxrate 0 means no server cap (sv_main.c:40).
   * A moving player's delta is about 20 to 30 bytes an update. Forty in view
     at 20 updates a second is 16 to 24 KB/s of player state alone. Rate 25000
     chokes in a big fight.
   * For 64-slot servers: rate 50000 to 100000, sv_minrate about 20000,
     cl_updaterate 30 or more.
   * Server upstream: 64 x 40-100 KB/s is 2.5 to 6.4 MB/s (20 to 50 Mbit/s).
   * New Byzantium has no PHS (engine-h9-phsbudget.patch), so every sound and
     PAS message goes to every player: that grows with the square of the
     player count.
   * Each joiner gets everyone's userinfo and score messages (11.4) and every
     player's spray (sv_send_logos 1, sv_uploadmax 0.5 MB each,
     sv_main.c:51-57).

 The numbers for a server of more than 32 slots (decision 9):
   * clients: rate 60000, cl_updaterate 30, cl_cmdrate 30;
   * server: sv_minrate 20000, sv_maxrate 100000, sv_minupdaterate 20,
     sv_maxupdaterate 60;
   * upstream: 64 players at about 60 KB/s is 3.8 MB/s (31 Mbit/s); plan for
     50 Mbit/s with joins, sprays and fights;
   * relay egress for browser players: about 60 KB/s each.
 They go into the 64-slot server's own config; the defaults stay as they are
 (rate 25000, cl_updaterate 20) until section 23.


 17. WHERE THE FRAME TIME GOES
 -----------------------------
 The Xash dedicated server is one thread, at sys_ticrate 100
 (engine\common\host.c:69). Each frame, in order:

   a. Reading packets: each real client's usercmds run pmove in the game DLL
      (with PlayerPreThink and PostThink, through Metamod and AMXX). Lag
      compensation moves every other client back and restores him for each
      command (sv_pmove.c:680-698, 836-850): the square of the player count
      times cl_cmdrate.
   b. The game frame: pfnStartFrame, through Metamod and ts_matchmode's two
      StartFrame hooks, which loop over players (ts_matchmode.sma:5437-5454).
      Then physics and thinks over every entity (sv_phys.c:123) in mp.dll.
      Every TraceLine and Touch goes through ts_matchmode's post-TraceLine and
      Touch hooks (:5116, :5119). fw_prethink is 838 lines of Pawn, run for
      every player every frame (:17396-18234). No per-player hook loops over
      all players, so there is no N-squared Pawn loop.
   c. Sending, for each real client due an update (cl_updaterate a second):
        - pfnSetupVisibility;
        - then pfnAddToFullPack for EVERY entity index 1 to numEntities, free
          or not, with no culling of the engine's own (sv_frame.c:56-160).
          Each call runs ts_matchmode's two Pawn hooks around reTS's
          AddToFullPack (ts_matchmode.sma:5073-5074; bodies :5627, :5710),
          which then culls by PVS itself (reTS dlls\client.cpp:1314-1380);
        - pfnUpdateClientData and weapon data;
        - delta encoding against the client's acknowledged frame
          (SV_EmitPacketEntities). For every entity new to the view, a search
          of up to MAX_CUSTOM_BASELINES earlier states for the cheapest
          baseline (sv_frame.c:170-222), each test a full size computation
          calling the game DLL's encoder (net_encode.c:499-508);
        - Netchan_Transmit.
   d. Sounds, temp entities and events: without a PHS (New Byzantium) they go
      to every client.
   e. RCBot's thinks, traces and navigation per bot per frame.

 Estimate for (c), AddToFullPack calls a second = clients x updaterate x entity
 indexes:
   * New Byzantium today at 32: 32 x 20 x 1,600, about 1 million;
   * at 64: 64 x 30 x 1,800, about 3.5 million.
 Each is two Pawn calls. Per-call costs were not measured here; this is the
 term most likely to fill the one core. The engine has `stats` (CPU, in, out,
 FPS; sv_cmds.c:859-888) and `edict_usage` (:1320), but no per-phase timers
 (no server host_speeds).


 18. PERFORMANCE AND THREADING
 -----------------------------

 18.1 Profiling plan
   * An engine patch, off by default (say sv_profile 1), that times with
     Sys_DoubleTime and prints a rolling average every 10 s into engine.log
     (run -log):
       - reading packets (with pmove and lag compensation);
       - pfnStartFrame;
       - SV_Physics;
       - for each client update: SetupVisibility and the AddToFullPack loop
         (time and call count);
       - SV_EmitPacketEntities (time, entities written, baselines tried);
       - Netchan_Transmit (time, bytes);
       - per-client totals.
   * Metamod-R has no per-hook timer of its own: its share shows in the
     differential runs below and in sv_profile's totals.
   * AMXX: differential runs. A test cvar in ts_matchmode that unregisters its
     AddToFullPack, TraceLine and Touch hooks shows their share.
   * Windows: perfmon for CPU per process and private bytes.

 18.2 What must stay on the main thread
   * mp.dll. It is reTS source now, but it is HL SDK code built on global
     state: gpGlobals, the entity lists, the string pool, static buffers, and
     the engine callbacks it calls (MESSAGE_BEGIN and friends write global
     message state). None of it is locked.
   * Metamod's hook chain: global hook tables and the META_RESULT globals.
   * The AMX Mod X Pawn VM and its natives: one VM per plugin, not reentrant
     across threads; natives call the engine and the game.
   * RCBot.
   * Everything that calls into them: pmove, PlayerPreThink and PostThink,
     physics and thinks, AddToFullPack, UpdateClientData, and the delta
     encoders (18.5).
 Threading the game simulation is not feasible. Only engine work that never
 calls into those can move.

 18.3 The order
 Measure (18.1) -> cut single-threaded costs (18.4) -> measure again -> thread
 the packet encode (18.5) only if still needed.

 18.4 Single-threaded cuts, first
   a. An engine pre-cull before AddToFullPack. reTS's AddToFullPack returns 0
      (sends nothing) for:
        - an entity index past its cap;
        - EF_NODRAW unless it is the host;
        - no model;
        - FL_SPECTATOR unless the host;
        - not visible by ENGINE_CHECK_VISIBILITY unless the host;
        - FL_SKIPLOCALHOST and owned by the host;
        - a groupinfo mismatch
      (dlls\client.cpp:1314-1380).
      What the engine can skip before calling into Metamod at all:
        - free edicts and edicts with modelindex 0: never sent on any path.
        - Non-player, non-host entities that fail the engine's own
          pfnCheckVisibility (sv_game.c:4316 and on), testing the same set
          the loop picks (PHS for EF_REQUEST_PHS), except:
            . entities whose aiment has EF_MERGE_VISIBILITY (portal cameras,
              sv_frame.c:127, 155);
            . FL_CUSTOMENTITY beams, which the check upcasts to their owner;
            . players: never pre-culled. ts_matchmode's sudden-death x-ray
              forces enemy players visible through CheckVisibility
              (fw_checkvis, ts_matchmode.sma:5688-5702), so players stay on
              the full path.
      Equivalence proof: a debug mode (sv_precull 2) runs both paths and logs
      any entity the pre-cull would skip that AddToFullPack actually sent. Run
      bots on every map and mode; enable only at zero mismatches.
      Risk: a plugin pre-hook that acts on entities outside the PVS no longer
      sees them; the proof mode catches the ones that matter.
      Saving: depends on each map's PVS; read it from sv_profile's call
      counts.
   b. Cheaper delta encoding. Cap the baseline search (sv_frame.c:188-205) at
      8 or 16 tries.
      Risk: slightly larger packets.
      Proof: bytes per update before and after, same bot match.
   c. sys_ticrate (host.c:69) and sv_fps. Every per-frame cost (thinks,
      PreThink for every player, StartFrame) scales with sys_ticrate. 100 is
      today's. 60 to 66 cuts those by about a third, and loses no updates at
      cl_updaterate 60 or less; commands are still processed one by one.
      Risk: physics and timing feel (TS slow motion, movement): test it.
      sv_fps (sv_main.c:117) only decouples a listen server's frame rate: not
      needed on a dedicated server.
   d. Plugin hot paths, in ts_matchmode:
        - move the per-viewer work (cloak, class icons, scan mark, sudden-death
          x-ray) from the two AddToFullPack hooks into reTS's AddToFullPack,
          in C, now that reTS is source; or register the hooks only while
          something needs them;
        - order fw_prethink's early-outs and move work that rarely changes to
          a 10 Hz task;
        - check whether every TraceLine and Touch really needs a Pawn call.
      Risk: behaviour changes. Test every mode.
   e. Update rate: cl_updaterate drives (c) per client; 20 against 60 is three
      times the AddToFullPack and encoding work.
   f. reTS's 2048 cap (6.2) is a correctness fix, not a speed one, but it lands
      in the same code.

 18.5 The threadable part: the per-client packet encode
 After the game frame, sending does for each client: build the entity list
 (AddToFullPack: game DLL), client data (UpdateClientData: game DLL), encode,
 transmit. Only the encode and transmit can leave the main thread.
 A barrier design:
   Phase A, main thread. Run the game frame. Then, for every client due an
   update:
     - SetupVisibility and the AddToFullPack loop into that client's new frame
       slot of svs.packet_entities (as today);
     - UpdateClientData and weapon data into per-client buffers;
     - the client's pending datagram and reliable data, copied;
     - the encoder results (the encoder problem, below).
   Snapshot. From here to the join nothing writes:
     - svs.packet_entities (this update's frames were all written in A; the
       older frames are untouched);
     - svs.next_client_entities;
     - the baselines, the static entities, the delta tables;
     - the precache lists, sv.time.
   Phase B, a worker pool (the main thread included). Per client:
     - SV_EmitPacketEntities against the acknowledged frame;
     - the client data delta;
     - assembling the datagram,
   into that client's own buffer.
   Join. The main thread waits for every client, then transmits, updates the
   statistics, and clears per-frame state.
 Thread-safety rules for phase B:
   * Each worker writes only its client's message buffer, its client's
     frame/netchan bookkeeping, and its own scratch. No shared mutable state.
   * Read-only for everyone: the ring, the baselines, the delta descriptors,
     sv.time.
   * Per thread: bit-writer scratch and the delta active-field flags.
   * No zone allocation (Mem_Alloc is not thread-safe): preallocate.
   * No Con_Printf from workers: log per thread, flush after the join.
   * No call into mp.dll, Metamod, AMXX or RCBot. A debug build asserts this
     with a thread-id check in the engine's wrappers around the game exports.
 The encoder problem. Delta_CustomEncode (net_encode.c:499-508) clears the
 shared table's bInactive flags and calls the game DLL's
 Entity_Encode/Player_Encode/Custom_Encode, which switch fields back through
 the engine (Delta_SetFieldByIndex, net_encode.c:2286-2292). That is a call
 into mp.dll and a write to shared state for every entity encoded. reTS's
 encoders (dlls\client.cpp:1637-1745) are pure functions of (from, to) after a
 one-time static init. Two ways out:
   1. An engine change making the active flags a per-call array, plus reTS
      registering thread-safe encoders through an extended entry point. Their
      one-time init runs on the main thread before the first threaded frame. A
      game DLL without the extension keeps the single-threaded path.
   2. Port reTS's encoders into the engine for this game, byte-verified.
 Prefer (1).
 Windows build: the engine already makes threads for its DNS resolver through
 SDL, pthreads or CreateThread (net_ws.c:308-337); a small pool with a barrier
 (events or semaphores) fits beside it. Worker stacks (1 MB each by default)
 come out of the 32-bit address space: keep the pool small (2 to 4).
 Browser build: no threads. The engine is built without -pthread, and threads
 would need cross-origin isolation (DEPLOY.txt:491-493). Compile only the
 single-threaded path there (#if !XASH_EMSCRIPTEN, or sv_threads 0).
 Verification. A determinism mode that encodes every client's packet both ways
 in the same process (threaded into a shadow buffer, single-threaded into the
 real one) and compares them byte for byte every frame; a mismatch logs the
 client, entity and field. Run it with bots and a few real clients on every map
 and mode; then soak with sv_threads on.
 What it can buy: phase B only. If sv_profile shows the AddToFullPack loop
 (phase A, main thread) dominating, threading buys little. Hence the order.

 18.6 Effort, by step
   * Profiling patch: 1 to 2 days. Bot runs: 1 day.
   * Pre-cull with its proof mode: 2 to 3 days.
   * reTS 2048 cap: half a day.
   * Baseline cap: 1 day.
   * sys_ticrate trial: half a day.
   * Moving ts_matchmode's per-viewer work into reTS: 3 to 5 days.
   * Threaded encode, only if needed (encoder API in reTS and engine,
     per-thread state, barrier, determinism mode, soak): 2 to 3 weeks.


 19. BOT LOAD TESTS
 ------------------
 What a bot is here: a fake client (FCL_FAKECLIENT).
   * It takes a slot and an edict, runs PreThink, PostThink and pmove, and
     appears in every human's packets.
   * But the server builds no packets for it and sends it nothing
     (sv_frame.c:846), it sends no usercmds over the network (no lag
     compensation), and it has no voice.
 Prerequisite: RCBot built for 128 (section 10), or it stops at 32 bots
 (bot_commands.cpp:1567). Maps need RCBot waypoints for bots to fight sensibly.
 Commands: rcbot config max_bots N, rcbot addbot (COMMANDS.txt:880-890).

 Layers, each on a test server:
   L0  today's build, 32 slots, 31 bots and one human observer: the baseline.
   L1  new engine, reTS, Metamod and RCBot; AMXX unloaded (its line taken out
       of addons\metamod\plugins.ini); 64 slots, 63 bots, one human. The

   L3  with H9's plugins, in each mode (Team Elimination, Siege, Uplink,

   L4  only if going past 64: 96, then 127 bots.
 Run L1 and L2 under the goldsrc-net prebuilt Metamod-R and under H9's
 build of it (7.4).

 What to measure, every run:
   * Server frame time: `stats` FPS against sys_ticrate, every 10 seconds;
     sv_profile's phases (18.1); CPU of the one core.
   * Bandwidth per client: `stats` In and Out (it averages real clients only,
     sv_cmds.c:871); net_graph 3 on the human (choke, loss), at rate 25000 and
     100000.
   * Memory: private bytes and the largest free block of HAVOC 9.exe at map
     load and after an hour (perfmon or typeperf); the ring's size printed at
     map load with -dev (sv_init.c:841).
   * Edicts: edict_usage (sv_cmds.c:1320) at the busiest point; no "no free
     edicts".
   * Crashes and errors: engine.log (-log), AMXX's logs (run time errors),
     Windows' Application event log for the faulting module.
   * The scoreboard: on the human, 63 bots plus himself, every row (11).
   * Soak: two hours per map and mode; ten map changes in a row.
 A tiny test-only AMXX plugin (or a ts_matchmode debug cvar) can run `stats`
 and `edict_usage` every 10 seconds into the log, so runs leave a record.

 What bots alone can test (with one human watching):
   * game logic per slot: the TS tables (6.5), the slow-motion memory bug
     (6.4), trigger_hurt (6.3), the escape zone, flying bullets, The One;
   * AMX Mod X's player tables and get_players (bots go through its connect
     hooks), every plugin's arrays, the MAXPL pass, the icons;
   * edicts, the 2048 cap (watch late entities on New Byzantium), memory (the
     ring follows maxplayers, whoever fills it), map changes;
   * RCBot itself;
   * the game frame's CPU (thinks, PreThink hooks, physics, traces);
   * the wire messages and the scoreboard as one human sees them;
   * spectating a bot in slot 64 (iuser2).
 What needs real clients:
   * everything per viewer. AddToFullPack, encoding and sending run only for
     real clients, so 63 bots and one human cost about a sixty-fourth of the
     per-viewer work of 64 humans: bot CPU numbers are a floor, not the
     answer;
   * bandwidth and choke; lag compensation; voice between two high slots;
   * client frame rate with 64 models (low-end PCs and the browser);
   * the refusal of old clients; the relay; A2S fragmentation; feel.
 Bridging the gap: run with k real clients (1, 2, 4, 8: other PCs or VMs with
 H9XASH at low settings) in place of k bots, read the per-viewer cost from
 sv_profile, and extrapolate to 64. A headless "client" that only connects and
 acknowledges would make it exact: a separate tool to write.

 21. RUNNING PAST 64: WHAT 128 ADDS
 ----------------------------------
 Built for 128, a server can be raised past 64 by maxplayers alone. What
 changes compared with 64:
   * Memory: the ring is 680 MiB at its stock size: the large-address flag or a
     smaller ring is then required (13). Both are built.
   * CPU: the per-viewer work about quadruples again; lag compensation and
     sounds without a PHS quadruple.
   * Bandwidth: about double per server; A2S_PLAYERS 5.3 KB.
   * The scoreboard: the compact and tabbed design (11.3).
   * Spawns: 64 a side; ts_matchmode's per-team lists hold exactly 64
     (:621-629), and the map-entity fallback list g_spawns[64] holds 64 in all.
     Make them larger.
   * Edicts: peaks of about 2,650 to 2,750 on the big maps: still under 4,098,
     with less room (and reTS's 2048 cap must be fixed by then in any case).
   * Bots, corpses and gameplay: maps built for 16 a side.
 Nothing is rebuilt and no client is rolled out again.

 24. RISKS
 ---------
   * CPU (sections 17 and 18): the biggest unknown. 64 may need the per-viewer
     hooks moved into reTS first, and perhaps the threaded encode.
   * The goldsrc-net sources: the AMX Mod X core needs the fork's source,
     and reTSX's reTS backend is in no public source (8.5). ts_matchmode
     depends on TSX natives.
   * A partial deploy: any server component left at 32 corrupts memory at slot
     33 (AMXX core worst). Hence the guard rail (9.1 g) and the checklist.
   * Memory: 340 MiB at 64 is likely fine; LAA is built, and 13 says how far it
     has been tested.
   * The patch chain: the new engine patch must pass xash.bat's reverse check
     with the rest, or the next full build stops.
   * Deploying AMXX, Metamod or RCBot only into H9XASH: build.bat overwrites
     them from the Steam install (8.4).
   * Gameplay: maps built for 16 a side: spawns, chokepoints, objectives,
     timers.
   * A2S_PLAYERS fragments past one MTU.
   * Hosting: 20 to 50 Mbit/s upstream at 64, and relay egress for browser
     players.

 Overflow and limit messages (2026-11-03)
 The engine's messages a 64-slot server or its players can hit, with each one's
 limit, where it lives and the safe way to raise it. From the engine build with
 engine-h9-overflowlog.patch on, each of them, printed or not, also goes to
 ts\logs\h9_overflow.log: the time, server, listen or client, the map and the
 message, the same message at most once in 10 s. SZ_GetSpace and MAX_MSGLEN are
 GoldSrc's names: they come from Steam HLDS or a GoldSrc client, never from Xash.
   * "<name> overflowed", the client dropped: its reliable stream passed
     MAX_INIT_MSG, 192 KB (net_ws.h:41, sv_frame.c). Find what floods it; do not
     raise it (every client shares the size).
   * "Datagram overflowed for <name>": a client's unreliable data or a whole
     frame's packet passed MAX_DATAGRAM, 16 KB (net_ws.h:34, sv_frame.c). The
     rates do not change that size. The whole frame is dropped, so the client
     gets no delta base and its next update is a full one again. On a big
     open map the entities in view fill it: about 10 bytes each when new to a
     client, 600 to 1,500 in view on New Byzantium. h9_msgstats shows which it
     is (COMMANDS.txt, DATAGRAM OVERFLOW); h9_staticprops takes the map's
     props out of the update; engine-h9-entbudget.patch (a proposal) holds the
     entities new to a client to a budget, so no update can pass 16 KB.
   * "sv.reliable_datagram overflowed, its messages dropped": the shared 16 KB,
     dropped whole (engine-h9-reliableburst.patch). A server-only raise.
   * "pfnMessageEnd: X has overflow multicast buffer" (8 KB) and "X too long
     (more than 2048 bytes)" (MAX_USERMSG_LENGTH, client and server alike):
     split the message.
   * "Server will restart due delta is outdated": the packet entity counter
     (sv_frame.c); engine-h9-deltacounter.patch brings it down long before.
   * "delta request from out of date entities" (-dev 1): a client's delta base
     left the packet entity ring, halved past 32 slots (13 c). With the large-
     address flag's 4 GB the full ring fits again, should this show.
   * "Too many entities in visible packet list. Ignored N entities":
     MAX_VISIBLE_PACKET, 2048 a client a frame (protocol.h:98-99).
   * "no free edicts (max is 4098)": max_edicts in ts\gameinfo.txt, up to 8192.
   * "Overflow N temporary ents!", "Overflow N particles", "not enough free
     beams!": the player's max_tempents 2048, max_particles 32768 and max_beams
     512 in ts\gameinfo.txt (raised 2026-11-03 from 500, 4096 and 128).
   * "Cbuf_...: overflow", "command buffer overflow": MAX_CMD_BUFFER, 32 KB
     (cmd.c:21), engine-local.
   * On a player's side, "CL_ParseServerMessage: overflow!", "illegible server
     message" or "svc_bad": the server sent a message cut off; the server's own
     line names the buffer.
