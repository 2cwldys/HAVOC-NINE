HD TEXTURES (AI upscaled, materials/)
=====================================

Every texture in the mod, upscaled 4x and handed to the engine as loose TGA files, with the
original art untouched. A player can switch between the two.

Status: the upscaling tools and the texture pass are built. The detail-texture pass (section 7)
and the download script (section 8) are NOT built yet and are marked where they appear.


1. THE IDEA, AND WHY IT COSTS NOTHING TO SWITCH OFF
---------------------------------------------------
The engine looks for a replacement texture on disk BEFORE it looks in the .wad and before it
reads the copy embedded in the map. The order is commented in the source, at
xash3d-fwgs\engine\common\mod_bmodel.c:2849:

    // Texture loading order:
    // 1. HQ from disk
    // 2. From WAD
    // 3. Internal from map

So an upscaled texture is an ADDITION. No .bsp, .wad or .mdl is edited, and with the feature off
the engine simply falls through to the art that was always there. That is also why the pack can
be optional: a player without it loses nothing.

It is the only approach that can work here. MAX_MAP_MIPTEX is 0x2000000, 32 MiB of texture data
per map (xash3d-fwgs\common\bspfile.h:86), and Xash does NOT raise it above GoldSrc.
h9_tsrp_hive.bsp already carries 22.2 MiB, so putting 4x art inside the map would need about
355 MiB and the map would not load. Recompiling from the .map sources hits the same wall.


2. WHERE THE ENGINE LOOKS
-------------------------
All paths are under the mod folder, so ts\materials\. TGA only -- the extension is hardcoded in
every one of these call sites. The pack is built to match them exactly.

  world, shared by every map   materials\common\<name>.tga
  world, one map only          materials\maps\<map>.bsp\<name>.tga
  decals                       materials\decals\<name>.tga
  studio models                materials\models\<model>\<texture>.tga
  sprites                      materials\sprites\<sprite>\frame00.tga

Where each comes from:

  * World textures: Mod_SearchForTextureReplacement, mod_bmodel.c:2643. It tries two folders, in
    order: the model's own name (which for a map is "maps\<name>.bsp") and then "common".
  * Decals: cl_tent.c:2983 builds "materials/decals/%s.tga" and never looks anywhere else. A
    decal left in common\ is simply not found.
  * Studio models: gl_studio.c:3441, "materials/%s/%s.tga" over the model name and the texture's
    own internal name. Note this one lives in the RENDERER, not the engine, so it works under
    ref_gl and not under the software renderer.
  * Sprites: cl_sprite.c:173. The sprite's name has its EXTENSION STRIPPED first (line 252-253),
    so sprites\foo.spr is looked up under materials\sprites\foo\. The file is
    <group_suffix><NN>.tga, where group_suffix is "frame", "group" or "angle" depending on the
    frame's type (lines 307-315), and NN is the frame number as two digits.

NAMES. The engine rewrites exactly one character: a leading '*' becomes '!' (mod_bmodel.c:2855).
A leading '{' is KEPT -- the engine's own documented example is materials/decals/{shot2.tga. A
texture name is char[16], so fifteen characters at most.


3. THE TWO SWITCHES
-------------------
They are independent and they stack.

  host_allow_materials   the texture itself: upscaled, or stock
  r_detailtextures       the bump overlay on top: on, or off

host_allow_materials (engine\common\host.c:82) ships at "0" and is FCVAR_LATCH|FCVAR_ARCHIVE.
LATCH means a change only takes effect on the next map load, because textures are uploaded to the
GPU when the map loads. So it is the cvar AND a reload:

    alias h9_tex_hd    "host_allow_materials 1; restart"
    alias h9_tex_stock "host_allow_materials 0; restart"

r_detailtextures (ref\gl\gl_opengl.c:28) ships at "1" and is FCVAR_GLCONFIG, NOT latched, and
Xash has a "toggle" command (engine\common\cvar.c:1282). So that one is a real instant A/B:

    bind F6 "toggle r_detailtextures"

Two things to know about host_allow_materials. It is forced to 0 on a dedicated server, which is
correct -- a server draws nothing. And because it is FCVAR_ARCHIVE, a player whose config has
already saved a value keeps that value: shipping the default at 1 reaches NEW installs only. A
saved config belongs to the player and is not migrated.

There is also a hard gate: Mod_AllowMaterials() requires that the mod has not set
ENGINE_DISABLE_HDTEXTURES (common\enginefeatures.h:30, bit 1<<30). Nothing in reTS sets it, and
TS has no custom renderer, so this is expected to be clear -- but it is worth confirming in game
the first time (section 6).


4. WHAT IS COVERED
------------------
Measured, not estimated. 13,383 places a texture is used, which dedupe to 6,189 distinct images.

  viewmodels        v_*.mdl              1,525 textures      114 unique
  world weapons     w_*.mdl                 59                54
  player weapons    p_*.mdl                106                62
  player models     models\player\        2,117               743
  matchmode models  models\matchmode\     1,355               109
  h9 models         models\h9\              296               210
  other models                              394               274
  map textures      inside the .bsp       6,136             3,517
  wad textures                            1,486               878
  decals            decals.wad              244               231
  sprites                                 1,051               962

NOT covered, and why:

  * Skyboxes. gfx\env\ is 154 loose TGA files the engine loads by worldspawn's skyname, not
    through any wad, bsp, mdl or spr, and sky replacement uses a different path with _solid and
    _alpha suffixes. A separate pass.
  * HUD sprites. cl_sprite.c:163 sends them down the other branch entirely; materials\ is never
    consulted for them.
  * Colormap model skins. gl_studio.c:3439 refuses a replacement for a texture flagged
    STUDIO_NF_COLORMAP, commented "colormaps must have the palette for properly work", because
    that is the team-colour remap path. A skin is that path when its name begins DM_Base or remap
    (ref\soft\r_studio.c:3016). Exactly ONE texture in the whole mod is one, so this costs
    nothing here.
  * Alias models. Upstream does not support replacement for them. TS does not use them.


5. RUNNING A PASS
-----------------
The tools are in tools\texpack\. They need node for the two .mjs and a Python with torch+CUDA for
the upscaler; the venv built for this lives outside the repo because torch is 2.5 GB.

    node tools\texpack\extract.mjs
        Reads every .bsp, .wad, .mdl and .spr, converts each texture to RGBA, hashes the PIXELS,
        and writes one PNG per distinct image named by that hash. Records every place each one is
        used. About a minute for the whole mod.

    <venv>\python.exe tools\texpack\upscale.py
        Upscales each PNG 4x on the GPU and writes a 32-bit RLE TGA named by the same hash.
        Takes the project's heavy-job lock for the run. Resumable: stop it and run it again.
        --sample 200 does a spread of sizes first, which is how to get a real time estimate.

    node tools\texpack\place.mjs --dry
        Works out where every texture has to go by the rules in section 2 and reports, writing
        nothing. Drop --dry to place them, --link to hard link instead of copying.

    node tools\texpack\manifest.mjs --write
        Stamps what has been made, with the recipe that made it (section 6).

Measured on an RTX 3070: 200 images in 97 s, the whole 6,189 in about an hour, roughly 10 GiB of
distinct output. RLE roughly halves a TGA, and the engine reads type 10 at 32 bits
(engine\common\imagelib\img_tga.c:112-119 and 149), so there is no reason to ship uncompressed.


6. THE DELTA: NEVER DOING THE SAME WORK TWICE
---------------------------------------------
Everything is keyed by the sha256 of a texture's PIXELS, not by its name or its file. One wall
texture used in fifty maps is one image and one upscale. A map recompiled without touching its
art produces the same hashes and is not redone.

Dedupe alone is not enough, though, because an old output would be reused even after the model
changed. So an entry also carries a RECIPE ID: a hash of the model's own sha256 plus the scale,
format, compression, bit depth and alpha handling. An output counts as reusable only when the
manifest says this recipe made it. Change the model and every entry goes stale, correctly,
instead of leaving a pack half in one style and half in another.

    manifest.mjs           reports fresh / stale / to do / orphaned
    manifest.mjs --write   records the current state
    manifest.mjs --prune   deletes outputs whose source is gone

There are TWO manifests and they do different jobs:

    manifest.json   source image hash -> output. Stops US redoing work. Lives with the work.
    hd-pack.json    install path -> blob hash. Ships INSIDE the pack. Stops PLAYERS
                    redownloading work. Written by place.mjs.

hd-pack.json is what makes an update small. It lists every file the pack installs and the blob
that fills it. Because a blob is named by the hash of its bytes, the server keeps ONE copy of
each distinct texture: 9,765 installed files come from 6,182 blobs, so an install pulls about a
third fewer files than copying path by path, and an update that changes fifty textures is fifty
blobs rather than a new ten-gigabyte download.


7. DETAIL TEXTURES -- NOT BUILT YET
-----------------------------------
A second, separate effect: a grey normal-map overlay that adds surface bump without changing
resolution. This is what the reference guide at
github.com/The-Specialists-Archive/ai-texture-upscaling (by Dementei) actually produces.

Engine support is complete, unmodified, and already switched on -- r_detailtextures is "1" in
ts\opengl.cfg:54 -- and there is not one detail asset in the mod. Adding them needs no engine
change and no recompile, only two new kinds of file:

    ts\gfx\detail\<map>\*.tga
    ts\maps\<map>_detail.txt      format: 'texturename' 'detailtexture' 'xScale' 'yScale'

Mod_ParseDetailTextures is at mod_bmodel.c:3190-3279 and resolves an asset as gfx/<name>. Strip
the leading '{' from a masked name in the list, as the guide says. One caveat before a mod-wide
write: ts\opengl.cfg also ships gl_vbo "0" and gl_vbo_detail "0", so the detail pass in
ref\gl\gl_rsurf.c:2568 is code this project has never exercised. Prove it on one map first.


8. THE DELTA PATCHING PROCESS -- NOT BUILT YET
----------------------------------------------
The pack is not in git and not in the base install. A script that ships with the client fetches
it, after the player gives a code their havoc9.org account issues.

No address, host name, key, token or account number appears in this file, in the shipped script,
or anywhere in the repository. They come from configuration that is not tracked. A reader of this
document learns the MECHANISM and nothing that would let them reach the service.

WHAT THE SERVER PUBLISHES

    hd-pack.json     the manifest of section 6: install path -> blob hash, plus every blob's size
    a blob store     one file per DISTINCT texture, named by the sha256 of its own bytes

Nothing is named after a map or a model, so the store is write-once: a blob that exists is never
rewritten, only referenced by more paths.

WHAT THE CLIENT KEEPS

Its own copy of hd-pack.json, saved after a successful install. That copy is the whole of its
state. If it is lost the client can rebuild it by hashing what it has on disk.

AN UPDATE, STEP BY STEP

    1. fetch the current hd-pack.json
    2. compare it with the local copy and work out three lists:
         blobs whose hash the client does not already hold   -> download
         paths whose blob hash changed, or that are new      -> write from the blob
         paths that are no longer in the manifest            -> delete
    3. download only the blobs in the first list
    4. verify each downloaded blob against the sha256 it was asked for, BEFORE using it
    5. write the changed paths, delete the removed ones, delete blobs nothing references
    6. save the new manifest as the local copy

WHY THIS SHAPE

  * A texture that did not change is never downloaded again, even if it moved to a different
    path or is now used by more maps.
  * A texture used in many places is downloaded once. 9,765 installed files come from 6,182
    blobs today.
  * An interrupted update resumes. Blobs already verified are kept, so step 2 simply finds fewer
    to fetch next time.
  * Corruption is detectable without a separate checksum file, because a blob's name IS its hash.
    A blob that does not hash to its own name is discarded and fetched again.
  * A changed pack is cheap to publish: regenerate the manifest, upload the blobs that are new.
    Fifty changed textures is fifty blobs, not a fresh ten-gigabyte archive.

ON THE CODE AND THE TOKEN

The code the account issues identifies the PLAYER, so it should be exchanged once for a
short-lived token, and the token is what authorises the fetch. The script keeps the token for its
lifetime and never the account password. The manifest and the blobs are ordinary files addressed
by hash, so the gate belongs at the fetch, not in the naming.

The pieces this builds on, all of which already exist: h9web owns the accounts and sessions, the
player id is already an HMAC rather than the raw account number (h9web\lib\playerid.js), the host
already serves behind an allowlist, and *.h9pk is already a tracked package format here.


9. CHECKING IT WORKED
---------------------
The engine will tell you, per texture, which is better than any amount of looking:

    host_allow_materials 2

At that setting every lookup is logged at any developer level, in the form

    Looking for maps/<map>.bsp:<texture> tex replacement...OK (materials/common/<texture>.tga)
    Looking for <texture> ... MISS (not found)
    Looking for models/<model> ... FAIL (materials/models/<model>/<texture>.tga)

OK means found and loaded. MISS means the file is not where the engine looked, which is a naming
or a folder mistake. FAIL means it was found and could not be read, which is a bad TGA. Capture
that log and diff it against the index -- that is the pack's ground truth, and it is automatic.

Remember the cvar is latched: set it, then reload the map, or it will appear to do nothing.
