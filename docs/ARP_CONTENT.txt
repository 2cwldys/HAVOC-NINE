ARP CONTENT ON HAVOC 9 -- the jobs, items, shops and NPCs of h9_tsrp_hive and h9_tsrp_newbyzantium
====================================================================================================

  Apollo RP builds every menu from content (docs\APOLLO_RP.txt, section 2). This is the content of H9's two roleplay
  maps: the Ministry of Defense ranks as jobs, a civilian layer, and the NPCs that open the shops, the banks, the
  ATMs, the doctors and the gun shops, standing on open ground of each map. Nothing here has been run in a game yet
  (section 8).


1. WHAT IS IN IT
----------------

  Per map, in apollo-rp\base\addons\amxmodx\configs\arp\maps\<map>\:
    <map>.sql   the jobs: 26 rows of INSERT OR IGNORE INTO arp_jobs. An admin loads it on the map (section 2); ARP does not run it by itself.
    npcs.ini    the NPCs: ARP_NPCs reads it when the map loads (hive: 22 NPCs, New Byzantium: 32).
    arp.ini     (already there) arp_table_jobs "arp_jobs_<map>": the jobs are the map's own, in their own table.

  The items themselves are not content: ARP's plugins register all 93 of them in code (section 5). What the content
  decides is which NPC sells which item for how much, and which jobs there are.


2. HOW AN ADMIN LOADS IT
------------------------

  1. Back up data\sqlite3\arp.sq3 with the server stopped (docs\APOLLO_RP.txt, section 4). Start the map once with the files in
     place: that makes the map's jobs table (arp_jobs_h9_tsrp_hive or arp_jobs_h9_tsrp_newbyzantium) with the one job Unemployed.
  2. Join as an ARP admin (access letter z) and, on THAT map, open the console and type  arp_config  ->  3. Load Map SQL Data. The menu
     opens for an ARP admin and for an AMX Mod X admin with the ban flag; the latter makes himself an ARP admin first with 1. Add First
     ARP Admin. The screen shows "N/26 Completed - 0 Errors" and then "Map SQL loading is complete". The file loaded is the one
     named for the map you are on (<map>.sql in its folder).
  3. Restart the map: the jobs are read when the map loads. arp_joblist in the console lists them, JOBID in the order of section 3.
  Loading again is harmless: every row is INSERT OR IGNORE, so a second load adds nothing and changes nothing, and a row an admin
  has edited keeps the edit. (Checked on a copy of the live database: two loads give 26 rows with 0 errors each time.)
  The loader runs one statement to a line, skips a line that starts with - ; or # (or is under 3 characters), and swaps ARP's default
  table names for the map's own: the file says arp_jobs and the statement runs on arp_jobs_<map>. The NPCs need no loading: npcs.ini is
  read at every map start, so a change to it shows after the map restarts.
  A MySQL server (arp_sql_type "mysql") needs  INSERT IGNORE  where the file says  INSERT OR IGNORE ; H9 runs SQLite.

  admin gives with arp_setjob and which nobody else can offer, since no job right holds z. Lord Minister is the same kind of job in
  that only an admin can give it (its letter g is held by no job right).
  The civilian layer has no letters. The jobs are a starting set: add more with arp_addjob (section 7).


4. HIRING, FIRING AND JOB RIGHTS
--------------------------------

  arp_setjob <player> <job>      ARP admins only (z). Sets the job at once. <job> is a name in quotes ("Enforcer 1") or the JOBID.
  arp_employ <player> <job>      Offers the job; the player accepts or declines. Allowed to an admin, or to anyone whose JOB RIGHT shares
                                 a letter with the job's access letters.
  arp_fire <player>              Sets the player Unemployed. Same rule: a job right that shares a letter with the player's job.
  arp_setjobright <player> <l>   ARP admins only. A player's job right is a set of letters kept on his character (arp_users.jobright),
                                 NOT taken from his job: set it when he is promoted and take it away when he is not (<l> = -  for none).
  The tiers make the Ministry hire from below. Give these job rights, and never a, b, g or z (a job right of a would let its holder offer
  every police job, and a job right of z or g would let its holder offer the Administrator or the Lord Minister):
    Sergeant 1, Sergeant 2, Lieutenant      c       can offer and take Cadet to Ensign and M-Cadet to M-Ensign
    Captain, Major                          cd      and Sergeant 1 to Lieutenant
    Guardian, Legate                        cde     and Captain, Major
    Lord Commander                          cdef    and Guardian, Legate, Lord Commander
    Lord Minister                           cdef    the same as a Lord Commander; the Lord Minister and the Administrator are an admin's to give
  A job whose name is inside another's (Cadet inside M-Cadet) is still the job you name: arp_employ <player> "Cadet" offers Cadet.
  That needs H9-arpcontent.patch (ARP_Commands: an exact name wins). Without it ARP answers "more than one job matching your input"
  for Cadet, Enforcer 1 to 3 and Ensign, and the JOBID works instead. The same patch (ARP_Core) stops a short name that matches
  three or more jobs ("Enforcer") from writing past the command's array.
  A character keeps the job he has on a map that does not offer it (docs\APOLLO_RP.txt, section 8): the Ministry ranks belong to
  these two maps only, and a visit elsewhere does not cost a rank.

7. CHANGING IT
--------------

  A salary or an access string (live, as an ARP admin in the console, on one line, with the map's real table name; it applies after the
  map restarts, and to a player after he reconnects):
      arp_query UPDATE arp_jobs_h9_tsrp_hive SET salary=90 WHERE name='Captain'
  Then make the file say the same, or a fresh database loads the old row: edit the number in <map>.sql. Editing the file alone changes
  nothing on a map that already has the row: arp_config runs INSERT OR IGNORE, which never overwrites a row.
  A new rank: arp_addjob "Warden" 55 ad   (name in quotes, salary, letters), or one more INSERT OR IGNORE line in the file. Put it in
  the file at the position you want (rows load in file order). arp_addjob refuses a name that lies inside an existing job's name.
  A rank taken away: arp_deletejob "Name". Players in the job become Unemployed at once; a character saved with its name is
  Unemployed on the map (with the notice that his job is not offered here) and keeps the saved name until he takes another job.
  The optional M-Sergeant 1, M-Sergeant 2 and M-Lieutenant are in each file as comments: remove the leading "-- " and load again.
  To change a rank on one map only, change that map's file/table; the two maps do not share a jobs table. To share ranks, give both
  maps' arp.ini the same arp_table_jobs (docs\APOLLO_RP.txt, section 8).

  Move or add an NPC: stand where it should be and type arp_getinfo (ARP admin): it prints Origin and the view angles. Put the origin in
  npcs.ini (the player origin is 36 over the floor; ARP drops the NPC to the floor), and the angle you want it to face PLUS 180. Keep it
  off doors, 56 units of open floor round it, and off a spawn point. Copy a block of the same type, change what is different, end it
  with [END]. Restart the map. A sell line is  sell "Item_Name price"  (underscores for spaces; the name need only be unique in the
  item list); heal "price" is a doctor's; addgun "Gun_Name price 0|1|2" is a gun shop's.
  A new KIND of item (a Ministry ID, a ration pack) needs a plugin: ARP_RegisterItem in ARP_Items.sma or one of its siblings, with a
  handler. A shop can only stock what is registered.
  The H9 content files are written by the tools that placed the NPCs; edit the files by hand from here on.


8. WHAT WAS CHECKED, AND WHAT WAS NOT
-------------------------------------

  Checked on files and a copy of the live database (nothing was run in a game):
    * Both .sql files, loaded the way arp_config loads them into a copy of the live arp.sq3 after the core's own table creation: 25
      statements, 0 errors; a second load changes no row; every other table of the copy is unchanged; every job is found by its own name.
    * Both npcs.ini files, read by a port of ARP_NPCs' own reader (its keyword order and parse() included): every block gives the
      intended type, name, model, origin, facing and stock, and every sell/addgun name resolves to its own item.
    * Every NPC spot, with the map's own space model (SMAK): floor under it, a standing body fits, level under all four corners,
      52 units from every door, breakable, button, ladder, water, hurt and travel-zone brush, 80 from every spawn and arrival, 40 from a
      bot waypoint, 56 units of open floor round it, and all spots of a hub on one connected stretch of floor. The only ts_model within
      70 units of an NPC is models/h9/re_dirt.mdl, at floor level, 68 units from the Paradise clinic.
    * The two plugin changes compile (ARP_Core with its 14 baseline warnings, ARP_Commands with none).
  NOT checked: any of it in a game. Specifically: that the NPCs show and face the way the table says (the facing plus 180 is read from
  ARP_RegisterNpc, not seen); that the player models are in the web client's package; that a bot does not snag on an NPC; that the
  arp_config load runs in a game; that the 25 rows arrive in file order (arp_config sends them as threaded queries; if the SQL
  module did not run them in order, arp_joblist would list the ranks in another order and nothing else would change).
