===============================================================================
 H9 VGUI: SERVER-DRIVEN VGUI PANELS FOR AMX MOD X PLUGINS
 (THE MATCH MODE'S MENUS AND HUD TEXT ARE THE FIRST USER)
===============================================================================

 Who this is for: whoever builds H9's reTS client or the match mode
 plugins, and any plugin author who wants a real panel on an H9XASH
 player's screen instead of AMX Mod X's text.

 Update (2026-11-05): the panels are drawn a quarter smaller (section 2c: menus 0.51, banners
 0.45, on text ladders of their own in the textschemes, 3d); a mode that keeps one pool of
 lives sends the scoreboard H9Pool (reTS cl_dll vgui_ScorePanel.cpp); and the MARK op
 (protocol 3, section 4i) draws a point of the world on the screen through the walls: the
 objectives of the mode plugins: the capture points of ts_assault, the zones and the uplink of
 ts_uplink and the flags and the pads of ts_ctf, all through include\h9_marks.inc.

 Status (2026-11-03): steps 1 and 2 of section 5 are built. The client
 side is in reTS\cl_dll (h9_vgui.cpp, vgui_H9Panel.cpp, hooked in hud.cpp,
 menu.cpp, ammo.cpp and the viewport's KeyInput), in the client.dll of
 2026-11-03 that also draws the scoreboard's level badges (SHA256
 417D00113232E0DA0CD358A22A7683E8
 7E51407CADFD14B9116D9A02D5F7D56C, item 14 of its client.dll.patch). The
 plugin side is in include\h9_vgui.inc, and ts_matchmode sends its side
 and class menus through it (h9_vgui 1). Then: the match bar (4g; the
 client's protocol 2, and ts_survival's breather on it), and step 3's
 menus, ts_rtv's map vote and nominations and h9_community's portal
 confirm. The decisions of section 7 are taken. The panel sprites and
 the chat bubble are H9 purple (section
 9). Line numbers are those of ts_matchmode 1.54-gameplay7 (2026-11-02,
 20:01) before this work and ts_rtv 1.0-h9.2. Other work is editing those
 files and the reTS client, so when a number has moved, find the code by
 the function named beside it.

 The short version
   * The match mode talks to players through AMX Mod X text menus (side,
     class, the .menu legend, the RTV vote and nominations, the portal
     question) and some forty set_hudmessage lines. An H9 client can draw
     all of it as VGUI, with the two panel sprites as the backgrounds and
     the scheme fonts for the text.
   * One plugin-registered user message, H9Vgui, carries three kinds of
     thing: MENUS (the VGUI twin of an AMX text menu), NOTICES (what a
     hudmessage says) and PANELS (any layout a plugin builds from labels,
     images, buttons, progress bars and text entries).
   * A menu stays an AMX menu. The plugin still calls show_menu(); a
     client with H9's client.dll draws the twin in place of the text and
     answers with the same "menuselect N", so every menu handler stays as
     it is, and every other client gets the text menu, as today.
   * A client says it can draw them in its userinfo, _h9vgui "1". The
     player's cl_h9_vgui 0 turns the system off for him, and his game then
     tells the server so.
   * Nothing new is needed in the engine or in AMX Mod X: one reTS client
     build, one include (include\h9_vgui.inc) and the plugins' own edits.
   * The panels' top stack takes the top of the screen, and TS's own
     notices ("<name> is The Specialist", the killing sprees: they stack
     down from 32 px at the top centre) are drawn beneath it while it
     shows something. The client keeps panels out of the other bands the
     HUD writes in (section 4c).

 1a. Menus

 Every AMX menu is drawn by the client's CHudMenu (reTS cl_dll\menu.cpp,
 Draw 136-219): at the left edge, x 20 px, centred on the screen's height
 (menu.cpp:168-176), in the HUD font, in the four colours the client
 parses (\w \d \y \r, plus TS's \g; menu.cpp:96-124). A number key comes
 in as slot1..slot10 (ammo.cpp:705-716), and SelectMenuItem sends it back

 the colour codes out of a menu_create() menu on a mod it does not know,

 2. THE PANEL SPRITES
 --------------------
 2a. Where they come from, where they ship, and what uses them

 Source: modelling\make-menu-panel.mjs draws both (panel(), from line 107)
 and writes each as an IDSP version 2 sprite to its three outputs
 (make-menu-panel.mjs:35-39): TSM\sprites, the source of truth;
 TSM\export\ts\sprites; and the Steam install's ts\sprites. It also writes
 previews, TSM\export-mdl\tsm_panel.png and tsm_banner.png. Run it from
 TSM\modelling: node make-menu-panel.mjs. Nothing else builds them.

 Shipping:
   export.bat     TSM\sprites into export\ts\sprites (export.bat:430-432),
                  H9XASH into export\H9XASH (667), export\ into the git
                  mirror with /E /XO (865)
   xash.bat       assets: export\ts into H9XASH\ts with /XO (xash.bat:427-440)
   web client     webclient-build\stage takes H9XASH's ts
   build.bat      does NOT copy sprites into the Steam install. It copies
                  sounds, models, resource and textschemes (build.bat:
                  128-204); the Steam copies come from the generator alone.

 What uses them today: nothing. No plugin source, no reTS client source
 and no engine source names them, and the compiled ts_matchmode.amxx in
 the Steam install and in H9XASH holds tsm_class.spr but neither of these
 (checked by inflating the plugin's code). ts_matchmode.cfg:1057-1078
 records why: a sprite placed in front of the player's eye was tried as a
 menu background and taken out, because a world entity lags every turn
 and swims across the screen. A server plugin cannot draw a picture at
 screen coordinates; a client can, which is what this design does.

 2b. What they are

   file             size     type         frames  format          bytes
   tsm_panel.spr    256x256  VP_PARALLEL  1       SPR_ALPHTEST    66366
   tsm_banner.spr   256x96   VP_PARALLEL  1       SPR_ALPHTEST    25406

 A 256-colour palette of which indices 0-7 and 9 are used; 255, the
 alpha-test key, is not: the surround is filled rather than cut away
 (make-menu-panel.mjs:102-105). Each is a slab of brushed metal (a
 vertical grain, a light falling from the top, a scanline every third
 row) with chamfered corners, a dark two-pixel rim, corner brackets, and
 a rail: down the left of the panel, where a menu's numbers start, and
 along the top of the banner, whose text is centred. Previews of both,
 before and after the recolour: D:\temp\vgui-design (section 9).

 Measured from the frames, in sprite pixels:

                      tsm_panel 256x256        tsm_banner 256x96
   rim                4..251                   x 2..253, y 2..93
   slab               6..249, 23 px chamfer    x 4..251, y 4..91, 10 px
   rail               x 13-17, y 25-230        y 12-14, x 10-245
   brackets, 3 px     arms 36 px: x 29-31 and  arms 16 px: x 14-16 and
                      224-226, y 8-10, 245-247 239-241, y 6-8 and 87-89
   content box        x 36..222, y 16..240     x 22..234, y 18..86
   insets L T R B     36 16 34 16              22 18 22 10
   corner slices      68 x 68                  32 x 32

 The content box is the room inside the rail and brackets where text
 sits. A corner slice is the part of each corner that must never stretch:
 the chamfer, the rim and the bracket's full arm.

 2c. The sprites as panel backgrounds

 The client reads the .spr itself: gEngfuncs.COM_LoadFile, then the
 header, the palette and frame 0, into RGBA, with alpha 0 for index 255
 in an alpha-test sprite and 255 elsewhere, as the engine reads it. From
 that it builds a vgui::Bitmap at the panel's size in pixels, the way
 CAvatarBitmap builds a picture at the size of its cell
 (vgui_ScorePanel.h:239-243, vgui_ScorePanel.cpp:385-480). The resample
 is a nine-slice with nearest-neighbour sampling: the four corner slices
 at the art's scale, the edges stretched along their length, the middle
 both ways. At exactly the art's proportions that is the same as scaling
 the whole image; the rail, rim and brackets stay sharp at any other
 size. Each bitmap is kept for the life of the client, per art and size
 (VGUI1 has no call that frees a texture, so the client reuses them, as
 the scoreboard does with its pictures). Widths are rounded, a menu's to
 8 px and a banner's to 16 px, so few sizes are ever made; past 64 a new
 size draws without its art.

 Why the .spr and not a TGA copy in gfx\vgui: one file, one source. The
 generator stays the only thing that draws the art, and a recolour like
 the one in section 9 reaches the panels with no second file to update.

 The size of a panel comes from its art (the numbers are in 4c):
   1. a scale, s = (screen height / 480) x the client's cl_h9_vgui_scale
      (0.51 for menus, 0.45 for banners by default; 0.68 and 0.60 until
      2026-11-05, and 0.8 and 0.6 in the first design);
   2. the panel starts at the art's own size x s (a menu 256 x 256 x s,
      a banner 256 x 96 x s), and its text goes in the content box x s;
   3. a menu's rows share the content box's height: title, rows, footer;
   4. if they do not fit, the footer goes first, then the fonts step down
      one scheme (Primary Button Text, CommandMenu Text, Scoreboard Text),
      then the panel grows, through the nine-slice, inside the safe area,
      or, on a screen too small for that (a phone's), on down over the
      chat band, so that no row is ever cut off;
   5. a row wider than the box widens the panel the same way; text is
      never squeezed or cut;
   6. a menu with few rows (the side menu has four) keeps the art's full
      square (decision 1, section 7).
 At 1920x1080 a menu is then 294 px square (content 213 x 257 px: twelve
 rows of 21 px, the class menu's maximum), a banner 259 x 97 px.

 3c. Draw order

 FWGS draws the HUD, then all of VGUI, then the H9 splash MOTD
 (xash3d-fwgs engine\client\cl_view.c:578-580). A VGUI panel is therefore
 always over HUD text where the two meet, whatever the client does.
 Putting panels under HUD text would take an engine change that would also
 put the scoreboard and the MOTD under it. So this design keeps panels
 out of the HUD's way instead (4c).

 4. THE DESIGN
 -------------
 4a. Three kinds of thing, one message

   MENU    The VGUI twin of an AMX text menu. The plugin says what is on it
           (a title, rows with their keys and flags, a footer); the client
           lays it out on the tsm_panel art. The AMX menu still runs
           underneath: the reply is "menuselect N", the handler is the one
           the plugin already has, and a client without H9's client.dll
           simply gets the text.
   NOTICE  What a hudmessage says: a slot (which, like a channel, a newer
           notice replaces), text, a colour, hold and fade times and a
           style. The client draws it on the tsm_banner art or as plain
           scheme text, where 4c puts it. It comes up over 0.35 s when
           it appears, holds, and fades out over its fade; a notice that
           replaces one still showing keeps the first one's rise, so a
           bar sent every tick does not come up again each time.
   STATUS  A notice that stays until its slot is replaced or cleared,
           stacks first from the top of the safe area, and counts its own clock
           down: {t} (m:ss) and {s} (seconds) in its text, from the one
           message (protocol 2).
   MARK    A point of the world drawn on the screen through the walls, and in
           a row under the top notices (protocol 3, section 4i).
   PANEL   Any layout: a panel and its controls, each by id. Labels,
           images, buttons, a progress bar, a text entry. The reply is a
           client command, "h9vgui <panel> <control> <value>", that the
           plugin registers.

 The match mode's side and class menus are MENUs; its round line, the
 freeze countdown, the warmup readout and a round's result are one
 STATUS, the match bar (4g); the rest of 1b are NOTICEs; PANEL is what a
 plugin author uses for anything else.

 4b. The message: H9Vgui

 Registered by every plugin that uses it, in plugin_precache:
     g_h9vgui = engfunc(EngFunc_RegUserMsg, "H9Vgui", -1);
 The engine gives every plugin the same id for the same name (FWGS
 engine\server\sv_game.c:3500-3504), and the client learns it at connect
 because it is registered while the map loads. Sent only with fakemeta,
 one player at a time:
     engfunc(EngFunc_MessageBegin, MSG_ONE, g_h9vgui,
         Float:{0.0, 0.0, 0.0}, id);
     ... write_byte / write_short / write_char / write_string ...
     message_end();
 Metamod-R does not record a plugin's messages, so AMX Mod X's own
 message_begin refuses them (ts_matchmode.sma:4083-4087, h9_motd.sma:72-74,
 board_sync() at ts_matchmode.sma:19287 does exactly this). Never MSG_ALL
 or MSG_BROADCAST: only a player whose userinfo has _h9vgui gets one.

 Size: at most 188 bytes a message. GoldSrc's user messages stop at 192
 (FWGS allows 2048, engine\common\common.h:137), and staying under it
 keeps the protocol right for an HLDS server too. The include splits what
 is longer.

 Every message starts with a byte, the op. Ids are 1-23 characters of
 a-z 0-9 . _ -, written "<plugin>.<name>" (tsm.side, tsm.class, rtv.vote,
 h9c.portal); the part before the dot is the plugin's own (4e). A new
 MENU, PANEL or NOTICE with an id that is already up replaces it.

  op  name    then
   1  MENU    string id, short keys (bit 0 = key 1 ... bit 9 = key 0),
              char time (-1 none, else seconds), byte style (0 panel art,
              1 banner art, 2 no art), byte flags (1 asks for the mouse,
              4d; 2 the client numbers the rows itself), string title,
              string footer
   2  ROWS    string id, byte count, then per row: byte key (1-10, 0 for a
              row without a key), byte flags (1 dim but pressable, 2 red,
              4 a gap above, 8 highlighted, 16 not pressable), string
              label (31 at most), string detail (31 at most). Rows append
              in order; a long menu takes several ROWS messages.
   3  TWIN    string id, short keys, short crc. Sent right before every
              show_menu() of that menu: see the pairing rule below.
  10  PANEL   string id, byte flags (1 modal: wants the mouse; 2 stays
              open over death and respawn), byte anchor (4c), short x,
              short y (offset from the anchor), short w, short h (0 = the
              art's own size), string art ("" none, "#panel", "#banner",
              or an image path, 4d), byte timeout (seconds, 0 none).
              Lengths are virtual units: 1/480 of the screen height, times
              the panel scale.
  11  CTRL    string id, byte control (1-48), byte type (1 label, 2 image,
              3 button, 4 progress, 5 entry), byte anchor (within the
              panel's content box), short x, y, w, h, byte font (0 text,
              1 title, 2 detail, 3 flash), byte align (0 left, 1 centre,
              2 right), byte r, g, b, a (a 0: the scheme's colour), byte
              flags (1 hidden, 2 disabled), byte key (0, or the number
              key 1-10 that presses it), string text (a button's or
              label's text, an image's path, an entry's first text)
  12  SET     string id, byte control, byte what (1 text: string;
              2 visible: byte; 3 enabled: byte; 4 value: short 0-1000;
              5 colour: four bytes; 6 image: string)
  13  SHOW    string id
  14  HIDE    string id
  15  CLOSE   string id ("<plugin>.*" closes all of that plugin's)
  16  COMMIT  string id. A PANEL and its CTRLs are drawn only once COMMIT
              arrives, so a panel never shows half-built, and a rebuilt one
              swaps in whole.
  20  NOTICE  string slot (an id), byte style (0 text, 1 banner art,
              2 flash, 3 bar), byte anchor, short y (offset), byte r, g,
              b, byte hold and byte fade (tenths of a second), short value
              (0-1000 for a bar, else -1), string text ("^n" breaks lines,
              160 bytes at most)
  21  STATUS  string slot, byte style (as NOTICE), byte r, g, b, short
              clock (seconds, -1 none), string text, its {t} and {s}
              the clock. Protocol 2. An empty text clears the slot.
  22  MARK    byte slot (1-32; 0 takes every mark down), byte owner (0
              nobody, 1 and 2 a side, 3 takes the slot's mark down), byte
              state (0 quiet, 1 being taken, 2 contested), byte side taking
              it, byte pct (0-100), short x, y, z (the world's, in units),
              string label (7 characters). Protocol 3.

 The client answers with exactly two commands, and nothing else:
   menuselect N      from a MENU: its number keys and, when it has the
                     mouse, a click on a row. The same command, through the
                     same CHudMenu::SelectMenuItem (menu.cpp:222-235), that
                     the text menu sends.
   h9vgui <id> <control> <value>
                     from a PANEL: a button (value 1); an entry, on Enter or
                     its button (value: the text); control 0 with "close"
                     when the player closed the panel (ESC or its close
                     button). Sent with gEngfuncs.pfnServerCmd, straight to
                     the server, never through the client's own command
                     buffer, so nothing a server wrote can run on the
                     client. The id is the one the client accepted (only
                     a-z 0-9 . _ -); typed text loses quotes, semicolons
                     and control characters and stops at 63 characters.

 How a client says it can draw them: userinfo _h9vgui, the protocol
 version: "1" for all but STATUS, "2" with it (the client of
 2026-11-03's match bar build), "3" with MARK too (2026-11-05). A plugin
 sends a STATUS only to a game of protocol 2 or more (h9vgui_status says
 whether it did) and a MARK only to a game of protocol 3 (h9vgui_mark), and
 the rest keep the hudmessage or what the plugin gives them instead. The client registers it as a FCVAR_USERINFO cvar; FWGS puts
 such a cvar into the userinfo as soon as it exists (engine\common\
 cvar.c:463, from pfnCvar_RegisterClientVariable at engine\client\
 dll_int\cl_game.c:1753), and sends the change when it is set. It reads
 "0" while the player has cl_h9_vgui 0. A plugin reads it with
 get_user_info(id, "_h9vgui", ...), as h9_community reads _h9travel
 (h9_community.sma:1838), each time it is about to send, so a change is
 seen at once. A bot never has it. (h9_motd's test, the h9_clientid key,
 says which ENGINE a player runs, not whether his client.dll can draw
 panels: the wrong test here.)

 The pairing rule: a MENU and its AMX menu.
 AMX Mod X keeps ONE menu per player: the last show_menu() or
 menu_display() decides where his next menuselect goes. The match mode
 already lives by this: its side menu waits while the RTV vote is up
 (rtv_holds_side_menu, ts_matchmode.sma:3292-3302). So the client must
 show the panel only while the AMX menu it stands for is the one the
 server would answer:
   1. The plugin sends MENU and ROWS when the menu's content changes, and
      TWIN immediately before every show_menu() of it: the menu's id, its
      keys and the CRC-16/CCITT-FALSE (polynomial 0x1021, start 0xFFFF)
      of the exact text it passes to show_menu().
   2. The client puts the TWIN aside. When the next ShowMenu has arrived
      whole (CHudMenu puts its parts together, menu.cpp:262-282), it
      compares the keys, and the CRC of the text as received. Both equal:
      the panel shows and CHudMenu draws no text. Anything else: no panel,
      and the text menu draws as it always has.
   3. Every later ShowMenu decides again. One with no keys (how
      drop_class_menu and task_vote_end take a menu down), a menuselect,
      or the menu's time running out closes the panel with the text menu.
      Another plugin's menu, or AMX Mod X's own admin menus, have no TWIN,
      so they close the panel and draw as text.
   4. The re-offers that ts_matchmode makes every second send only TWIN
      plus the ShowMenu, about 30 bytes more than today; MENU and ROWS go
      again only when a row changes (a class filling up).
 The fallback is in the rule. A client without H9's client.dll never gets
 H9Vgui and draws the text. An H9 client whose panel cannot be built (the
 art missing, say) draws the text too, because CHudMenu still has it.
 With cl_h9_vgui 0 the server sends no H9Vgui at all.

 4c. Placement: keep clear of the HUD's text

 FWGS draws VGUI after the HUD (3c), so a panel would cover any HUD text
 under it. The client keeps every server panel inside a SAFE AREA, with
 bands taken out where the HUD writes, in pixels as the client sees the
 screen:

   top margin   0 to 16 px (1.5% of the height, 8 at least), the full
                width: the stack of notices and the panels anchored along
                the top start there. TS's own notices start at 32 px and
                come 16 px lower for each live one (ts_message.cpp:
                75-103); while the stack shows something they are drawn
                beneath it (H9Vgui_StackBottom, CHudTSMessage::Draw), else
                they keep their place. The round time (top right) and the
                powerup label (top left) are corner text the centred stack
                does not meet. cl_h9_vgui_top changes the margin. A panel
                anchored along the top counts as part of the stack only
                when it is in the top quarter of the height and reaches into
                the middle half of the width; one pinned to a corner that
                stops short of that (the Officer's waiting list, at the top
                right) sits beside the stack and pushes nothing down, so the
                row of marks and TS's notices keep their place as it grows.
   bottom band  the full width, from 10 px above the chat's top, which is
                H - 60 - 7 x the HUD font's height (saytext.cpp:248): 196 px
                with the stock 18 px font. It also holds TS's bottom
                notices at H-64, the status bar, the health, team and
                powerup boxes.
   crosshair    W/2 +-12% of the width, H/2 +-6% of the height. No passive
                panel covers it; the teammate readout (0.56) and the plant
                and zone bars sit by it as HUD text.
   centre column  the middle half of the width between 0.19 and 0.40 of
                the height: admin csay (0.19-0.27), imessage (0.20), the
                engine's centre print (0.25), the TS stats plugin's
                grenade, headshot and double kill lines (0.25-0.35), and
                adminchat's @@ (0.29-0.37). Only a banner anchored at the
                top edge of the safe area enters it, and never past 0.25
                of the height (see Default placement).

 Anchors: TL T TR, L C R, BL B BR (0-8), relative to the safe area: T is
 centred along its top, L is 16 px from the left edge and centred on
 the safe area's height, and so on. x and y move the panel from its
 anchor, in virtual units. Whatever a plugin asks, the client clamps the
 result into the safe area (moving it, then shrinking it), keeps passive
 panels off the crosshair box, and never lets a passive panel be larger
 than 45% of the width or 55% of the height (a modal one 90% and 80%).

 Default placement, at 1920x1080 for the numbers:
   menus      L: the left column, 16 px in, as the AMX text menus are. The
              top at 0.34 of the height (the text menu's top is about
              there, menu.cpp:171, and it clears the TS stats plugin's
              "who killed you" card, 0.15 to about 0.33 on the left), then
              moved up, never above the top margin, if the bottom would
              reach the bottom band. 461 px square: 367 to 828 px.
   banner     T: centred, its top edge on the top margin, 346 x 130 px:
              16 to 146 px. Its bottom stays above 0.25 of the height
              (270 px here), where the centre print and the stats lines
              start: on a smaller screen the banner's scale comes down to
              keep it there, to half the art's size at least.
   notices    under the banner, one below another, newest last (LIVE
              and SUDDEN DEATH are banner notices); a FLASH (WAVE n) in the
              same column; a BAR (the satchel and zone) at its hudmessage's
              place, 0.47, just above the crosshair box, because it
              answers the player's own +USE.
   TS's       beneath the stack: the top row of TS's own notices, which
   notices    start 32 px down, is drawn from the stack's bottom edge
              (+4 px) while the stack shows something, else where TS
              puts it.
   panels     where the plugin anchors them, inside the safe area.
 What the defaults still meet: the left column overlaps adminchat's
 amx_tsay and "say @" lines (left, 0.64-0.72), and the centre column's
 messages when a host enables the stats plugin; a seventh TS notice in
 one burst would draw under the banner. Section 7 asks about these.

 4d. Input, safety and limits

 A server is untrusted to the client. The client holds to these,
 whatever a message says:

   Input      A PASSIVE panel (the default, and every MENU unless the
              player allows the mouse) takes no cursor and no keyboard.
              Its number keys reach it the way they reach a text menu
              today, through the slot commands; nothing else is read.
              A MODAL panel shows the cursor, like TS's team menu, and
              takes its own controls' clicks, the number keys and ESC; the
              movement keys still move. One modal at a time; the player's
              cl_h9_vgui_mouse 0 makes every panel passive. This client
              keeps every panel passive, a modal one too (decision 2,
              section 7): no cursor at all. A text entry
              takes keys only after the player clicks into it, and lets
              go on Enter, ESC or a click elsewhere. A server can never
              give focus, read a key, change a binding or run a command.
   ESC        always closes the newest server panel (TeamFortressViewport::
              KeyInput, kept from the engine, 3b), before the game menu
              opens; a second ESC opens it as ever. Closing a MENU this
              way sends nothing (its AMX menu runs out on the server as
              an ignored text menu would; a 0 key would be wrong, since
              on a ten-class map 0 is the tenth class); closing a PANEL
              sends "h9vgui <id> 0 close".
   Opt-out    cl_h9_vgui 0 closes every panel, refuses all H9Vgui, and
              turns _h9vgui to "0" so servers stop sending.
   Images     The two built-in arts, "#panel" and "#banner", are
              sprites\tsm_panel.spr and sprites\tsm_banner.spr. Any other
              image: a .tga or .spr; a path in lower-case a-z 0-9 _ . - /
              under gfx/vgui/, sprites/ or resource/; no "..", no leading
              slash, no drive, no backslash; at most 512 x 512 pixels and
              1 MB; at most 16 different images a map. And only the game's
              own files: the client asks filesystem_stdio's
              VFileSystem009::GetLocalPath (xash3d-fwgs filesystem\
              VFileSystem009.h:107) where the file was found, and refuses
              one under ts_downloads, the folder FWGS mounts for downloads
              (filesystem\searchpath.c:376-377). Nothing is ever fetched
              for a panel. This client draws the two built-in arts and
              nothing else; other images, with that test, come with a
              later build, and a text entry too (decision 8).
   Limits     8 server panels open at once, 48 controls a panel, 16 rows
              a menu; ids 23 characters, labels 63, a menu row's label and
              detail 31 each, a notice 160; a message over 192 bytes, or
              one that reads past its end, is dropped whole; at most 64
              H9Vgui messages a second are read (the rest dropped, and
              said once in the console).
   Text       drawn as text, never interpreted; a "#token" is looked up in
              titles.txt, as menu and HUD text already are; characters
              below 32 other than line breaks are removed.
   Lifetime   every server panel closes at a disconnect and a map change
              (TeamFortressViewport::Initialize, 3a); a passive one hides
              while the scoreboard is up (as CHudMenu does, menu.cpp:
              149-151), during intermission, and with the HUD hidden; in
              demo playback panels show but never take the mouse.

 4e. The plugin side

 One include, include\h9_vgui.inc, of stocks; nothing to load first.

   h9vgui_precache()          in plugin_precache: registers H9Vgui
   h9vgui_init("ns")          in plugin_init: this plugin's ids are ns.*,
                              and it registers the "h9vgui" command
   bool:h9vgui_supported(id)  _h9vgui >= 1, not a bot, the message
                              registered, h9_vgui 1 on the server
   MENUs
   h9vgui_show_menu(id, keys, const text[], time, const amx[], const panel[],
                    const title[] = "", style = 0)
       The one-line change: in place of show_menu(). It reads the rows out
       of the text itself: "N." starts a row, a \d row is dim, \r red,
       the lines before the first row are the title unless one is given,
       and two spaces or a \d split a row's label from its detail.
       It sends MENU, ROWS and TWIN to an H9 client, then calls
       show_menu() for every client.
   h9vgui_menu_begin(const panel[], const title[], style = 0)
   h9vgui_menu_row(key, flags, const label[], const detail[] = "")
   h9vgui_menu_send(id, keys, const text[], time, const amx[])
       The same, built row by row, for a plugin that has the parts at
       hand (the class menu does).
   NOTICEs
   h9vgui_notice(id, const slot[], style, const text[], Float:hold,
                 Float:fade, r, g, b, Float:x = -1.0, Float:y = -1.0,
                 channel = -1)
       To an H9 client a NOTICE; to any other, the set_hudmessage and
       show_hudmessage it replaces, with the same text, colour, place and
       channel. id 0 goes to every player, each the right way.
   h9vgui_notice_bar(id, const slot[], const text[], permille, r, g, b, ...)
   h9vgui_alert(id, const slot[], style, const text[], r, g, b,
                Float:y, Float:hold, Float:fade)
       For what was a set_hudmessage and a show_hudmessage pair: call
       set_hudmessage for the old look as before, then this. An H9
       client gets a NOTICE with that colour, y, hold and fade; any
       other the show_hudmessage, so its old look is exactly what it

   PANELs

 Callbacks. h9vgui_init() registers the client command "h9vgui" to a
 public the include defines. It reads <id> <control> <value>, returns
 PLUGIN_CONTINUE for an id outside the plugin's own namespace (so the
 next plugin's handler gets it) and otherwise calls the plugin's
     public h9vgui_event(id, const panel[], ctl, const value[])
 through callfunc_begin("h9vgui_event") on the plugin itself, then returns
 PLUGIN_HANDLED. That is the forward-like helper: each plugin gets only
 its own panels' events. The include drops a player's commands past ten
 a second. Like any client command it can arrive at any time, forged or
 late, so the plugin checks its own state before acting on it, as
 class_menu_key does with may_pick_class (ts_matchmode.sma:3616).

 Server switch: h9_vgui (1), registered by the first plugin that includes
 the stocks; 0 sends no H9Vgui at all, so every player gets text.

 Would an AMX Mod X module add anything a Pawn include cannot?
 Nothing that is needed. A module could take arrays in its natives, keep
 one table of open panels for every plugin, and catch every show_menu()
 in the core to send twins for plugins that were never changed. Stocks
 do the first well enough; a hub plugin, h9_vgui.amxx with natives and a
 real multi-forward, would do the second if many plugins come to share
 the system (not now: decision 6); and the third is better done by the
 client, which could skin any AMX text menu from its text with no server
 change at all (not now: decision 3).

 Is the engine needed? No. Each thing the system relies on is already
 there:
   ESC first to the client         in_keys.c:749-771 (3b)
   messages from plugins           engfunc and sv_game.c:3500-3504; H9Board,
                                   H9Link and H9Lives prove it
   the userinfo flag from client.dll cvar.c:463, cl_game.c:1753
   telling ts_downloads apart      VFileSystem009::GetLocalPath
   keys for a text entry           VGui_KeyEvent, in_keys.c:767
 Two things only the engine could change, and this design does without:
 drawing VGUI under HUD text (cl_view.c:578-580: it would move the
 scoreboard and the MOTD too), and, if the web client's build has no
 filesystem_stdio interface to ask, the downloads test, which an engine

 4i. The capture points' marks (MARK, protocol 3)

 A MARK is a point of the world a mode wants every player to know of, wherever it is and
 whatever stands between: ts_assault sends one for each of its capture points, ts_uplink one
 for each zone and one for the uplink (UPLINK, CARRIER over whoever has it, DROPPED where it
 lies), ts_ctf one for each flag (FLAG, CARRIED, DROPPED with a bar draining to the moment it
 flies home) and each pad (BASE). The three share include\h9_marks.inc, which keeps the table of
 marks, sends a mark when what it shows changes, refreshes two a second and gives a game with
 no marks TS's own objective markers. The client
 draws it where the point lands on the screen (pTriAPI->WorldToScreen), so through any wall
 or floor, and keeps it on the screen's edge, in its direction, while it is out of view or
 behind the player. A player sees every mark whatever they are doing: living, dead or
 spectating.
   the badge       a square of 30 x (screen height / 480) x cl_h9_vgui_scale x 0.5 px
                   (22 px on a 708 px screen, 33 at 1080), framed in the owner's colour,
                   dark inside, the label in white: blue (0 170 255) for side 1, red (255 70
                   60) for side 2, grey (225) for nobody; the frame blinks yellow (255 220
                   80) while the point is contested. A bar under it, in the colour of the
                   side taking the point, fills as pct. Out of view the badge is three
                   quarters the size and fainter, pinned to the edge.
   the row         from two marks, the same badges in a row at the top of the screen under
                   the notices, centred, so the whole map's points are always in one place.
                   TS's own notices go on beneath the row (H9Vgui_StackBottom).
   when it shows   not with cl_h9_marks 0, not with the HUD hidden (nohud), not under the
                   scoreboard, not in an intermission. cl_h9_marks_strip 0 takes the row
                   away and leaves the badges in the world.
   how long        a mark lives 30 seconds without a message for its slot, and every new map
                   or server clears them all: a plugin sends again, as h9_marks.inc does at
                   once when a mark changes and two marks a second in turn the rest of the
                   time, so a game that joined late has them all within seconds.
 Plugin side: h9vgui_mark(id, slot, owner, phase, side, pct, const Float:at[3], label)
 in include\h9_vgui.inc; it sends nothing to a game of protocol 2 or less and says so, and
 h9_marks.inc gives that game TS's own Objective marker instead (a compass icon and the label
 text at the point, drawn where TS draws objectives). No game gets both.

 6. RISKS
 --------
   * One AMX menu per player. Anything that shows another menu (another
     plugin, AMX Mod X's admin menus) takes the keys; a panel left up
     would then send its menuselect to the wrong handler. The pairing rule
     (4b) closes the panel on any ShowMenu without its TWIN.
   * Bandwidth. A class menu's MENU and ROWS come to about 700 bytes, once
     per player per change; the re-offers add a 30-byte TWIN to today's
     ShowMenu, and the round banner about 70 bytes a second for each H9
     player. Keep ts_matchmode's one-menu-a-frame spread (21004-21018):
     a burst of reliable menus has dropped clients with svc_bad before.
   * Overlap that placement cannot avoid: on a screen under about 600 px
     tall the banner, at half size, still meets the 0.25 band; a seventh
     TS notice in one burst; the left column against adminchat's tsay
     and "say @" lines (4c); on a phone's screen a long menu over the
     chat band.
   * A notice of four lines, the freeze countdown, does not fit the band
     above 0.25 of the height at a readable size (134 px at 1080): its
     fonts step down to Scoreboard Small Text. Step 4 has to send it as
     two lines, or let that banner pass the line.
   * Moving targets. ts_matchmode.sma changed twice while this was being
     written (the numbers here are of 1.54-gameplay7, 20:01), and cl_dll
     at 16:40: the line numbers drift, the function names do not.
   * reTS's swap contract. H9Vgui, the h9vgui reply and the cl_h9_vgui
     cvars are additions to TS's client, as the scoreboard's H9 messages
     are, and coverage.py will report the cvars as EXTRA. A stock client
     never receives H9Vgui, because it never sets _h9vgui.
   * FWGS paths not yet exercised by reTS: typing into a VGUI1 TextEntry
     (VGui_KeyEvent), the art bitmaps' texture memory (VGUI1 frees no
     texture, so they are kept per size, 64 at most), textures that are
     not powers of two (a 461 px panel; round up if a renderer needs it).
   * The web client: the browser draws the fonts (Arial, not Square 721),
     and it may have no filesystem_stdio interface for the downloads test
     (4e). Both are worth one run before the web client ships it.
   * The two new menus (legend, nominations) stay text (decision 3).

 8. FOR PLUGIN AUTHORS: A SHORT GUIDE
 ------------------------------------
 (This part is also the head of include\h9_vgui.inc. Both ship in the
 repository: export.bat carries docs\ into the git mirror (export.bat:770),
 and the include once it has copy lines beside tsm_api.inc's (89-91,
 229-231).)

 What you get: on the screen of a player running H9XASH with H9's
 client.dll, a real VGUI panel, in H9's purple art and the game's own
 fonts, that you build from your plugin. Every other player gets what you
 send them as text. Nothing to install on the server but the include.

 The rules
   1. Register in plugin_precache with h9vgui_precache(), and name your
      namespace in plugin_init with h9vgui_init("yours"). Your ids are
      then "yours.<name>": 23 characters at most, a-z 0-9 . _ -.
   2. Send only through the stocks. They use engfunc(EngFunc_MessageBegin,
      MSG_ONE, ...) (AMX Mod X's message_begin refuses a plugin's message
      under Metamod-R), keep each message under 188 bytes, and send
      nothing to a player whose client cannot draw it.
   3. Have a fallback. A menu through h9vgui_show_menu() and a notice
      through h9vgui_notice() fall back to text by themselves. For a
      PANEL, test h9vgui_supported(id) and give everyone else a menu or a
      chat line.
   4. Placement. Anchor your panel (H9V_TL ... H9V_BR); anchors are
      relative to the client's safe area, and the client moves anything
      that leaves it back inside. The safe area starts at the top of the
      screen (a 16 px margin at 1080; TS's kill notices, "is The
      Specialist" and the sprees, are drawn beneath what the top of it
      holds) and ends 196 px above the bottom (chat, TS's HUD). Leave
      the crosshair alone, and the centre column between 0.19 and 0.40 of
      the height to the HUD's centred messages; a banner anchored H9V_T
      sits at the top margin. A menu goes in the left column, as
      AMX text menus do.
   5. A panel is passive unless you set the modal flag: no cursor, its
      number-key buttons and nothing else. Ask for the mouse only for
      something the player asked for. ESC always closes a panel, and the
      player may refuse the mouse, or every panel.
   6. Images: "#panel", "#banner", or the game's own .tga and .spr files
      under gfx/vgui/, sprites/ or resource/. Nothing else loads, and
      nothing is ever downloaded for a panel.
   7. A reply is a client command, "h9vgui <id> <control> <value>", that
      reaches your public h9vgui_event() for your own ids only. Anyone can
      type one at any time: check your own state before acting on it.
   8. Build once, update small: send a panel once, then h9vgui_set_*();
      a re-offered menu costs a 30-byte TWIN while its rows stay the same.
   9. Test with cl_h9_vgui 0 and with a game that is not H9XASH.

 A worked example: a ready check
 -------------------------------
   #include <amxmodx>
   #include <fakemeta>
   #include <h9_vgui>

   #define RC_MENU  "RC Ready"   // the AMX menu, as register_menuid names it
   #define RC_PANEL "rc.ask"     // a panel of this plugin's namespace, "rc"

   new bool:g_ready[MAX_PLAYERS + 1];

   public plugin_precache()
   {
   	h9vgui_precache();
   }

   public plugin_init()
   {
   	register_plugin("Ready Check", "1.0", "you");
   	h9vgui_init("rc");
   	register_menucmd(register_menuid(RC_MENU), (1 << 0) | (1 << 1),
   		"rc_key");
   	register_clcmd("say .rc", "cmd_rc");
   	register_clcmd("say .rcpanel", "cmd_rc_panel");
   }

   // 1. A MENU: one call where show_menu() was. Every player gets the AMX
   //    menu; an H9 player sees it on the panel art. rc_key answers both.
   public cmd_rc(id)
   {
   	h9vgui_show_menu(id, (1 << 0) | (1 << 1),
   		"\yReady for the next round?^n^n1. Ready^n2. Not yet", 15,
   		RC_MENU, "rc.menu");
   	return PLUGIN_HANDLED;
   }

   public rc_key(id, key)
   {
   	g_ready[id] = (key == 0);
   	return PLUGIN_HANDLED;
   }

   // 2. A PANEL: a banner at the top, a question and two buttons
   //    on the 1 and 2 keys. A player who cannot draw it gets the menu.
   public cmd_rc_panel(id)
   {
   	if (!h9vgui_supported(id))
   	{
   		return cmd_rc(id);
   	}
   	h9vgui_panel(id, RC_PANEL, 0, H9V_T, 0, 0, 0, 0, "#banner", 15);
   	h9vgui_label(id, RC_PANEL, 1, H9V_T, 0, 4, 200, 20,
   		"Ready for the next round?", H9V_FONT_TITLE, H9V_CENTRE);
   	h9vgui_button(id, RC_PANEL, 2, H9V_BL, 8, -6, 90, 20, "Ready", 1);
   	h9vgui_button(id, RC_PANEL, 3, H9V_BR, -8, -6, 90, 20, "Not yet", 2);
   	h9vgui_commit(id, RC_PANEL);
   	return PLUGIN_HANDLED;
   }

   // "h9vgui rc.ask <control> <value>": only this plugin's ids come here.
   public h9vgui_event(id, const panel[], ctl, const value[])
   {
   	if (!equal(panel, RC_PANEL))
   	{
   		return;
   	}
   	if (ctl == 2 || ctl == 3)
   	{
   		g_ready[id] = (ctl == 2);
   		h9vgui_close(id, RC_PANEL);
   	}
   }

 What happens: say .rc shows the menu, as text for most players and on
 the purple panel for an H9 player, who presses 1 or 2 either way, and
 rc_key() gets the key. say .rcpanel shows an H9 player the banner
 at the top with two buttons (keys 1 and 2; clickable only if
 he allows the mouse); his choice comes back through h9vgui_event(). ESC
 closes either and sends "h9vgui rc.ask 0 close" for the panel.
