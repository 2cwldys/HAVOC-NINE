SHIPPING A VERSION OF HAVOC 9 -- the whole run, in order, for the next agent
=============================================================================

Written 2026-11-15 after build 1.63. docs\H9_RELEASE.txt says what a release IS (the gate, the build number, the hashes); this says how to
RUN one from the last feature to the verified site. Run it ONCE per batch, after the last feature has its own Windows build and checks.
Never push; no Co-Authored-By line; commits only when the owner says "stage" or "commit" (CLAUDE.md).

0. BEFORE ANYTHING
------------------
- The owner's game must be closed. Never launch or kill a game while they play; ask, or look at the process list (do not probe their PC beyond it).
- ONE heavy job at a time. release-prepare.mjs, build-linux.cmd and export.bat take D:\temp\HEAVY-JOB.lock THEMSELVES. Never create that file yourself
  "to be safe": the job then waits for your lock (release-prepare waits up to 90 minutes, build-linux refuses). 2026-11-15 lost 25 minutes to that.
- ASCII only in every command and file you write (an em dash breaks the Bash call), temp files in D:\temp, no recursive grep over TSM, run .bat files as
  MSYS_NO_PATHCONV=1 cmd /c "<full path> < NUL > <log> 2>&1". Edit CRLF files with an exact-replace helper (python, read bytes, replace, write bytes), not sed -i.
- D:\Downloads\TSM is the master tree (build.bat, export.bat, release-prepare.mjs live there). D:\GIT Storage\ts_h9_team_elimination is the git copy
  that the ZIPs, the web client and the site are made from.

1. THE ORDER (what ran for 1.63; ~45 minutes of machine time)
-------------------------------------------------------------
 a. Engine changed?  xash.bat engine. Every rebuilt xash.dll / ref_gl.dll / h9webview.dll needs its .dll.patch note (history block, size, SHA-256).
 b. reTS (client or game DLL) changed?  reTS\scripts\build-win32-dropin.ps1 with RETS_REBUILD=1 (PowerShell 7, ~20 s incremental). It OVERWRITES
    reTS\binaries\ts\...\client.dll.patch and mp.dll.patch with old release notes: save the notes first (D:\temp), restore after, then edit the client
    note (Size, SHA-256, a new numbered item) and copy client.dll + note to reTS\binaries, H9XASH\ts\cl_dlls in the master AND the git copy.
    The master's reTS and the git copy's reTS must be the same source before this (2026-11-15: the git copy held the rally mode, the master did not;
    compare with diff -rq reTS and merge by hand, never by time stamp: some files are newer in the git copy, some in the master).
 c. Plugins:  from D:\Downloads\TSM run
       node tools\release-prepare.mjs --auto --state "D:\GIT Storage\ts_h9_team_elimination\dist\.release-state.json"
    It compares the compiled plugins with the state file, raises VERSION in ts_matchmode.sma by one when any changed, runs build.bat and export.bat
    (log D:\temp\release-prepare-build.log / -export.log, ~10 minutes) and writes the four official presets. Run from the git copy it refuses (no build.bat).
    If it says "kept 1.xx" the compiled plugins did not change: build.bat has to run FIRST for new .sma code.
 d. Linux:  build-linux.cmd (no -Stage), then export.bat again so H9XASH-linux reaches the git copy.
 e. Web client:  node tools\webclient-sync.mjs  (rebuilds the wasm engine and client, lays the stage out, runs a headless-browser smoke test), then
    node tools\webclient-sync.mjs --check in the master AND in the git copy (both must say "up to date"). "out of date ... client" in the git copy means its
    reTS differs from the master's. A "refusing: these must never be served" line means a PC-local file (cacert.pem, ids, keys) is in H9XASH: add it to
    make_webclient_game.py's SKIP_NAMES, never to the allowed list.
 f. Deliver, from the git copy, PowerShell 7:  .\deploy-vps.ps1   (log it: *> D:\temp\h9vps\deploy_xx.log)
    It runs stage-h9xash.ps1 (ZIPs, updater files in dist\files, release-prepare keeps the build), makes the host packages (site, h9web, server list),
    builds the preset bundle (tools\preset_bundle.py), plans the delta, uploads in 6 parallel scp streams (~5 MB/s, a normal release sends 100-300 MB),
    and runs C:\havoc9\receive-deploy.ps1 on the host. packaging.ini switches each part. First it refreshes the host's OWN receive-deploy.ps1 and
    delta.py when they differ (an older receiver meets a newer delivery otherwise).
 g. Verify (section 2), then stage the commits (section 5).

2. VERIFY THE SITE (all of it, every time)
------------------------------------------
- deploy log ends "everything is up", exit 0; all services Running; "code as installed: unchanged since the last install".
- ssh havoc9-vps "type C:\havoc9\site\downloads\.build"  ->  the build number.
- https://havoc9.org/files/manifest.json (needs header X-H9-Updater: 1 and a user agent starting H9XASH-Updater/) says "build": "<build>".
- https://havoc9.org/downloads/files/ holds H9XASH-<build>.zip, H9XASH-linux-<build>.zip, H9XASH-linux-server-<build>.zip, H9XASH-Updater-<build>.exe.
- The server list bot's About Me names the build WITHOUT a restart: serverlist.ini on the host has build_file = C:\havoc9\site\downloads\.build and the bot
  re-reads it every few seconds; its log (C:\havoc9\data\serverlist or logs\havoc9-serverlist_*.out.log) says "About Me now names H9XASH <build>".
  The status line never carries the build. If the bio is old, .build was not written (the deploy stopped early).
- The official plugin list (preset) was imported by the same deploy ("the official plugin list" step); an official server must show "ok / the official preset".
- The server browser and https://havoc9.org/api/servers answer (empty is fine when no server is up).

3. HOW THE UPDATER WORKS (what the owner and a player see)
----------------------------------------------------------
H9XASH-Updater.exe asks https://havoc9.org/files/manifest.json (every file of the current build with its SHA-256), compares it with the player's H9XASH
folder, downloads only the files that are new or changed (a changed file is fetched whole, named by its SHA-256, verified, resumable), swaps them in by
atomic rename with a rollback copy, and never touches the player's own files (configs, ids, saves, networking.ini, cacert.pem; its skip lists are the
stage script's). No git, no LFS. Its only cache is a folder beside the player's H9XASH. Its certificate list (h9tls.py) is the bundled Mozilla one first,
the Windows store second. A new release replaces the site's copy: only files the host lacks are uploaded.

4. PITFALLS THAT COST TIME
--------------------------
- The host's SSH shell is cmd: no pipes or && inside the ssh string; use certutil -hashfile, dir /b, type. Native-command stderr under
  $ErrorActionPreference = Stop kills PowerShell child calls (the receiver wraps them in Invoke-Child / Invoke-Delta).
- game.havoc9.org must stay an IPv4-only, grey-cloud name: Cloudflare answers havoc9.org over IPv6 and cannot be told not to; servers enroll and
  heartbeat (curl -4) through game.havoc9.org.
- Hard links in C:\havoc9\store are unsafe: delta.py copies.
- A blob can be in the store but not in site\files (the same file is inside a client ZIP and is also an updater file): receive-deploy step 6 copies it.
- A plugin rebuild changes its hash even with no code change (amxxpc is not deterministic): build only what changed, or the preset list goes stale.
- An admin import of the preset needs the owner's word once ("Just do it") on this machine's permission classifier; do not retry around it.
- Never run stage-h9xash.ps1 --here . to test it: the stage bumps the build, builds and exports. Test in isolation.
- A game server run from the git-copy root loads h9_presence and enrolls to the real site: use a private copy without it for rigs.
- export.bat copies with robocopy /XO (a file NEWER in the git copy is kept). After a branch switch every file there is "newer", so a stale file can
  survive an export: the mirror check lists "differs" files; compare the content and copy the master's file by hand where the master is the newer work.

5. COMMITS (only after the owner says so; never push)
-----------------------------------------------------
Split by topic: engine, client, web client, deploy scripts, the release (plugins, presets, VERSION.txt, the download page). A file that carries two topics
(docs\COMMANDS.txt) is split by hunk. Left uncommitted on purpose: runtime noise (ts\settings.scr, user.scr, rcbot\*.rld and botprofiles, README.txt).
The method that worked: a plan script that builds each commit on a throwaway index with git commit-tree, checks that the final tree equals the working
tree for the planned paths, rejects any message with a credit line or a non-ASCII character, and moves the branch with update-ref compare-and-swap;
rehearse first, then apply. (D:\temp\h9vps\p_commit_batch5.py and p_commit_163.py are the templates.)

6. RECOVERY
-----------
- A deploy that stops midway can simply be run again: delivered files are checked by SHA-256 and only missing ones are sent.
- The host's own start/stop: C:\havoc9\start-all.ps1 / stop-all.ps1 (desktop shortcuts Start, Stop, Restore, Backups), restore-backup.ps1 for the
  package installer's backup (taken before every install; settings, keys and data are kept).
- Host logs: C:\havoc9\logs\deploy-*.log (every receive-deploy run).
