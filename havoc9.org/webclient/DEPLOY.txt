===============================================================================
 HAVOC 9 WEB CLIENT -- DEPLOY NOTES
===============================================================================

 This folder is the web client's page, served at https://havoc9.org/webclient/.
 It runs H9XASH, built for WebAssembly, in the player's browser. PLAY starts the
 game to H9's main menu, as starting H9XASH does; the menu's server browser lists
 H9's servers and joins them through one relay. Until a build is published beside
 it, the page says the client is in preparation.

 Nothing in this file is a secret, and nothing secret may be added to it: it
 sits in the site folder. The nginx config in section 8 hides it anyway.


 1. WHAT IS HERE
 ---------------
   index.html      the page, in the site's own style (nav, header, footer)
   client.js       the loader: checks for a build, fetches the game files,
                   starts the engine, carries its network over the relay, keeps
                   the player's settings in the browser
   h9audio.js      the game's sound on the audio thread: an AudioWorklet that
                   plays what the engine mixes (section 11), so a held key or a
                   long frame cannot leave a hole in the sound
   settings.json   where the build is, the relay, the master address and the
                   JOIN links (section 4)
   DEPLOY.txt      this file

   Made by the packer (section 3D) and copied in at deploy time:
   engine/         xash.js, xash.wasm
   manifest.json   every game file with its size and hash, and the fonts for
                   VGUI text
   preload.json    the files fetched before the engine starts
   game/           the game files: the engine's disk (on the VPS it lives
                   outside the site folder, see section 5)

   Tools, in TSM\tools (copies in the repository's tools\):
   make_webclient_game.py   the packer (3D)
   serve_webclient.py       serves the site and a package on this PC the way the
                            VPS does, to try a build (3E)

 C. The client library: reTS, for the browser

   reTS stands in for TS 3.0's closed client.dll, as it already does natively:
   the web client is built from the same reTS source as H9XASH's client.dll
   (the cloak in view.cpp, the mouse-button release in inputw32.cpp).

   VGUI: reTS\cl_dll\CMakeLists.txt's Emscripten branch (the block marked "H9
   web client") compiles FWGS's freevgui into the client: its Xash3D support
   layer with INTERNAL_VGUI_SUPPORT, which names the entry point
   InitVGUISupportAPI; the browser font backend platform\emscripten\font.cpp
   (posix's draws no text); FREEVGUI_NO_GLOBAL_NEW. The sources come from
   HALFLIFE_XASH3D_DIR, by default ..\xash3d-fwgs, so H9's VGUI scheme
   (freevgui-h9-scheme.patch) comes with them. gameinfo.txt's
   internal_vgui_support 1, written by the packer, makes the engine take VGUI
   from the client. reTS's own openvgui and vgui_support folders stay empty.

     emcmake cmake -S D:\Downloads\TSM\reTS -B D:\Downloads\TSM\webclient-build\reTS-wasm
           -G Ninja -DCMAKE_BUILD_TYPE=Release
           -DCMAKE_INSTALL_PREFIX=D:\Downloads\TSM\webclient-build\reTS-install\ts
     cmake --build D:\Downloads\TSM\webclient-build\reTS-wasm --target client -- -j6

   (The install prefix must end in the mod's folder name; nothing is
   installed.) Output: reTS-wasm\cl_dll\client_emscripten_wasm32.wasm, 832 418
   bytes (277 570 gzip). It compiled with no error and no source change beyond
   that CMake block. Its 1036 imports all resolve against xash.wasm's exports
   and xash.js's functions, and it exports F (the client API), the classic
   exports, InitVGUISupportAPI, GetVGUISupportAPI, IN_ClientLookEvent and
   IN_ClientMoveEvent.

   CMake 4.3.0 prints a warning from Emscripten's toolchain that it "does not
   support emscripten shared libraries". reTS turns shared libraries back on
   after project() and links with -sSIDE_MODULE=1, and the output is a proper
   side module, so the warning does not apply here (CMake 4.3.3 and later do
   not print it).

   The server library is not built: the page joins servers and starts none.

 4. SETTINGS.JSON
 ----------------
   engine     folder with xash.js and xash.wasm             "engine/"
   game       folder the game files are served from          "game/"
   manifest   the packer's file list                         "manifest.json"
   preload    the packer's preload list                      "preload.json"
   gamedir    the game folder on the engine's disk           "ts"
   args       more engine arguments, e.g. ["-dev", "2"]
   commands   console commands once the engine is up         ["voice_enable 0"]
   fonts      [{ family, file, weight, style }] in place of the manifest's
              list (3D); empty, as shipped, to use the manifest's
   relay      the relay's path on this site, or a wss:// URL "relay"
   master     the address the relay answers as the master    "192.0.2.1:27010"
              server (section 6); the page writes "clearmasters" and
              "addmaster <master>" into ts\networking_resolved.cfg
   servers    [{ name, address }]: small JOIN links under PLAY, shortcuts
              that join a server as soon as the game is up. address is
              ip:port, numbers: the browser engine resolves no host names. An
              entry without an address is not shown.

   The engine starts as h9xash.bat starts it: -game ts -console, then
   settings.json's args. Before the menu shows, the page writes for the
   player: userid_resolved.cfg (cl_h9_userid, from the signed-in account's
   player id, window.h9webAccount.playerId, or else an id kept in this
   browser), networking_resolved.cfg (the master), menu_bg_video_resolved.cfg
   (a video picked from menu_bg_videos.txt, fetched with the preload), an empty
   menu_music_resolved.cfg (the page starts a random track of menu_music.txt
   itself once it has fetched it), the config.cfg kept in this browser, and
   .xash_id.

   The game's X, its Quit and quit or exit in the console end on the site's
   front page (../index.html), as LEAVE does; the config.cfg the engine writes
   as it shuts down is kept first. From that quit on the page calls into the
   engine no more (client.js quitHome): the engine has shut down and freed its
   memory, though the module stays loaded, and a command sent then (the page's
   disconnect as it leaves) freed memory twice ("Mem_FreeBlockSmall: not
   allocated or double freed", cmd.c). engine-h9-webquit.patch makes the
   engine refuse such a command too, from its next web build. An error that
   ends the game stays on the screen instead. The menu's minimize button leaves
   full screen.

 6. THE RELAY
 ------------
   A page cannot send UDP. The relay, with the site's accounts and login, is
   h9web's (its own README.txt). What the page and the engine expect of it:

   * One WebSocket per engine UDP socket, at /webclient/relay, for every H9
     server. The browser sends the site's session cookie with it; the relay
     takes signed-in players only, and only from the site's own Origin.
   * Every binary message, both ways, is one datagram: bytes 0-3 an IPv4
     address, bytes 4-5 a port (both network order), then the UDP payload.
     From the page the address is the destination; from the relay, the source.
     So the engine's sendto and recvfrom keep each server's own address.
   * It sends only to the servers on H9's list, from one UDP port of its own
     per WebSocket for the life of that WebSocket, so a server sees one stable
     address per player socket.
   * The master server: 192.0.2.1:27010 (TEST-NET-1: never a real server). The
     page adds it as the engine's only master, and the relay answers the
     server browser's query there itself with H9's list. The engine sends
       31 FF "0.0.0.0:0" 00 <infostring> 00
     (no FF FF FF FF; the infostring has \gamedir\ts and \key\1 among others)
     and parses the reply
       FF FF FF FF 66 0A   7F KK KK KK KK 00   then 6 bytes per server
       (4 IPv4 + 2 port, network order)   then 00 00 00 00 00 00
     The 7F block must be there: for an Xash master the engine always reads
     one byte before the list. Then the engine asks each server
     "FF FF FF FF info 49" itself; that and every connect go to the server's
     own address, as normal datagrams.
   * Datagrams up to at least 1500 bytes (the connect's bandwidth test sends
     1400-byte fragments). After an idle close the page opens a new WebSocket
     on the engine's next datagram.
   * A refused upgrade (the page sees a close before any open) or a close for
     sending too much (4429) makes the page wait 3 s before it asks again,
     then twice as long each time up to 30 s; the engine's datagrams in
     between are dropped. 4401 (signed out) and 4403 (suspended) put a line on
     the game's screen and are asked again every 30 s.
   * LAN discovery (broadcast) is not carried.

   One relay serves every H9 server. The page needs nothing per server but the
   relay's list.


 7. THE GAME SERVER
 ------------------
   The relay's list holds Xash servers: H9XASH's h9xash_server.bat (HAVOC 9.exe
   -dedicated, with Metamod, AMXX and RCBot). A Steam hlds server refuses every
   Xash client, browser or native ("STEAM validation rejected",
   docs\ENGINE_DIFFERENTIALS.txt). The relay may run on the VPS while the game
   servers stay where they are; a server then sees every browser player coming
   from the relay's address.

   Because every browser player comes from the relay's one address, in each
   server's config:

     sv_connect_max_per_ip 0   default 3: a fourth browser player still loading
                               is refused while three others load
     sv_timeout 120            a browser loading a map it has not fetched yet
                               stands still for a while
     sv_query_rate_limit 30    default 1: one info, ping, players or rules
                               reply a second per address (a burst of 5).
                               Every browser player's server browser asks from
                               the relay's address, so with 1 most of them see
                               the server missing from the list. 0 turns the
                               limit off
     sv_connect_timeout 600    default 60: a client that has not spawned that
                               long after it connected is dropped, whatever
                               it still sends. A first visit fetches the
                               game's files for the map in the browser
                               before it can spawn (300 MB on
                               h9_te_neuropolis): over a slow link that is
                               minutes
     sv_connect_timeout_ban 0  default 1: the engine then also bans the
                               dropped client's address for 2 minutes, which
                               for a browser player is the relay's address:
                               every browser player of the server at once

   The engine also allows about one challenge and one connect a second per
   address (a burst of 5; not a cvar), so players joining in the same few
   seconds retry for a moment. None of H9's plugins look at player addresses;
   each browser player still has its own h9_clientid (cl_h9_userid).

   Open each server's UDP port to the relay's address (and to native players).


 8. NGINX
 --------
   /etc/nginx/sites-available/havoc9.org, linked into sites-enabled, and the
   two snippets it includes from /etc/nginx/snippets/ (below). nginx-setup.sh
   writes all three. Always nginx -t before systemctl reload nginx.

     # havoc9.org, written by havoc9.org/deploy/nginx-setup.sh (DEPLOY.txt section 8 explains each
     # part). After an edit by hand: nginx -t && systemctl reload nginx

     # Rate limits in front of h9web, per client address (h9web keeps its own as well); over one,
     # nginx answers 429. Sign-in, sign-up and the password and name forms share a stricter one.
     map $uri $h9web_auth_limit {
         ~^/api/(?:login|signup|password|account/rename)$  $binary_remote_addr;
         default                                           "";
     }
     limit_req_zone $binary_remote_addr zone=h9web_api:10m rate=10r/s;
     limit_req_zone $h9web_auth_limit zone=h9web_auth:10m rate=6r/m;

     # H9XASH-Updater's own requests, by its X-H9-Updater header and its User-Agent: only those get
     # the files under /files/ (DEPLOY.txt section 8). It hides the folder; it is not access control.
     map "$http_x_h9_updater:$http_user_agent" $h9_updater {
         ~^1:H9XASH-Updater/  1;
         default              0;
     }

     server {
         listen 80;
         listen [::]:80;
         server_name havoc9.org www.havoc9.org;
         server_tokens off;

         # Let's Encrypt's checks, at every renewal
         location /.well-known/acme-challenge/ { root /var/www/letsencrypt; }
         location / { return 301 https://havoc9.org$request_uri; }
     }

     server {
         listen 443 ssl;
         listen [::]:443 ssl;
         server_name www.havoc9.org;
         server_tokens off;
         ssl_certificate     /etc/letsencrypt/live/havoc9.org/fullchain.pem;
         ssl_certificate_key /etc/letsencrypt/live/havoc9.org/privkey.pem;
         include snippets/havoc9.org-tls.conf;
         add_header Strict-Transport-Security "max-age=31536000" always;
         return 301 https://havoc9.org$request_uri;
     }

     server {
         listen 443 ssl;
         listen [::]:443 ssl;
         http2 on;
         server_name havoc9.org;
         server_tokens off;
         ssl_certificate     /etc/letsencrypt/live/havoc9.org/fullchain.pem;
         ssl_certificate_key /etc/letsencrypt/live/havoc9.org/privkey.pem;
         include snippets/havoc9.org-tls.conf;

         root /var/www/havoc9.org;
         index index.html;
         include snippets/havoc9.org-headers.conf;

         # only the methods the site and h9web use; small request bodies unless a location below
         # allows more; slow clients are cut off
         if ($request_method !~ "^(?:GET|HEAD|POST|PUT|PATCH|DELETE)$") { return 405; }
         client_max_body_size 16k;
         client_header_timeout 15s;
         client_body_timeout 30s;
         keepalive_timeout 30s;

         # the two published downloads, matched before the archive rule below
         location ~ "^/downloads/H9XASH(-linux)?\.zip$" { }
         # the downloads' file index (vps/linux/README-VPS.txt step 13 lists what goes in it): a plain
         # listing, and the packages, their reports and the checksums in it. ^~ keeps the rules below
         # away from it, so the ones nested here stand in for them: a dot file, a subfolder or any
         # other kind of file there is a 404
         location ^~ /downloads/files/ {
             autoindex on;
             autoindex_exact_size off;
             location ~ /\. { return 404; }
             location ~* "^/downloads/files/[^/]+\.(?:zip|exe|txt)$" { }
             location ~ "^/downloads/files/." { return 404; }
         }

         # never for visitors: dot files and folders (.git, .env, .gitattributes), backups, archives,
         # sources, scripts, keys and logs, these notes and the VPS scripts
         location ~ /\.(?!well-known/) { return 404; }

   WHAT AN .htaccess FILE WOULD DO. nginx reads no .htaccess (that is
   Apache's); the same rules live in the config above:
   * Never served (404): dot files and folders (.git, .env, .gitattributes;
     .well-known excepted), backups (*.bak*, *.orig, *.old, *.swp, *~ ...),
     archives, sources and scripts (.sma, .inc, .amxx, .sh, .ps1, .bat, .cmd,
     .py, .patch, .diff), keys and certificates, SQL and database side files,
     logs, these notes and deploy/. Game files under /webclient/game/ keep
     their own names (.cfg, .txt, .lst, .db ...), so the list leaves those
     alone. /api/ is ^~, so the list never touches h9web's addresses (a
     username may end in .sh).
   * /downloads/H9XASH.zip and /downloads/H9XASH-linux.zip, the two client
     packages the DOWNLOADS page links, are served: their location comes
     before the archive rule, which answers 404 for every other .zip.
   * /downloads/files/ is the downloads' file index (ALL FILES on the
     DOWNLOADS page; vps/linux/README-VPS.txt step 13 lists what goes in
     it): a listing (autoindex), and only the .zip, .exe and .txt files in
     it are served; a dot file, a subfolder or any other file there is a
     404. It is ^~, so the archive rule above never touches it, and its
     nested locations stand in for the rest. The folder carries an
     .htaccess with the same rules, for an Apache host.
   * Methods: GET, HEAD, POST, PUT, PATCH and DELETE (405 for any other). No
     OPTIONS: no other site may call the API (h9web sends no CORS headers).
   * Request bodies: 16k unless a location allows more (128k for /api/, 11m for
     the picture upload, 1k for the relay, 4k for the server list); slow
     headers (15 s) and bodies (30 s, 60 s for a picture) are cut off.
   * /serverlist/ is the H9 server list (serverlist-bot\README.md), which
     listens on 127.0.0.1:8081 only; networking.ini's list_bot is
     https://havoc9.org/serverlist. With the list stopped nginx answers 502
     there and the game's Internet tab shows no H9 list.
   * /files/ holds H9XASH-Updater's files (tools\updater\README_UPDATER.txt):
     manifest.json and each game file under its SHA-256, which
     stage-h9xash.ps1 publishes into dist\files for copying here. Only the
     updater's own requests get them: without its X-H9-Updater: 1 header
     and an H9XASH-Updater/ User-Agent (the map $h9_updater), every address
     there is a 404, so is any other name, and there is no listing. That
     keeps the folder out of browsers and search engines; it is not access
     control (the files are the public game). The manifest is revalidated
     each time (no-cache), the files are kept a year (immutable).
   * Rate limits per client address: 10 requests a second (bursts of 60) to
     /api/, and 6 a minute (bursts of 10) to sign-in, sign-up, password change
     and name change requests; the relay's upgrades and picture uploads share
     the first. h9web's own limits (h9web/README.txt section 2) stay; these
     stop a flood before it reaches Node. Behind a CDN or another proxy every
     visitor would share its address: set real_ip_header and set_real_ip_from
     for it first.
   * server_tokens off: the Server header and the error pages name no version.
   * Headers on every page and file: Strict-Transport-Security for a year,
     X-Content-Type-Options nosniff, Referrer-Policy
     strict-origin-when-cross-origin, X-Frame-Options SAMEORIGIN and
     Content-Security-Policy frame-ancestors 'self' (no other site may frame a
     page; the web client framing a server's MOTD page is the other way round),
     base-uri 'self' and object-src 'none', and a Permissions-Policy that turns
     off the camera, location, payments, USB, serial, HID, Bluetooth, MIDI,
     screen capture and Topics. The forum, admin and account pages carry their
     full Content-Security-Policy in a <meta> tag; the web client's page allows
     https: frames for a server's splash MOTD; the MEDIA page (media/) allows
     pictures from https://i.ytimg.com and frames from
     https://www.youtube-nocookie.com only, for its videos (nothing in nginx to
     change for it).

   TLS (the tls snippet): TLS 1.2 and 1.3 only, Mozilla's "intermediate"
   ciphers without its DHE ones (no dhparam file needed; every TLS 1.2 client
   in use has ECDHE), a shared session cache and no session tickets. nginx
   settles the TLS version on a port with the default server of that port:
   with other sites on this VPS, the first 443 site (or the one marked
   default_server) must include the same snippet, or older versions stay on.
   nginx-setup.sh's last check says whether a TLS 1.1 handshake is refused.
   Left as they are, for the owner to decide: includeSubDomains and preload in
   Strict-Transport-Security (every subdomain would have to serve HTTPS, and
   preload is hard to undo), and a full Content-Security-Policy header for the
   pages that have none (it has to be tried in a browser first).

   http2 on; needs nginx 1.25.1 or later (nginx -v). On an older nginx
   (Ubuntu 24.04 has 1.24, Debian 12 has 1.22) leave that line out and write
   listen 443 ssl http2; and listen [::]:443 ssl http2; in the havoc9.org
   block instead.

   MIME types: .wasm must be application/wasm (nginx's stock mime.types may
   lack it, hence the types blocks), .js text/javascript, .json
   application/json; game files are application/octet-stream, and the page
   reads them as bytes whatever the type says.

   COOP / COEP: not needed. This engine build has no threads (no -pthread in
   engine\wscript's link flags), so it needs no SharedArrayBuffer and no
   cross-origin isolation. If a later build adds threads, isolate /webclient/
   only, in its locations:

       add_header Cross-Origin-Opener-Policy "same-origin" always;
       add_header Cross-Origin-Embedder-Policy "credentialless" always;

   "credentialless" keeps the page's Google Fonts loading; "require-corp" would
   need CORS headers on them. self.crossOriginIsolated in the page's console
   tells whether it took.

   THE CERTIFICATE comes from Let's Encrypt, by havoc9.org/deploy/https-setup.sh.
   Run it as root on the VPS once DNS points both names at it, before this
   file is installed: nginx refuses a site whose certificate files do not
   exist yet. It installs certbot, puts up a small plain-HTTP site that only
   answers Let's Encrypt's checks (from /var/www/letsencrypt) and sends
   everything else to HTTPS, fetches a test file through each name the way
   Let's Encrypt will, asks for one certificate for havoc9.org and
   www.havoc9.org, and adds the hook that reloads nginx after each renewal:

     bash https-setup.sh               a test certificate, from Let's Encrypt's
                                       staging service
     STAGING=0 bash https-setup.sh     the real one, in the test one's place

   The test one first: a wrong DNS record or a shut port 80 then costs
   nothing, where the real service allows 5 failed checks per name an hour
   and 5 certificates for the same names a week. Then
   havoc9.org/deploy/nginx-setup.sh installs this file for the domain, takes
   out the stand-in site and reloads: the port-80 block above answers the
   checks from then on. On a fresh VPS nginx-setup.sh alone does all of it:
   it installs nginx and, with no certificate yet, runs https-setup.sh (a
   test certificate, then the real one) first. nginx-setup.sh writes the
   config of this section; keep the two in step.

   * Renewal: certbot's own timer (snap.certbot.renew.timer, or certbot.timer
     from apt) renews it through the port-80 block. Keep that location and
     port 80 open, or renewals fail. certbot renew --dry-run tests it.
   * Nothing warns before it expires: Let's Encrypt stopped its expiry emails
     in 2025. certbot certificates shows the date; an outside expiry check is
     worth having. The certificates are getting shorter too (90 days, 64 from
     February 2027, then 45), so never put one in by hand.
   * Strict-Transport-Security makes a browser that has seen the site refuse
     plain HTTP for it, and refuse a bad certificate with no way past, for a
     year: a certificate that lapses locks those visitors out until it is
     renewed.
   * No ssl_stapling: Let's Encrypt's certificates carry no OCSP address any
     more (it ended OCSP in 2025).
   * Optional: a CAA record, havoc9.org. CAA 0 issue "letsencrypt.org", so no
     other certificate authority may issue for the domain.
   * The script must reach the VPS with Unix line ends, as git keeps it
     (deploy/.gitattributes). If bash answers $'\r': command not found, it
     was saved with Windows ones: sed -i 's/\r$//' https-setup.sh

 10. THE VPS AND THE DOMAIN, IN ORDER
 ------------------------------------
   Steps 3 and 5 to 9 (all but the DNS and the web client's game files) and
   h9web's backups (section 13) come as one package:
   make-vps-package.ps1 in the repository's root writes
   dist\havoc9-vps-linux-<build>-<yyyyMMdd-HHmm>.zip, and its setup.sh does
   them on the VPS, step by step in vps/linux/README-VPS.txt
   (dist\havoc9-vps-windows-<build>-<yyyyMMdd-HHmm>.zip and
   vps/windows/README-WINDOWS.txt for a Windows host). The order below is the
   same.
   1. Build the engine (3B) and reTS's client (3C), package (3D). Try it on
      this PC with serve_webclient.py (3E).
   2. A real join on the LAN, before anything public: an H9 server on the LAN
      (h9xash_server.bat), h9web's relay on this PC with that server on its
      list, serve_webclient.py --relay ws://127.0.0.1:<relay port>/. PLAY,
      Multiplayer > Internet games: the server is listed; join it from there,
      leave it, join it again; also "connect <ip>:<port>" in the console.
   3. The VPS: a current Debian or Ubuntu with nginx and certbot. Where the
      provider offers disk or volume encryption, turn it on (it protects a
      disk or snapshot that leaves the provider, not a running server); SSH
      by key only; unattended-upgrades for security updates; a firewall open
      only for SSH, 80, 443 and the game ports.
   4. DNS: A (and AAAA) records for havoc9.org and www.havoc9.org.
   5. The certificate: havoc9.org/deploy/https-setup.sh (section 8).
   6. The site and the build in place (section 5).
   7. h9web: accounts and the relay, with H9's server list (section 6),
      and its backup timer (section 13).
   8. settings.json: the relay and master as shipped; JOIN links only if
      wanted (section 4).
   9. nginx: havoc9.org/deploy/nginx-setup.sh (section 8).
   10. Each game server's cvars and firewall (section 7).
   11. Checks:
         curl -sI https://havoc9.org/webclient/
             200
         curl -sI https://havoc9.org/webclient/engine/xash.wasm
             200, content-type: application/wasm
         curl -s https://havoc9.org/webclient/manifest.json | head -c 120
             {"version":1,...
         curl -sI https://havoc9.org/webclient/game/ts/addons/amxmodx/configs/ts_advertise.cfg
             404
         curl -sI https://havoc9.org/webclient/DEPLOY.txt
             404
         curl -sI https://havoc9.org/deploy/https-setup.sh
             404
       Then in a browser: sign in, PLAY, the main menu; Multiplayer > Internet
       games lists the servers; join one, and its console shows the player
       coming from the relay's address. window.h9web.log in the page's console
       holds the engine's log.


 11. ENGINE CHANGES FOR THE BROWSER
 ----------------------------------
   * engine-h9-websound.patch (xash3d-h9-patches\patches, registered in xash.bat,
     logged in PATCH_CHANGELOG.md): in the browser build only (#if
     XASH_EMSCRIPTEN), the sound mixer skips the time a long frame already
     played instead of painting into it, and mixes at least 0.2 s ahead,
     whatever _snd_mixahead says (TS 3.0's config.cfg sets 0.1). A frame in a
     browser can run long: a game file is fetched the first time it is read.
     Written for H9 from the msr-web kit's description; none of the kit's files
     was copied. The Windows build compiles as before.
     The same patch gives the browser's sound a thread of its own. SDL plays
     through a ScriptProcessorNode, which runs on the page's main thread, so a
     frame in progress, or the browser's own work for a key held down, held the
     sound back and left a hole in it. The engine now hands what it mixes to the
     page (Module.audio, audioFeed in client.js) and an AudioWorklet
     (h9audio.js) plays it; the mixer's clock is the audio thread's own. Where
     the page has no Module.audio, or the browser no AudioWorklet or no secure
     context (plain http on any host but localhost), SDL's device plays it, as
     it always did. Module.audio.stats() in the console says which one is in
     use and how many frames it played, was sent and had to play as silence.
   * engine-h9-webmenu.patch (the same, row 26 of PATCH_CHANGELOG.md), in the
     browser build only: the main menu's video is decoded by the page and drawn
     by the engine (avi_ffmpeg.c gets an XASH_EMSCRIPTEN branch beside the
     FFmpeg one: Module.video in client.js decodes H9's Motion-JPEG AVI with the
     browser's own JPEG decoder, and the engine uploads each picture with
     GL_UpdateTexture and draws it as the FFmpeg branch does); Sys_Quit stops
     the frames and tells the page instead of jumping to a jump buffer the
     browser build never set (the X and Quit used to leave a dead canvas); the
     minimize command asks the page. The packer re-encodes a menu video in any
     other codec to Motion-JPEG with ffmpeg, so the page needs only the one
     decoder; H9's needs none.
   * Not carried: the kit's freevgui App::panelRemoved. It guards against a
     panel deleted while the app still points at it; reTS's client takes panels
     out (CListBox, CGrid, the command menu's removeAllChildren) without
     deleting them, so the case does not arise in TS.
   * No engine change was needed for the relay: the webassembly patch's socket
     hooks already hand each datagram's address to the page (Module.net), and
     client.js frames it.

 13. H9WEB BACKUPS ON THE VPS
 ----------------------------
   h9web's state is /var/lib/h9web: the database, the modules' files (the
   forum's pictures, the presence keys), secrets.json and data.key. It is
   not in git. bin/h9web-backup.js backs it up and puts it back
   (h9web/README.txt section 10 has every option); it runs as h9web:
     B="sudo -u h9web /usr/bin/node /opt/h9web/bin/h9web-backup.js --config /etc/h9web/config.json"

 13A. The daily timer
   /etc/systemd/system/h9web-backup.service:
     [Unit]
     Description=h9web backup
     [Service]
     Type=oneshot
     User=h9web
     UMask=0077
     ExecStart=/usr/bin/node /opt/h9web/bin/h9web-backup.js --config /etc/h9web/config.json backup --out /var/lib/h9web/backups --keep 14
     ExecStartPost=/usr/bin/find /var/lib/h9web/backups -name "h9web-*.db" -mtime +14 -delete
   /etc/systemd/system/h9web-backup.timer:
     [Unit]
     Description=Daily h9web backup
     [Timer]
     OnCalendar=daily
     Persistent=true
     [Install]
     WantedBy=timers.target
   then
     sudo systemctl daemon-reload
     sudo systemctl enable --now h9web-backup.timer
   It takes the place of the unit that ran h9web-admin backup; the
   ExecStartPost line deletes that unit's h9web-*.db copies as they age. A
   backup holds the password hashes and the presence keys: the files are
   0600 and the folder 0700 (UMask=0077 and the command itself). Check it:
     systemctl list-timers h9web-backup.timer
     journalctl -u h9web-backup --since today
     $B list

 13B. Encrypted copies off the VPS
   Only encrypted backups leave the VPS. A passphrase file only h9web reads:
     sudo install -m 600 -o h9web -g h9web /dev/null /etc/h9web/backup-passphrase
     sudo nano /etc/h9web/backup-passphrase     (one line, 12 characters or more)
   Keep a copy of the passphrase offline, with secrets.json and data.key:
   without it the encrypted backups cannot be opened, and they hold the keys.
   /etc/systemd/system/h9web-backup-offsite.service, as h9web-backup.service
   but with
     Description=h9web encrypted backup for copies off the VPS
     ExecStart=/usr/bin/node /opt/h9web/bin/h9web-backup.js --config /etc/h9web/config.json backup --encrypt --with-keys --passphrase-file /etc/h9web/backup-passphrase --out /var/lib/h9web/offsite --keep 7
   and no ExecStartPost, and h9web-backup-offsite.timer as the daily one
   (OnCalendar=daily); sudo systemctl enable --now h9web-backup-offsite.timer.
   Then copy /var/lib/h9web/offsite off the machine (rsync or scp as root,
   on a schedule of your own); never the whole of /var/lib/h9web. Each copy
   carries secrets.json and data.key too (--with-keys), sealed under the
   passphrase with the rest, so one file and the passphrase are enough for a
   new VPS. Without --with-keys the offline copy of the keys is needed as
   well. Check a copy where it lands (any machine with Node 24 and h9web):
     H9WEB_BACKUP_PASSPHRASE=... node bin/h9web-backup.js verify <file>
   or with --passphrase-file <file> instead of the variable.

 13C. Restoring on a new VPS
   1. Set the new VPS up as h9web/README.txt section 7 says, with the h9web
      code the backup was made with (verify prints its h9web and module
      versions) and the old /etc/h9web/config.json and servers.json; do not
      start h9web (or stop it).
   2. The keys, unless the backup holds them (--with-keys):
        sudo install -d -m 700 -o h9web -g h9web /var/lib/h9web
        sudo install -m 600 -o h9web -g h9web secrets.json data.key /var/lib/h9web/
      and for an encrypted backup the passphrase file as in 13B.
   3. The backup, where h9web can read it, then restore:
        sudo install -m 600 -o h9web -g h9web <file> /var/lib/h9web/
        $B verify /var/lib/h9web/<file> --passphrase-file /etc/h9web/backup-passphrase
        $B restore /var/lib/h9web/<file> --passphrase-file /etc/h9web/backup-passphrase
      (no --passphrase-file for a backup that is not encrypted). restore
      refuses a secrets.json other than the backup's: every password and
      player id would fail.
   4. sudo systemctl enable --now h9web; the checks of h9web/README.txt
      section 9; sign in with an existing account. The timers (13A, 13B).
   5. Delete the copied backup file from /var/lib/h9web once all is well.

 13D. Moving to another VPS, in order
   1. A day before: lower the DNS records' TTL, so the switch is quick.
   2. The new VPS ready as in 13C steps 1 and 2, h9web not started.
   3. The old VPS: sudo systemctl stop h9web (nothing changes after this),
      then a last backup with all of it:
        $B backup --out /var/lib/h9web/move
   4. Copy that file to the new VPS (scp), restore it (13C step 3), start
      h9web there and check it.
   5. Point havoc9.org's A and AAAA records at the new VPS. Each game
      server's firewall opens its UDP port to the relay's address (section
      7): add the new address. The presence keys came with the backup, so
      the game servers go on reporting as before.
   6. Keep the old VPS stopped, with its data, for a few days; then wipe it.
